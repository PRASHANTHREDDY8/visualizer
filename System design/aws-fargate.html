Component Breakdown

Detailed responsibilities and technology choices for each component.

Fargate Compute Engine

Runs containers without provisioning or managing EC2 instances. Each task gets its own isolated kernel runtime.

microVM (Firecracker) Linux kernel ENI per task
Scales: Horizontally by launching more tasks. Each task is fully isolated with dedicated CPU/memory.

ECS Cluster & Services

Orchestrates container lifecycle: scheduling, placement, health checks, rolling deployments.

Task Definitions Services Capacity Providers
Scales: Service auto-scaling adjusts desired task count based on CloudWatch metrics or step/target-tracking policies.

Application Load Balancer

Routes traffic to Fargate tasks by path, host header, or query string. Health-checks unhealthy tasks out.

Layer 7 routing TLS termination Sticky sessions
Scales: Fully managed, auto-scales internally. No task-level changes needed.

Elastic Container Registry

Private Docker image repository integrated with ECS. Image scanning, lifecycle policies, cross-region replication.

Image scanning Immutable tags OCI compliant
Scales: Managed service. Lifecycle policies auto-delete old images.

VPC & Networking

Network isolation with private/public subnets, NAT gateways, and security groups. Each Fargate task gets an ENI.

awsvpc mode PrivateLink NAT Gateway
Scales: Ensure sufficient IP addresses in subnets. /20 CIDR or larger for high task counts.

Application Auto Scaling

Dynamically adjusts number of running tasks based on CPU utilization, memory, request count, or custom metrics.

Target tracking Step scaling Scheduled scaling
Scales: Target tracking keeps a metric (e.g., CPU 70%) stable by adding/removing tasks.

CloudWatch

Centralized logging (awslogs driver), metrics, alarms, and dashboards for Fargate tasks.

Log groups Container Insights Metric alarms
Scales: Managed. Use log retention policies to control cost.

IAM Roles

Task Role: permissions for your app code. Execution Role: permissions for ECS agent (pull images, write logs).

Task Role Execution Role Least privilege
Scales: No scaling concerns. One role definition applies to all tasks in a service.

Decision Matrix

Choose Fargate when...

  • You want container flexibility without server ops
  • Workloads are bursty or unpredictable
  • Team is small and cannot dedicate capacity to infra
  • Task isolation and security are critical
  • Running 10-500 tasks (sweet spot for cost)

Choose EC2 when...

  • Running 1000+ steady-state tasks (cost savings ~30-50%)
  • Need GPUs, custom AMIs, or specific instance families
  • Spot instances would save significantly
  • Require daemonsets or host-level agents
  • Have dedicated platform engineering team

Choose Lambda when...

  • Tasks are event-driven and complete in <15 min
  • Traffic is highly spiky with periods of zero load
  • Don't need persistent connections or long processes
  • Want true scale-to-zero (no idle cost)

Use Cases & Common Pitfalls

Where Fargate shines, and where it doesn't.

Primary Use Cases

Microservices

Each service runs as independent Fargate tasks with its own scaling policy. Perfect for decomposed architectures.

10-100 QPS/service Independent deploys

Batch Processing

Run ETL jobs, data pipelines, or ML inference. Spin up tasks, process data, terminate. Pay only for compute used.

Minutes to hours Scheduled or event-driven

CI/CD Workers

On-demand build agents that scale with your pipeline. No idle runners burning money overnight.

CodeBuild alternative Parallel builds

API Backends

RESTful/gRPC services behind ALB with auto-scaling. Handles variable traffic without capacity planning.

100-10K RPS Blue-green deploys

Anti-Use-Cases

Don't use Fargate for:

GPU Workloads

Fargate has no GPU support. Use ECS on EC2 with P/G instance families, or SageMaker for ML.

Steady High-Volume

Running 500+ tasks 24/7 is ~40% more expensive than EC2 with Reserved Instances. Do the math.

Sub-second Cold Starts

Fargate cold starts are 15-45 seconds. If latency-sensitive, keep minimum tasks running or use Lambda with provisioned concurrency.

Common Pitfalls

Oversizing task CPU/memory +

The mistake: Allocating 4 vCPU / 8 GB to a service that uses 0.3 vCPU at peak.

Why it happens: Teams copy-paste task definitions or "play it safe" without profiling.

The consequence: 10x cost waste. Fargate charges per vCPU-second and GB-second regardless of utilization.

The fix: Start small (0.25 vCPU / 0.5 GB), monitor CloudWatch Container Insights for actual usage, right-size after 1 week of production data.

Ignoring task startup time in health checks +

The mistake: Setting ALB health check interval to 5s with 2 unhealthy threshold. Tasks get killed during startup.

Why it happens: Default health check settings assume instant readiness. Fargate tasks need time to pull images + start.

The consequence: Tasks stuck in a restart loop. Service never becomes stable.

The fix: Set health check grace period (60-120s), use startupHealthCheckGracePeriodSeconds in the service definition. Add a /health endpoint that returns 200 only after full initialization.

Running out of ENI IP addresses +

The mistake: Deploying 200 tasks in a /24 subnet (254 IPs). Fargate uses awsvpc mode — each task needs its own IP.

Why it happens: Works fine at small scale, then deploys fail silently when IPs exhaust.

The consequence: New tasks can't launch. Service stuck at old count. No obvious error in ECS console.

The fix: Use /20 or larger subnets. Spread across multiple AZs. Monitor "ENI trunking" if using large task counts. Consider enabling ENI trunking for higher density.

Not configuring proper stop signals +

The mistake: Container doesn't handle SIGTERM. ECS sends SIGTERM, waits stopTimeout (default 30s), then SIGKILL.

Why it happens: Works fine locally. In production, rolling deploys kill in-flight requests.

The consequence: 502 errors during deployments. Lost messages in queue workers.

The fix: Handle SIGTERM in your app — drain connections, finish current requests, then exit. Set stopTimeout appropriately. Use ALB deregistration delay.

Using latest tag for container images +

The mistake: Task definition references myrepo:latest. Different tasks may run different code versions.

Why it happens: Convenient during development. Never updated for production.

The consequence: Non-reproducible deployments. Can't roll back to a known-good version. Debugging nightmares.

The fix: Use immutable tags (git SHA or semantic version). Enable immutable tags in ECR. Update task definition with specific image digest for each deploy.

Best Practices

Proven practices for running production Fargate workloads.

Design Phase

Right-size from day one

Start with the smallest Fargate configuration (0.25 vCPU / 0.5 GB). Load test, observe Container Insights, then right-size. It's easier to scale up than to convince finance to approve a cost-reduction project.

Design for horizontal scaling

Fargate tasks are ephemeral. Store no local state. Use external stores (Redis, DynamoDB, S3) for session data. This makes auto-scaling seamless.

Plan your networking early

Choose between public subnet (tasks get public IPs) or private subnet + NAT Gateway. Private is more secure but adds NAT cost. Use VPC endpoints for AWS services to avoid NAT data charges.

Implementation

Multi-stage Docker builds

Smaller images = faster cold starts. A Go binary in a scratch image pulls in 2s vs. 30s for a 1GB Node image. Target under 200MB. Use .dockerignore aggressively.

Separate task and execution roles

Execution role: pull from ECR + write CloudWatch logs. Task role: only the permissions your app needs (specific S3 buckets, DynamoDB tables). Never use the same role for both.

Use Secrets Manager, not env vars

Fargate natively integrates with AWS Secrets Manager. Reference secrets in your task definition — they're injected at runtime without appearing in the definition itself.

Operations

Enable Container Insights

Gives CPU, memory, network, and disk metrics per task. Essential for right-sizing and detecting memory leaks. Costs ~$0.01/task/day — worth every penny.

Blue-green deployments with CodeDeploy

Route traffic gradually to new task set. Automatic rollback on CloudWatch alarm. Zero-downtime deploys with the ability to abort at 10% traffic if errors spike.

Set up circuit breakers

ECS deployment circuit breaker: if new tasks keep failing health checks, automatically rolls back. Prevents a bad deploy from taking down your entire service.

Cost Optimization

Use Fargate Spot for fault-tolerant workloads

Up to 70% savings for batch processing, dev/test environments, or any workload that can handle interruptions. Mix Spot and On-Demand in the same service with capacity providers.

Compute Savings Plans

1-year or 3-year commitments save 20-50% on Fargate. If you have steady-state baseline, commit that portion and use on-demand for bursts above.

Scaling & Trade-offs

Capacity estimation, growth strategies, and failure scenarios.

Capacity Estimation

If each task handles 100 req/s at 0.5 vCPU, serving 10K RPS needs ~100 tasks. At $0.04/vCPU-hr, that's ~$50/day for compute alone. Add ALB, NAT, and data transfer.

10x Growth Strategy

Auto-scaling handles 10x naturally. Ensure: subnet IPs sufficient, service quotas raised (default 500 tasks/region), downstream databases can handle connection surge.

100x Growth Strategy

At this scale, consider hybrid: Fargate for burst + EC2 for baseline. Use capacity providers to mix. Shard services by tenant/region. Add caching aggressively.

Cold Start Mitigation

Keep minimum task count >0. Pre-pull images via ECR cache. Use smaller images. ECS warm pools reduce launch from 45s to ~15s for repeated task launches.

Failure: Task Crashes

ECS automatically replaces failed tasks. Deployment circuit breaker rolls back if >50% of new tasks fail. CloudWatch alarm triggers SNS notification to on-call.

Failure: AZ Outage

Spread tasks across 3 AZs with balanced placement strategy. ALB routes around unhealthy AZ. Service maintains desired count by launching in remaining AZs.

Trade-off: Cost vs. Latency

Minimum tasks = lower latency (no cold starts) but higher cost. Scale-to-zero saves money but adds 15-45s startup. Balance based on SLA requirements.

Trade-off: Isolation vs. Density

Fargate: strong isolation (microVM per task) but lower density than EC2 bin-packing. Choose Fargate for multi-tenant, EC2 for single-tenant high-density.
