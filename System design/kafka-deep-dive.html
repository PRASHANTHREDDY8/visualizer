Kafka Internals

How Kafka achieves high throughput and durability under the hood

▩ Log-Structured Storage

  • Each partition is an ordered, append-only commit log
  • Messages stored in segment files (default 1GB each)
  • Index files map offsets to positions in segment files
  • Time-based and size-based retention (default 7 days)
  • Log compaction: keeps latest value per key forever
  • Segments are immutable once rolled — enables zero-copy reads

▩ Zero-Copy Transfer

  • Uses sendfile() syscall — data goes from disk to NIC, bypassing user space
  • No serialization/deserialization on the broker for reads
  • Batch compression (gzip, snappy, lz4, zstd) at the producer
  • Consumers decompress — broker never touches message content
  • Page cache utilization — hot data served from OS cache
  • Sequential I/O patterns — 600MB/s writes on commodity hardware

▩ Replication Protocol (ISR)

  • Each partition has one leader and N-1 follower replicas
  • ISR (In-Sync Replicas): followers caught up within replica.lag.time.max.ms
  • Leader writes → followers pull → ack to producer
  • High watermark: highest offset replicated to all ISR members
  • Consumer only reads up to high watermark (committed data)
  • Unclean leader election: trade availability vs. data loss

▩ Consumer Group Protocol

  • Group Coordinator broker manages consumer membership
  • Partition assignment strategies: Range, RoundRobin, Sticky, CooperativeSticky
  • Rebalance triggered on: join, leave, crash, topic partition change
  • Cooperative rebalance: incremental, avoids stop-the-world
  • Offset commit: stored in __consumer_offsets topic
  • Static group membership: group.instance.id prevents unnecessary rebalances

Core Components

Detailed breakdown of each architectural component and its role

P

Producer

Publishes records to topics. Handles partitioning (key-based hash, round-robin, or custom), batching for throughput, compression, retries with idempotence, and exactly-once semantics via transactions.

Batching Compression Idempotent Transactional
B

Broker

Stores and serves data. Handles replication, leader election, request routing. Each broker can be leader for some partitions and follower for others. Brokers coordinate via KRaft consensus.

Zero-copy Page cache Sequential I/O ISR
C

Consumer

Reads records from partitions. Part of a consumer group for parallel processing. Manages offsets (auto-commit or manual), handles rebalances. Each partition consumed by exactly one consumer in a group.

Pull-based Offset tracking Group protocol
K

KRaft Controller

Manages cluster metadata using Raft consensus (replaces ZooKeeper). Handles broker registration, topic/partition metadata, leader election, and configuration management. Single controller quorum for the cluster.

Raft consensus Metadata log No ZK dependency
T

Topic & Partitions

Topics are logical channels. Partitions provide parallelism and ordering. Each partition is an ordered log. Key-based partitioning ensures related messages go to the same partition (ordering guarantee per key).

Ordered per partition Parallel reads Retention policy
KC

Kafka Connect

Framework for streaming data between Kafka and external systems. Source connectors ingest (DB CDC, files, APIs). Sink connectors export (HDFS, Elasticsearch, DBs). Handles offsets, schema evolution, scaling.

Source/Sink Distributed mode SMTs
KS

Kafka Streams

Client library for building stream processing applications. Supports stateful operations (joins, aggregations, windowing) with local state stores backed by changelog topics. No separate cluster needed.

Stateful Exactly-once Interactive queries
SR

Schema Registry

Stores and validates Avro, Protobuf, and JSON schemas. Enforces compatibility modes (backward, forward, full). Producers/consumers validate against registered schemas. Prevents data corruption.

Use Cases

Where Kafka shines in real-world system design — and concrete examples of each pattern

⚡ Event-Driven Microservices

Decouple services via events instead of synchronous API calls. Services publish domain events; others react asynchronously. Enables independent deployment and scaling.

OrderService → "order.created" → InventoryService, NotificationService, AnalyticsService

📊 Real-Time Analytics Pipeline

Stream clickstream, transactions, or sensor data to analytics systems in real-time. Replace batch ETL with continuous streaming. Sub-second data freshness.

Clickstream → Kafka → Flink/Spark → Druid/ClickHouse → Dashboard

📄 Log Aggregation

Centralize logs from hundreds of services. Higher throughput and lower latency than traditional log solutions. Enables real-time alerting alongside batch analysis.

App logs → Kafka → ELK Stack / Splunk + S3 long-term archive

🔁 Change Data Capture (CDC)

Stream database changes as events. Keep derived data stores (search index, cache, data warehouse) synchronized. Debezium + Kafka is the industry standard.

PostgreSQL WAL → Debezium → Kafka → Elasticsearch + Redis + Snowflake

📚 Event Sourcing

Store state as a sequence of events rather than current state. Kafka's durable log is a natural event store. Replay events to rebuild state or create new views.

Banking: Every transaction is an event → account balance derived from event replay

⚙ Stream Processing

Transform, enrich, aggregate, and join streams in real-time. Kafka Streams, Flink, or Spark Structured Streaming. Stateful processing with exactly-once guarantees.

Fraud detection: Join payment stream with user profile stream, apply ML model in real-time

🚀 CQRS (Command Query Separation)

Separate write (command) path from read (query) path. Commands produce events to Kafka; read models subscribe and build optimized query views. Scale reads independently.

Write → Kafka → Materialized View (DynamoDB) + Search (ES) + Analytics (Druid)

🔌 System Integration / Data Mesh

Kafka as the central nervous system connecting legacy and modern systems. Data products publish to shared topics. Schema Registry enforces contracts between teams.

Legacy mainframe → Kafka Connect → Kafka → Modern microservices + Data Lake

📢 Activity Tracking / Metrics

High-volume user activity (views, clicks, searches) and operational metrics. LinkedIn's original use case. Buffering layer between high-volume producers and slower consumers.

100K events/sec → Kafka → Real-time recommendations + Batch analytics (daily)

Tradeoffs & Design Decisions

Every architecture choice has costs — understanding Kafka's tradeoffs informs when to use it and how to configure it

Dimension Kafka's Choice Benefit Cost When It Hurts
Storage Model Append-only log with retention Sequential I/O, replay, multi-consumer Disk grows with retention; no in-place delete When you need immediate deletion (GDPR) or random-access patterns
Delivery Pull-based consumers Consumers control pace; natural backpressure Polling overhead; latency vs. CPU tradeoff in poll interval Ultra-low-latency requirements (<1ms) — push-based is faster
Ordering Ordered per partition only Enables parallelism; no global lock No global ordering across partitions When total order across all events is required (use single partition, sacrifice throughput)
Acks Configurable: acks=0, 1, all Tune latency vs. durability per use case acks=all adds latency proportional to slowest ISR member High-throughput + strong durability both needed: must choose or add brokers
Semantics At-least-once default, exactly-once optional Simple default; EOS available when needed EOS has ~3x latency overhead and requires idempotent producers + transactions Financial systems needing EOS at high throughput — complex configuration
Partitioning Fixed partition count at topic creation Predictable routing; stable consumer assignment Increasing partitions breaks key-ordering guarantee; can't decrease When workload is unpredictable — over-partition initially or re-architect
Message Size Optimized for small messages (KB range) High throughput, efficient batching Large messages (>1MB) degrade performance, memory, and replication Video/file transfer — use claim-check pattern (store in S3, send reference)
Consumer Groups Partition-level parallelism in groups Simple scaling: more partitions = more consumers Max consumers = partition count; rebalances can pause consumption Bursty workloads needing elastic scaling beyond partition count

When NOT to Use Kafka

Request-Response / RPC

Kafka is designed for asynchronous event streaming. If you need synchronous request-response with <10ms latency, use gRPC or HTTP. Kafka adds unnecessary complexity and latency.

Small-Scale / Simple Queuing

For fewer than 1K messages/second with simple queue semantics, RabbitMQ or Redis Streams are simpler to operate. Kafka's operational overhead isn't justified at small scale.

Database Replacement

Kafka is not a database. No ad-hoc queries, no secondary indexes, no efficient point lookups. Use it as a durable log that feeds actual databases.

Guaranteed Delivery to One Consumer

If you need message delivery to exactly one consumer with acknowledgment per message and dead-letter queues, traditional message brokers (RabbitMQ, SQS) are better fits.

Production Pitfalls

Hard-won lessons from operating Kafka at scale — avoid these common mistakes

Consumer Lag Explosion HIGH

Slow consumer processing causes lag to grow. If lag exceeds retention, data loss occurs silently. Consumers restart at earliest available offset and miss messages forever.

Mitigation: Monitor consumer lag (Burrow). Alert when lag exceeds 50% of retention window. Scale consumers, increase partitions, or add separate consumer groups for different processing speeds.

Rebalance Storms HIGH

Frequent consumer joins/leaves trigger rebalances. During rebalance, ALL partitions in the group stop being consumed (eager protocol). Long GC pauses or slow heartbeats trigger cascading rebalances.

Mitigation: Use CooperativeSticky assignor. Set session.timeout.ms=45000, heartbeat.interval.ms=15000. Use static group membership (group.instance.id). Tune max.poll.interval.ms based on actual processing time.

Under-Replicated Partitions HIGH

Broker disk full, network issues, or GC pauses cause followers to fall out of ISR. If min.insync.replicas isn't met, producers get errors. If unclean leader election is enabled, data loss on leader failure.

Mitigation: Monitor ISR shrink/expand. Keep unclean.leader.election.enable=false. Size disks for 2x expected usage. Use JBOD or RAID10 for disk failures. Set min.insync.replicas=2 with replication factor 3.

Hot Partitions (Skewed Keys) MEDIUM

One key produces vastly more messages than others → one partition gets disproportionate load → one consumer is overwhelmed while others idle. Common with tenant-based partitioning when one tenant dominates.

Mitigation: Add salt to hot keys (e.g., key + random(0-9)). Use custom partitioner that spreads hot keys across multiple partitions. Monitor partition size distribution. Consider separate topics for high-volume tenants.

Message Ordering Violations MEDIUM

With retries > 0 and max.in.flight.requests.per.connection > 1, failed batches retry out of order. Messages within the same partition arrive in wrong order silently.

Mitigation: Enable idempotent producer (enable.idempotence=true) which sets max.in.flight=5 safely with sequence numbers. Or set max.in.flight.requests.per.connection=1 (but reduces throughput by ~20%).

Offset Commit Issues (Duplicate Processing) MEDIUM

Auto-commit commits offsets before processing completes. If consumer crashes between commit and actual processing → message skipped. If commit fails → message re-processed. Neither is exactly-once.

Mitigation: Use manual offset commit AFTER processing. For exactly-once, use Kafka transactions or implement idempotent consumers (store offset alongside result in same transaction at the sink).

Topic Partition Count Mismatch MEDIUM

Too few partitions: can't scale consumers beyond partition count. Too many partitions: more memory per broker, longer leader elections, more open file handles, slower controlled shutdown.

Mitigation: Rule of thumb: partitions = max(target throughput / partition throughput, max consumer count). Start with 6-12 for moderate topics, 30-100 for high-volume. Kafka handles 10K+ partitions per broker in KRaft mode (better than ZK).

Schema Evolution Breaking Consumers LOW

Producer changes message format without coordination. Consumers fail to deserialize new format. No Schema Registry means silent data corruption or crashes on incompatible changes.

Mitigation: Always use Schema Registry. Enforce BACKWARD compatibility (new schema can read old data). Never remove required fields. Use Avro/Protobuf, not JSON (schema embedded in every message wastes bandwidth).

Large Messages Degrading Cluster LOW

Messages >1MB cause: broker memory pressure, slow replication, consumer fetch timeouts, and uneven batch sizes. max.message.bytes must be tuned across broker, topic, producer, AND consumer.

Mitigation: Use the claim-check pattern: store large payload in S3/GCS, send only the reference through Kafka. If unavoidable, tune message.max.bytes, replica.fetch.max.bytes, fetch.max.bytes, and max.partition.fetch.bytes consistently.

▲ Scaling Strategies

  • Horizontal: Add brokers → reassign partitions with kafka-reassign-partitions tool
  • Partitions: More partitions = more parallelism. Scale consumers linearly up to partition count
  • Tiered Storage: Offload old data to S3 — keep hot data on local SSDs, cold data in object store
  • Multi-cluster: MirrorMaker2 / Cluster Linking for cross-region replication
  • Rack awareness: Spread replicas across failure domains (AZs, racks)
  • Quota management: Per-client throttling prevents one producer from starving others

▲ Capacity Planning Formula

  • Storage: msg_size × msgs/sec × retention_sec × replication_factor
  • Network in: msg_size × msgs/sec × replication_factor (leader receives + replicates)
  • Network out: msg_size × msgs/sec × num_consumer_groups
  • Brokers: max(storage_needed / disk_per_broker, throughput_needed / broker_throughput)
  • Partitions: max(target_throughput / partition_throughput, desired_consumer_parallelism)
  • Memory: ~1MB page cache per active partition + OS overhead + JVM heap (6-8GB)
