⚠ Use Cases & Common Pitfalls

Primary Use Cases

Photo/Video Sharing

Core feature: upload, filter, share media to followers. ~100M photos/day. Requires fast upload, processing pipeline, and CDN delivery.

News Feed

Ranked, personalized feed combining posts from followed accounts. ML-ranked with engagement signals. Target: <200ms latency.

Stories (Ephemeral Content)

24-hour disappearing content. 500M+ daily viewers. High write throughput, TTL-based expiry, view tracking.

Direct Messaging

1:1 and group messaging with media support. Real-time delivery via WebSocket. End-to-end encryption option.

Explore/Discovery

ML-powered content recommendation for non-followed accounts. Collaborative filtering + content-based signals.

Reels (Short Video)

TikTok-style short-form video feed. Requires video transcoding, recommendation engine, and low-latency streaming.

Common Pitfalls

Fan-out storm for celebrity posts ▸
The mistake
Using pure push model for all users, including those with 100M+ followers.
Why it happens
Push model is simpler and works great for normal users (<10K followers).
Consequence
Single celebrity post triggers 100M+ writes, causes write storms and cascading delays.
The fix
Hybrid approach: push for users <10K followers, pull (merge at read time) for celebrities.
Hot partition on user_id sharding ▸
The mistake
Sharding only by user_id, which creates hot partitions for celebrity profiles.
Why it happens
User_id seems like the natural shard key for a social network.
Consequence
Celebrity shards get 1000x more reads than average, causing latency spikes.
The fix
Multi-layer caching in front of hot shards; separate read replicas; consider post_id based sharding for feed data.
Thundering herd on cache expiry ▸
The mistake
Setting identical TTLs for popular content cache entries.
Why it happens
Uniform TTL policy is easy to configure and reason about.
Consequence
All caches for trending content expire simultaneously, flooding DB with requests.
The fix
Jittered TTLs (base + random offset); cache warming; request coalescing (single-flight pattern).
Unbounded media processing queue ▸
The mistake
No backpressure on the media processing pipeline during viral events.
Why it happens
Normal traffic fits processing capacity; spikes are underestimated.
Consequence
Queue grows unbounded, processing latency goes to minutes/hours, OOM crashes.
The fix
Bounded queues with backpressure; priority lanes (paid/verified users first); auto-scaling workers with lag-based triggers.
Not separating read and write paths ▸
The mistake
Using the same database cluster for both uploading posts and serving feeds.
Why it happens
CQRS feels over-engineered early on.
Consequence
Write spikes (e.g., a viral moment) degrade feed read latency for all users.
The fix
CQRS: separate write path (post ingestion) from read path (feed serving). Different optimization for each.

✔ Best Practices

Design: Start with the feed ranking equation ▸

Define your feed ranking formula early: score = affinity * recency_decay * engagement_weight. This determines your data model — you need to store interaction history (likes, comments, DMs, profile visits) to compute affinity, timestamp for recency, and engagement counters. The ranking equation drives the architecture.

Design: Separate media metadata from media bytes ▸

Store media metadata (dimensions, format, upload time, user_id, caption) in a relational/NoSQL DB, and actual bytes in object storage (S3). This lets you query/index metadata at low cost and serve media through CDN independently. Never put BLOBs in your primary database.

Implementation: Use multiple image resolutions ▸

Generate thumbnails at upload time (150px, 320px, 640px, 1080px). Serve the smallest adequate resolution based on viewport. This reduces bandwidth by 60-80% for thumbnail-heavy views (feed, grid profile). Store all variants in the same object store bucket with predictable key naming: {post_id}/{resolution}.jpg.

Implementation: Idempotent upload with client-generated IDs ▸

Let clients generate a UUID for each upload attempt. The server deduplicates on this ID. This prevents double-posts on network retries without server-side dedup logic. The upload API becomes safely retriable: PUT /media/{client_upload_id}.

Operations: Cache feed at multiple levels ▸

L1: in-process cache (per-server, hot users). L2: distributed cache (Redis/Memcached, pre-computed feeds). L3: CDN edge (for public profiles/explore). Invalidate L2 on new posts from followed users. The feed cache should store post IDs only (not full posts) to keep it small and reduce cache-bust surface area.

Scaling: Shard the social graph separately ▸

The followers/following graph has different access patterns than posts or feeds. Shard it independently (by user_id) in a graph-optimized store (like TAO/FlockDB). Queries: "who does X follow?" (outbox) and "who follows X?" (inbox) should both be O(1) per page. Bi-directional adjacency lists.

⇧ Scaling & Trade-offs

Capacity Estimation

2B MAU, 500M DAU. 100M photos/day = ~1,160 uploads/sec. Avg photo 2MB = 200TB new storage/day. Feed reads: 500M * 10 opens/day = ~58K QPS.

~58K feed reads/sec ~200TB/day new media

Feed Scaling (10x to 100x)

At 10x: horizontal scale feed service, add cache shards. At 100x: move to regionalized feed caches, pre-compute feeds in nearby data centers, introduce edge computing for feed assembly.

Regional feed caches

Media Storage (Petabyte Scale)

Multi-tier storage: hot (SSD, recent 7 days), warm (HDD, 7-90 days), cold (S3 Glacier, archival). Deduplication for reposts. Content-addressable storage for identical images.

~73PB/year growth

Database Sharding Strategy

Posts: shard by post_id (even distribution). Feeds: shard by user_id (locality for feed reads). Social graph: shard by user_id (adjacency reads). Separate DBs for each domain.

Domain-based sharding

Trade-off: Consistency vs. Latency

Feed: eventual consistency (seconds delay OK). Likes/comments count: eventual (stale counts acceptable). DMs: strong consistency (ordering matters). Follow/unfollow: eventual (seconds to propagate).

Per-feature consistency

Failure Scenarios

Feed cache down: serve stale feed from L2 + degrade to chronological. Media CDN failure: fallback to origin. DB primary fails: promote replica (seconds). Notification service down: queue + retry.

Graceful degradation
