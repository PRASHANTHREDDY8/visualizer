Docker Containerization

OS-level virtualization for packaging, distributing, and running applications in isolated, reproducible environments

Architecture Diagram

Docker uses a client-server architecture with a daemon managing container lifecycle, images, and networks

Component Breakdown

Deep dive into each component's responsibility, technology, and scaling characteristics

Docker CLI

User-facing command-line tool that translates commands into Docker Engine API calls

Go REST API Client Unix Socket / TCP

Key decisions: Communicates via /var/run/docker.sock (local) or TCP with TLS (remote). Supports context switching for multi-host management.

Scaling: Stateless — multiple CLI instances can connect to the same daemon concurrently.

Docker Daemon (dockerd)

Central management process that orchestrates all Docker objects and exposes the API

Go REST API Server Plugin Architecture

Key decisions: Manages image layers, container lifecycle, network creation, and volume mounts. Delegates actual container execution to containerd.

Scaling: Single daemon per host. Horizontal scaling via Docker Swarm or Kubernetes orchestration across multiple hosts.

containerd

High-level container runtime managing full container lifecycle independently from Docker

Go gRPC API CNCF Graduated

Key decisions: Handles image pull/push, container execution, snapshot management, and task supervision. Used directly by Kubernetes (CRI) without Docker.

Scaling: One per host. Designed for high-density workloads (thousands of containers per host).

runc

Low-level OCI-compliant runtime that spawns container processes using Linux kernel primitives

Go OCI Runtime Spec namespaces + cgroups

Key decisions: Creates Linux namespaces (PID, NET, MNT, UTS, IPC, USER), configures cgroups for resource limits, applies seccomp profiles and AppArmor/SELinux policies.

Scaling: Ephemeral process — spawns to create containers, then exits. Minimal overhead per container creation.

Container Registry

Remote storage and distribution service for container images using content-addressable storage

OCI Distribution Spec HTTPS + Token Auth Content-Addressable

Key decisions: Images stored as manifests + layer blobs (SHA256 addressed). Supports multi-arch manifests, signing (Notary/cosign), and vulnerability scanning.

Scaling: CDN-backed blob storage. Layer deduplication across images reduces storage. Geo-replicated registries for global distribution.

Union Filesystem (Images)

Layered, copy-on-write filesystem enabling efficient image storage and container creation

OverlayFS Copy-on-Write Layer Caching

Key decisions: Each Dockerfile instruction creates a read-only layer. Containers add a thin writable layer on top. Shared base layers mean 100 containers from the same image use ~same disk as 1.

Scaling: Layer deduplication saves storage. Build cache speeds rebuilds. Multi-stage builds reduce final image size.

Comparisons with Alternatives

How Docker compares to other containerization and virtualization approaches

Approach Key Idea Pros Cons Best For
DockerPOPULAR OS-level containers via Linux namespaces + cgroups with layered images Fast startup (~ms), efficient resource use, huge ecosystem, Dockerfile reproducibility Shared kernel (less isolation), Linux-centric, daemon dependency Microservices, CI/CD, dev environments, cloud-native apps
Podman Daemonless, rootless container engine with Docker-compatible CLI No root daemon, systemd integration, pod-native, Docker CLI compatible Smaller ecosystem, less tooling, networking complexity in rootless mode Security-sensitive envs, RHEL/Fedora shops, rootless requirements
Virtual Machines Hardware-level virtualization with full OS per instance (KVM, VMware, Hyper-V) Strong isolation, different OS kernels, mature security model Heavy resource overhead, slow boot (minutes), large disk footprint Multi-tenant isolation, legacy apps, different kernel requirements
LXC/LXD System containers — full Linux OS in a container (like a lightweight VM) Persistent system containers, closer to VM experience, low overhead Less portable, no layered images, smaller community Long-lived workloads that need full OS, lightweight VM replacement

When to pick each

Choose Docker when...

You need fast, reproducible application packaging with a massive ecosystem. Best for microservices, CI/CD pipelines, and cloud deployments where developer experience matters.

Choose Podman when...

Security policy mandates no root daemons, or you're in a Red Hat environment. Drop-in Docker replacement with better security posture for production.

Choose VMs when...

You need kernel-level isolation between tenants, run Windows/Linux side-by-side, or compliance requires hardware-level separation.

Choose LXC/LXD when...

You want a lightweight VM replacement for long-running system workloads that need init systems, persistent state, and full OS tooling.

Use Cases & Common Pitfalls

Where Docker excels, where it doesn't, and mistakes to avoid

Primary Use Cases

PRIMARY

Microservices Deployment

Each service in its own container with defined interfaces. Enables independent deployment, scaling, and technology choices per service. Scale: 10s to 1000s of services.

PRIMARY

CI/CD Pipelines

Reproducible build environments, test isolation, and artifact packaging. Every build runs in a fresh container — no "works on my machine" drift. GitHub Actions, GitLab CI, Jenkins all Docker-native.

PRIMARY

Local Development

docker-compose.yml defines entire stacks (DB + cache + app + queue). New developer onboarding: clone + docker compose up. Matches production topology locally.

PRIMARY

Cloud-Native Applications

Kubernetes, ECS, Cloud Run, App Runner — all container-first. Docker images are the universal deployment artifact for modern cloud platforms.

Anti-Use Cases

AVOID

Stateful Databases in Production

Running primary databases in containers adds complexity (volume management, backup, failover) without clear benefit. Use managed services (RDS, Cloud SQL) instead.

AVOID

GUI Desktop Applications

Docker containers lack display servers. While X11 forwarding works, it's fragile and slow. Use native packaging (Snap, Flatpak) or VMs for desktop apps.

AVOID

High-Performance Computing (HPC)

Network namespace overhead and storage layer indirection hurt latency-sensitive workloads. HPC prefers bare-metal or Singularity containers designed for the space.

Best Practices

Proven patterns for building, running, and operating Docker containers in production

● Image Building

  • Use multi-stage builds to separate build deps from runtime
  • Pin base image versions with SHA digests, not just tags
  • Order Dockerfile layers from least to most frequently changing
  • Use .dockerignore to exclude build context bloat
  • Run as non-root user (USER directive)
  • Use distroless or Alpine for minimal attack surface
  • Scan images with Trivy/Snyk before pushing to registry

● Runtime & Security

  • Never run containers as root in production
  • Set memory and CPU limits (--memory, --cpus)
  • Use read-only root filesystem (--read-only) where possible
  • Drop all capabilities, add back only what's needed
  • Use secrets management (Docker secrets, Vault) not env vars for sensitive data
  • Enable Docker Content Trust for image signing
  • Apply seccomp profiles and AppArmor/SELinux policies

● Networking

  • Use user-defined bridge networks (not default bridge)
  • DNS-based service discovery between containers
  • Don't expose ports unless required (use internal networks)
  • Use overlay networks for multi-host communication
  • Implement health checks for load balancer integration
  • Consider service mesh (Istio, Linkerd) for complex topologies

● Operations & Monitoring

  • Log to stdout/stderr — let the platform handle collection
  • Implement graceful shutdown (trap SIGTERM)
  • Use health checks (HEALTHCHECK instruction or orchestrator probes)
  • Monitor: container CPU/mem, restart count, image age
  • Tag images with git SHA + semver for traceability
  • Automate image garbage collection on hosts and registries
  • Use docker system prune in CI to prevent disk exhaustion

● Docker Compose

  • Use profiles to separate dev/test/prod service sets
  • Declare depends_on with health check conditions
  • Use named volumes for data persistence
  • Pin compose file version to docker compose v2 spec
  • Use .env file for environment-specific configuration
  • Separate override files (docker-compose.override.yml) for local dev

● CI/CD Integration

  • Use BuildKit for parallel multi-stage builds
  • Cache layers in registry (--cache-from / --cache-to)
  • Build once, promote the same image through environments
  • Never use :latest in production — always pin versions
  • Scan images in pipeline before allowing deployment
  • Use multi-platform builds (docker buildx) for ARM + x86

Scaling & Trade-offs

How Docker handles growth and the fundamental trade-offs in containerization

Container Density

Containers per host100–1000+
Startup time~100ms
Memory overhead per container~10–50 MB
Image pull (cached layers)seconds
Image pull (cold, 500MB)30–120s

Scaling Strategies

  • Single host: Docker Compose with resource limits. Good for small apps, dev environments
  • 10x (multi-host): Docker Swarm or Kubernetes. Service discovery, load balancing, rolling deploys
  • 100x (cluster): Kubernetes with node auto-scaling. Pod HPA, cluster autoscaler, resource quotas
  • 1000x (global): Multi-cluster federation, geo-distributed registries, edge deployment with K3s

Trade-off: Isolation vs. Efficiency

Containers: Shared kernel, fast, efficient — but a kernel exploit escapes to host

VMs: Separate kernel, strong isolation — but 10x memory overhead and slow boot

Hybrid: Kata Containers / Firecracker — VM-level isolation with near-container speed. Used by AWS Lambda, Fargate.

Trade-off: Image Size vs. Debuggability

Minimal (distroless/scratch): 5–20 MB, tiny attack surface — but no shell, no debugging tools

Alpine: 5 MB base, musl libc — but subtle glibc incompatibilities

Debian/Ubuntu: 80–120 MB base, full tooling — but larger attack surface, slower pulls

Trade-off: Stateless vs. Stateful

Stateless containers: Trivial to scale, replace, and update. Ideal for application tiers.

Stateful containers: Require volumes, careful scheduling, backup strategies. Complexity ≈ managing a DB.

Recommendation: Keep containers stateless. Push state to managed services (RDS, ElastiCache, S3).

Failure Scenarios

  • Daemon crash: All containers on host stop. Orchestrators reschedule. Use --live-restore to survive daemon restarts.
  • OOM kill: Kernel kills container process. Set proper memory limits + monitor. Restart policy handles recovery.
  • Registry down: Can't pull new images. Mitigate with local caches, pre-pulled images, or mirrored registries.
  • Disk full: Builds fail, containers can't write. Automate pruning, set storage driver limits, monitor disk usage.
