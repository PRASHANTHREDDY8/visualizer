◆ Section 4

Comparisons with Alternatives

RAG vs other approaches for grounding LLM outputs in domain knowledge.

Approach Key Idea Pros Cons Best For
RAG✓ Chosen Retrieve relevant docs at query time, inject into prompt Fresh knowledge, no retraining, interpretable sources Latency overhead, retrieval quality dependent, context window limits Dynamic knowledge bases, compliance-heavy domains
Fine-tuning Train model weights on domain-specific data Fast inference, deeply learned patterns, no retrieval needed Expensive to update, can hallucinate trained facts, stale quickly Stable domains, style/format adaptation
Long-context stuffing Put entire knowledge base in prompt context Simplest architecture, no vector DB needed Expensive per query, limited by context window, no relevance filtering Small knowledge bases (<100 pages)
Knowledge Graphs + LLM Structure knowledge as graph, traverse for context Precise relationships, reasoning chains, explainable High upfront effort, brittle to schema changes, complex maintenance Highly structured domains (medical, legal ontologies)

Choose RAG when...

Your knowledge changes frequently (daily/weekly), you need source attribution, or you have too much data to fine-tune on economically. RAG shines with 10K-10M documents.

Choose Fine-tuning when...

You need the model to adopt a specific tone/format, the knowledge is stable for months, or you need sub-100ms latency without retrieval overhead.

Choose Context Stuffing when...

Your entire knowledge base fits in ~50K tokens, the information rarely changes, and you want zero infrastructure beyond the LLM API.

Hybrid: RAG + Fine-tuning

Fine-tune for domain vocabulary and reasoning style, use RAG for factual grounding. This is the production pattern for most enterprise deployments at scale.

◆ Section 5

Use Cases & Common Pitfalls

Where RAG excels, where it doesn't, and mistakes to avoid.

Primary Use Cases

Enterprise Knowledge Assistants

Internal chatbots that answer employee questions from HR policies, product docs, engineering wikis — always current, always cited.

1K-100K docs · 100-10K QPS

Customer Support Automation

Answer customer queries using support articles, product manuals, and ticket history. Reduces ticket volume 40-60%.

10K-1M docs · 500-50K QPS

Legal & Compliance Research

Search across regulations, case law, and contracts. Provide answers with exact citations to source paragraphs.

100K-10M docs · 10-1K QPS

Code Documentation Q&A

Developer assistants grounded in your repo's docs, API specs, and architecture decisions. Reduces onboarding time.

1K-50K docs · 50-5K QPS

Anti-Use Cases

❌ Creative writing or open-ended generation ▼

RAG retrieves existing knowledge — it doesn't help generate novel fiction, poetry, or marketing copy that requires originality. The retrieved context would constrain creativity rather than enhance it.

❌ Real-time data with sub-second freshness requirements ▼

RAG has inherent indexing lag (minutes to hours). For live stock prices, real-time dashboards, or streaming data, use direct API calls or function calling instead.

❌ Computation or mathematical reasoning ▼

RAG can retrieve formulas but can't execute calculations. For math-heavy tasks, pair with code execution tools or calculator APIs rather than relying on retrieved text.
