How Swiggy's architecture compares to alternative approaches

Delivery Assignment Strategy

ApproachKey IdeaProsConsUsed By
Dynamic Batching + ML CHOSEN ML model scores rider-order affinity, batches nearby orders, reassigns dynamically Optimal utilization, handles demand spikes, multi-order deliveries High engineering complexity, model drift risk Swiggy, DoorDash
Nearest Rider Assign order to closest available rider via geospatial query Simple, fast assignment, easy to implement Ignores traffic, rider capacity, restaurant prep time Early-stage startups
Zone-Based Dispatch City divided into zones; riders assigned within zone only Predictable, easy ops, no cross-zone deadheading Suboptimal at zone boundaries, rigid supply allocation Uber Eats (early)
Auction Model Broadcast order to nearby riders; first accept wins Self-optimizing, riders choose profitable orders Cherry-picking, longer wait for unpopular orders Grab, Gojek

Real-Time Tracking Architecture

ApproachKey IdeaProsConsUsed By
WebSocket + Server Push CHOSEN Persistent WebSocket connection; server pushes location updates every 4s Low latency, efficient for frequent updates, bidirectional Connection management at scale, reconnection handling Swiggy, Uber
Long Polling Client polls server every N seconds for new location Simple, works everywhere, stateless server Higher latency, more bandwidth, many idle connections Older food apps
Server-Sent Events (SSE) One-way server-to-client stream over HTTP Simpler than WebSocket, auto-reconnect, HTTP compatible Unidirectional only, limited browser connections per domain Some logistics platforms

5 Use Cases & Common Pitfalls

Primary Use Cases

On-Demand Food Delivery

Customer orders from nearby restaurants with 25-40 min delivery. Requires real-time tracking, dynamic ETA, surge pricing.

2M+ orders/day

Grocery & Essentials (Instamart)

15-30 min delivery from dark stores. Higher item count per order, inventory management, smaller delivery radius.

500K+ orders/day

Scheduled / Pre-orders

Orders placed for future time slots. Batching optimization, predictable demand, capacity planning.

200K+ orders/day

Dine-In & Takeaway

Table reservations, in-restaurant ordering, and pickup. No delivery logistics, focus on discovery and payment.

100K+ daily sessions

Anti-Use-Cases

Long-Distance Logistics

This architecture isn't suited for inter-city freight or package delivery (>50km). Use a hub-and-spoke model with route optimization instead.

B2B Bulk Ordering

Enterprise catering with 500+ meals needs different fulfillment: advance planning, bulk prep coordination, not real-time dispatch.

Scaling Strategies by Component

Order Service → 10x

Shard by city_id + date. Each city is independent for order state. Use Kafka for async downstream (payment, assignment, notifications).
Strategy: Horizontal sharding by geography

Location Service → 10x

In-memory geospatial index (Redis with geohash). Partition by city. Writes go to time-series DB (InfluxDB/TimescaleDB) asynchronously.
Strategy: Partition by geohash prefix

Search/Discovery → 10x

Elasticsearch cluster per region. Cache popular queries (top restaurants near area) in Redis with 5-min TTL. Pre-compute rankings hourly.
Strategy: Read replicas + aggressive caching

WebSocket Gateway → 10x

Sticky sessions via consistent hashing on user_id. Horizontally scale WS servers. Use pub/sub (Redis) to fan out location updates to correct server.
Strategy: Horizontal + pub/sub fan-out
