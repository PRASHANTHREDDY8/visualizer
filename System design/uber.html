Component Breakdown

Matching Service (DISCO)

Core dispatch optimization engine that matches riders with the best available driver.

Go / Java Ringpop

Key decisions: Uses supply positioning to pre-position drivers; batch matching every 2 seconds; considers ETA, driver rating, vehicle type, and surge zone.

Scaling: Sharded by geographic cell. Each cell handled by a dedicated worker. Consistent hashing for cell-to-worker assignment.

Location Service

Ingests and indexes millions of GPS location updates per second from active drivers.

Google S2 Redis Geo

Key decisions: Google S2 geometry library for hierarchical spatial indexing. Drivers report location every 4s. S2 cell level 12 (~3.3km2) for coarse queries, level 16 for fine-grained.

Scaling: Horizontally scaled with geo-sharding. Redis cluster per region with GEOADD/GEORADIUS for nearest-driver queries.

Trip Service

State machine orchestrating the entire trip lifecycle from request to completion.

State Machine Saga Pattern

States: REQUESTED → MATCHING → DRIVER_ASSIGNED → EN_ROUTE → ARRIVED → IN_TRIP → COMPLETED → BILLED

Scaling: Stateless service with trip state persisted in PostgreSQL. Events published to Kafka for downstream consumers.

ETA Service

ML-powered arrival time predictions using road graph, real-time traffic, and historical patterns.

ML Model Road Graph

Key decisions: Gradient-boosted trees trained on historical trips. Features include: time of day, weather, events, road segment speeds, traffic signals. Updates road speed estimates in real-time from driver GPS traces.

Scaling: Pre-computed ETA matrices for popular routes; on-demand computation for long-tail. Cached aggressively with 30s TTL.

Pricing / Surge Service

Dynamic pricing engine using real-time supply/demand signals to set fare multipliers.

Dynamic Geofenced

Key decisions: City divided into surge hexagons (H3 cells). Supply/demand ratio computed per cell every 30s. Surge multiplier = f(demand/supply, time, events). Upfront pricing locks fare at request time.

Scaling: Stateless computation; reads supply/demand from Redis counters. Cached surge maps per city.

Payment Service

Handles fare calculation, payment authorization, charge capture, and driver payouts.

PCI-DSS Idempotent

Key decisions: Pre-authorization at trip start; capture at completion. Idempotency keys prevent double charges. Supports 15+ payment methods per country. Fraud scoring on every transaction.

Scaling: Async settlement via Kafka. Weekly driver payouts batched by region. Separate write-ahead log for financial consistency.

When to Pick Each Architecture Style

Batch Matching

When you need to optimize fleet utilization across many concurrent requests in dense urban areas.

Greedy Nearest

When demand is sparse (rural/suburban) or when sub-second match latency is critical.

Auction/Bidding

For freight/logistics where jobs are heterogeneous and driver preferences matter more than speed.

Use Cases & Common Pitfalls

Primary Use Cases

Ride-HailingCore

On-demand rides: UberX, Pool, Black, XL. ~14M rides/day, sub-5s match time target in metros.

Food Delivery (Eats)Adjacent

Three-sided marketplace (customer, restaurant, driver). Adds prep-time prediction and batched delivery routing.

Freight / LogisticsExtended

Long-haul trucking matching. Different constraints: hours-of-service, cargo type, multi-stop routing.

Micro-mobilityAdjacent

Scooters/bikes with fixed pickup zones. Simpler matching but adds battery management and rebalancing.

Common Pitfalls

Ignoring GPS Drift and Noise

The mistake: Trusting raw GPS coordinates without filtering or snapping to road network.

Why it happens: GPS seems precise enough (5m accuracy), so teams skip map-matching.

The consequence: Drivers appear in buildings, wrong sides of highways, or off-road. ETA estimates become wildly inaccurate. Riders see drivers "teleporting."

The fix: Apply Kalman filtering on raw GPS, then snap to road network using Hidden Markov Model map-matching. Discard locations with speed > 200 km/h or accuracy > 50m.

Single-Region Matching Without Cell Boundaries

The mistake: Searching for drivers only within a single geospatial cell without checking adjacent cells.

Why it happens: Simplicity — one cell lookup is faster than multi-cell queries.

The consequence: A driver 100m away but in an adjacent cell is invisible. Riders near cell boundaries get much worse match quality.

The fix: Always query the target cell AND its 8 neighbors (or use S2 region covering). The slight overhead is negligible vs. match quality improvement.

Surge Pricing Without Smoothing

The mistake: Applying surge multipliers instantaneously based on momentary supply/demand spikes.

Why it happens: Direct ratio calculation seems correct and responsive.

The consequence: Surge oscillates wildly (spikes to 5x then crashes). Riders see different prices seconds apart. Drivers "chase surge" creating feedback loops.

The fix: Exponential moving average on surge multiplier. Ramp up quickly (30s) but decay slowly (5min). Cap maximum surge. Show riders the surge direction trend.

Not Handling Driver App Disconnections Gracefully

The mistake: Immediately removing a driver from the available pool when WebSocket disconnects.

Why it happens: "Disconnected = offline" seems logical.

The consequence: Tunnel passages, brief connectivity blips, or app backgrounding removes drivers mid-trip. Riders get "driver cancelled" for no reason.

The fix: Grace period of 30-60s before marking offline. If mid-trip, never remove. Use last-known location + heading for ETA. Require explicit "go offline" action for true offline.

Monolithic Trip State Without Event Sourcing

The mistake: Storing only current trip state in a single row, updating in place.

Why it happens: Simpler schema, fewer writes.

The consequence: Cannot audit state transitions. Race conditions on concurrent updates (rider cancels while driver accepts). Debugging disputes becomes impossible.

The fix: Event source the trip: append state transitions as immutable events. Derive current state from event log. Use optimistic concurrency (version field) on the materialized view.

Best Practices

Design Phase

Start with the Matching Problem, Not the CRUD

The core challenge in ride-hailing is real-time spatial matching under constraints. Design the matching algorithm and data flow first, then build supporting services around it. Too many teams start with user/trip CRUD and bolt on matching later.

Design for the Unhappy Path First

What happens when: driver doesn't accept (timeout + cascade to next)? Rider cancels mid-match? Payment fails post-trip? Network drops mid-ride? Design explicit state machine transitions for every failure mode before building the happy path.

Implementation

Use S2/H3 Cell Levels Strategically

Level 12 (3.3km2) for initial nearby-driver queries. Level 14 for fine-grained matching. Level 8 for city-wide analytics and surge computation. Don't use a single level — different operations need different precision.

Separate Read and Write Paths for Location

Write path: driver location updates → Kafka → Redis (hot store) + Cassandra (cold store). Read path: matching queries Redis only. Never let high-write location ingestion compete with latency-sensitive matching reads.

Implement Circuit Breakers Between Services

If ETA service is down, matching should still work with cached/estimated ETAs. If payment is slow, trip should still complete (charge async). Define graceful degradation for every dependency. Hystrix/resilience4j patterns are essential.

Operational

Monitor Supply-Demand Balance Per Cell, Not Globally

Global metrics hide localized problems. Airport might have excess drivers while downtown is starved. Alert on per-cell imbalance. Trigger incentives (heat maps, quest bonuses) automatically when cells are undersupplied for > 5 minutes.

Canary Deploys by City, Not by Instance Percentage

A matching algorithm change that works in NYC might break in Mumbai (different road patterns, traffic). Canary to a single smaller city first, observe for 24h (covering all demand patterns), then roll out to larger cities progressively.

Back-of-Envelope Calculations

Location data storage:

5M drivers x 1 update/4s = 1.25M writes/sec
Each update: ~100 bytes (lat, lng, timestamp, driver_id, heading, speed)
Daily location data: 1.25M x 86,400s x 100B = ~10.8 TB/day (cold storage)

Matching throughput:

Peak: 3x average = ~480 ride requests/sec
Each match: query ~50 nearby drivers, compute ETA for top 10 = ~500 ETA calls/sec per ride
Peak ETA service load: 480 x 500 = 240K ETA computations/sec

WebSocket connections:

5M active drivers + ~2M active riders = 7M concurrent connections
At 50K connections/server = ~140 WebSocket gateway servers

Trade-off Analysis

Match Quality vs. Latency

Larger batch windows → better global optimum but slower match. Uber chose 2s as the sweet spot: measurably better utilization with acceptable wait.

Consistency vs. Availability

Location data is AP (eventual consistency acceptable). Trip state is CP (can't double-assign a driver). Payment is CP with saga compensation.

Accuracy vs. Computation Cost

More ETA candidates → better match but exponential compute. Uber uses tiered approach: coarse filter (S2 radius) → fine rank (top-10 ETA).

Driver Fairness vs. Rider Experience

Pure nearest-driver is unfair (hotspot drivers get all rides). Pure queue is slow for riders. Uber blends: proximity-weighted with fairness adjustments for idle time.
