AWS Lambda

Serverless compute service that runs code in response to events. Zero server management, pay-per-invocation, scales from zero to thousands of concurrent executions automatically.

How Lambda Works

Fundamentals
⚡

Event-Driven Execution

Lambda functions are triggered by events — HTTP requests via API Gateway, S3 uploads, DynamoDB streams, SQS messages, CloudWatch schedules, and 200+ other AWS event sources.

📦

Execution Model

Each invocation runs in an isolated micro-VM (Firecracker). The runtime initializes your code, executes the handler, then either stays warm for reuse or is terminated after idle timeout (~5-15 min).

📈

Auto-Scaling

Scales from 0 to your account concurrency limit (default 1,000, extendable to tens of thousands). Each concurrent request gets its own execution environment — no thread-safety concerns.

💰

Pay Per Use

Billed per invocation ($0.20/million) + duration (GB-seconds). Free tier: 1M requests + 400,000 GB-seconds/month. Zero cost when idle — no baseline infrastructure spend.

🚀

Runtimes

Native support for Node.js, Python, Java, .NET, Go, Ruby. Custom runtimes via container images (up to 10GB) or Lambda Layers for any language (Rust, C++, etc.).

🔒

Security Model

Each function gets an IAM execution role. Runs in AWS-managed VPC by default (or your VPC). Execution environments are fully isolated via Firecracker microVMs — hardware-level separation.

Cold Start Mitigation Strategies

Provisioned Concurrency

Pre-warm N instances. Eliminates cold starts but costs ~$15/month per instance. Use for latency-critical paths.

Eliminates cold start $$$

SnapStart (Java)

Takes a snapshot after init phase. Restores from snapshot instead of re-initializing. Reduces Java cold start from ~6s to ~200ms.

Java only Free

Keep Warm (Ping)

Schedule a CloudWatch event every 5 min to invoke the function. Hacky but cheap. Doesn't scale for >1 concurrent cold start.

Workaround

Minimize Package Size

Smaller deployment = faster init. Use tree-shaking, remove dev deps, use Lambda Layers. Target <5MB zipped.

Always do this

Tradeoffs

Analysis

✓ Strengths

Zero operational overhead

No patching, no capacity planning, no OS maintenance. AWS handles all infrastructure concerns including HA and AZ distribution.

True pay-per-use

Zero cost at zero traffic. Perfect for variable/spiky workloads. A function that runs once/day costs fractions of a cent vs $30+/month for smallest EC2.

Instant scaling

Scales from 0 to 1000+ concurrent executions in seconds. No pre-provisioning, no auto-scaling group lag, no warm-up period.

Reduced blast radius

Each function is isolated. A memory leak or crash affects only that invocation. No cascading failures across a shared server.

Built-in integrations

Native triggers from 200+ AWS services. Event filtering, batching, retry policies all built-in without custom integration code.

Rapid development velocity

Focus on business logic only. Deploy single functions independently. Faster iteration cycles for small, focused services.

✗ Weaknesses

Cold start latency

First invocation adds 100ms-6s depending on runtime and package size. Unacceptable for real-time APIs unless using provisioned concurrency ($$$).

15-minute execution limit

Hard timeout. Long-running tasks need Step Functions orchestration or must be chunked. Video transcoding, ML training = not a fit.

Vendor lock-in

Deep coupling to AWS event model, IAM, and service integrations. Porting to another cloud requires significant rearchitecture.

Debugging difficulty

No SSH access. Distributed tracing across functions is complex. Local development doesn't perfectly replicate cloud behavior.

Cost at high throughput

Above ~1M requests/day with long durations, containers or EC2 become cheaper. Lambda's per-invocation pricing has a crossover point.

Statelessness constraints

No local state between invocations. Must externalize all state to DynamoDB/Redis/S3. Adds latency and complexity for stateful workflows.

Connection management

Each concurrent Lambda = new DB connection. At scale, easily overwhelms RDS connection limits. Requires RDS Proxy ($$$) or connection pooling tricks.

Best Practices

Guidelines
1

Minimize deployment package

Use tree-shaking, exclude dev dependencies, leverage Layers for shared code. Smaller packages = faster cold starts.

2

Initialize outside the handler

Put DB connections, SDK clients, and config loading in module scope. They persist across warm invocations — free caching.

3

Use ARM (Graviton2)

20% cheaper, often 10-20% faster. Nearly all workloads run unchanged on ARM. Switch architecture for instant savings.

4

Right-size memory

More memory = more CPU. A 128MB function may run 3x slower than 512MB. Use AWS Lambda Power Tuning to find the sweet spot.

5

Use reserved concurrency wisely

Set reserved concurrency to protect downstream services from Lambda's aggressive scaling. Prevents DB connection floods.

6

Design for idempotency

Lambda retries on failure. SQS can deliver twice. Always use idempotency keys or make operations naturally idempotent.

7

Use structured logging

JSON logs with request IDs, correlation IDs. Use Powertools for Lambda (Python/TypeScript/Java) for structured observability.

8

Set appropriate timeouts

Don't use 15 min as default. Set timeout to 2-3x expected duration. Prevents runaway functions from burning budget.

9

Use Dead Letter Queues

Configure DLQ for async invocations. Failed events should land somewhere observable, not silently disappear.

10

Use environment variables + SSM

Config in env vars (4KB limit), secrets in SSM Parameter Store or Secrets Manager. Cache secrets in memory between invocations.

11

Implement circuit breakers

When downstream is failing, fail fast rather than burning Lambda duration waiting on timeouts. Use exponential backoff.

12

Use batch processing for streams

Process SQS/Kinesis in batches (up to 10,000 records). Configure partial batch failure reporting to avoid reprocessing succeeded items.
