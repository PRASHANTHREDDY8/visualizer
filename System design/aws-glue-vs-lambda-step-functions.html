Use Cases

Daily Data Warehouse Load (Glue)

Nightly ingestion from 50+ S3 data sources into Redshift. Glue crawlers detect schema changes, DynamicFrames handle nested JSON, bookmarks track incremental progress.

Real-time File Processing (Lambda + SF)

S3 upload triggers validation, thumbnail generation, metadata extraction, and indexing. Step Functions orchestrate the parallel fan-out and aggregate results.

CDC Pipeline (Lambda + SF)

DynamoDB streams trigger Lambda to capture changes, transform, and replicate to Elasticsearch. Step Functions handle dead-letter retry and alerting on persistent failures.

Data Lake Compaction (Glue)

Consolidate thousands of small Parquet files into optimally-sized partitions. Glue's Spark engine handles the shuffle efficiently with auto-scaling DPUs.

Multi-step Order Processing (Lambda + SF)

Validate payment, check inventory, reserve stock, send confirmation. Step Functions provide exactly-once semantics with compensation logic for rollbacks.

Anti-Pattern: Glue for Small Events

Don't use Glue for processing individual API events or small files. The 1-10 min cold start and DPU minimum make it 100x more expensive than Lambda for sub-MB payloads.

Anti-Pattern: Lambda for TB-Scale Joins

Lambda's 10GB memory and 15-min timeout can't handle distributed joins across terabytes. You'd need thousands of functions with manual shuffle logic—use Spark instead.

Anti-Pattern: Step Functions for Simple Cron

If your workflow is "run one thing on a schedule" with no branching or retries, EventBridge + Lambda is simpler and cheaper than Step Functions overhead.

Common Pitfalls

Using Glue for real-time requirements
The mistakeDeploying Glue ETL jobs expecting sub-minute latency for event-driven processing.
Why it happensGlue handles the full ETL lifecycle, so teams assume it can also do near-real-time. The marketing says "serverless" which implies instant.
The consequence1-10 minute cold starts per job run, with minimum billing of 1 DPU (10 min). A job processing 1KB costs the same as one processing 1GB.
The fixUse Lambda for event-driven lightweight transforms. Reserve Glue for scheduled batch jobs or micro-batching at 5+ minute intervals.
Lambda payload size limits breaking pipelines
The mistakePassing large datasets between Lambda functions via Step Functions state (256KB limit) or synchronous invocation payload (6MB).
Why it happensWorks fine in dev with small test data, then fails in production when real data exceeds limits.
The consequenceStateTooLarge errors crash the workflow, data is lost, and there's no built-in recovery for partial progress.
The fixPass S3 pointers (bucket + key) between steps, not data. Each Lambda reads from and writes to S3. Use Step Functions only for orchestration metadata.
Not using Glue job bookmarks for incremental loads
The mistakeReprocessing the entire dataset on every Glue job run instead of using bookmarks to track what's already been processed.
Why it happensBookmarks require specific source formats and aren't enabled by default. Teams skip them to "keep things simple."
The consequenceLinear cost growth as data accumulates. A job processing 1TB daily becomes 30TB monthly because it rescans everything.
The fixEnable job bookmarks, partition source data by date, and use pushdown predicates to read only new partitions.
Step Functions Standard vs Express mode confusion
The mistakeUsing Standard workflows (priced per state transition) for high-volume, short-duration tasks that should use Express workflows.
Why it happensStandard is the default. Express requires async invocation patterns that are less intuitive.
The consequence10,000 events/hour at 5 states each = 50,000 transitions = $1.25/hour on Standard. Express would cost ~$0.05/hour for the same workload.
The fixUse Express for high-volume, short-lived workflows (<5 min). Reserve Standard for long-running workflows needing exactly-once execution history.
Over-provisioning Glue DPUs "just in case"
The mistakeSetting max DPUs to 100 when the job only needs 10, or not enabling auto-scaling.
Why it happensFear of OOM errors or job failures during peak loads. "More DPUs = safer" mentality.
The consequencePaying $44/hour for idle Spark executors. A 10-DPU job costing $4.40/hr ballooning to $44/hr with no performance gain.
The fixEnable Glue auto-scaling (Glue 3.0+). Start with 2-5 DPUs, monitor with CloudWatch, and only increase after profiling bottlenecks.

Best Practices

Design Phase

  • Map data volume and velocity first — this determines Glue vs Lambda before anything else
  • Define latency SLA upfront: seconds = Lambda, minutes = either, hours = Glue
  • Estimate cost at 10x scale early — Glue DPU costs compound faster than Lambda per-invocation
  • Design for idempotency in both approaches — duplicate processing should produce same results

Implementation

  • Glue: Use DynamicFrames over DataFrames for schema flexibility; apply resolveChoice() for type conflicts
  • Lambda: Keep functions focused (single responsibility); share code via Lambda Layers
  • Step Functions: Pass references (S3 URIs) not data; use ResultPath to preserve original input
  • Both: Implement dead-letter queues for failed records; never silently drop data

Operations

  • Glue: Enable continuous logging, set CloudWatch alarms on job duration and DPU utilization
  • Lambda: Set concurrency limits to prevent downstream overwhelm; use reserved concurrency for critical functions
  • Step Functions: Use execution input/output for debugging; enable X-Ray tracing for latency analysis
  • Both: Tag all resources with pipeline name for cost allocation and quick identification

Scaling

  • Glue: Partition output data by date/region; enables Athena queries without full scans
  • Lambda: Use SQS with batch window to smooth spiky loads; set maxBatchingWindow for micro-batching
  • Hybrid: Use Lambda for ingestion/validation, Glue for heavy transforms — combine strengths
  • Monitor costs weekly; set AWS Budgets alerts at 80% threshold for each service
