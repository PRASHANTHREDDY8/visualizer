ACID Properties Breakdown

Each property and how InnoDB implements it

A

Atomicity

All or nothing. A transaction either completes entirely or has no effect at all. If any part fails, the entire transaction is rolled back.

Implementation: InnoDB uses the undo log to store the inverse of every operation. On rollback or crash recovery, it replays these undo records to restore the previous state.

Undo Log Rollback Segments Transaction IDs
C

Consistency

Valid state to valid state. Every transaction moves the database from one consistent state to another. Constraints, triggers, and cascades are enforced.

Implementation: MySQL enforces constraints (PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK, NOT NULL) at statement or transaction end. Doublewrite buffer prevents torn pages.

Constraints Doublewrite Buffer Crash Recovery
I

Isolation

Concurrent transactions don't interfere. Each transaction behaves as if it's the only one running. The isolation level controls the degree of isolation.

Implementation: InnoDB uses MVCC (multi-version concurrency control) with read views plus row-level locking (shared/exclusive locks, gap locks, next-key locks).

MVCC Read Views Row Locks Gap Locks
D

Durability

Committed = permanent. Once a transaction commits, its changes survive any subsequent crash, power failure, or hardware failure.

Implementation: Write-Ahead Logging (WAL) — changes written to redo log and flushed to disk before commit returns. The doublewrite buffer prevents torn pages during flush.

Redo Log (WAL) fsync innodb_flush_log_at_trx_commit

Use Cases & When ACID Matters

Where full ACID compliance is critical vs. where you can relax guarantees

Primary Use Cases

ACID CRITICAL

Banking & Financial

Money transfers require atomicity (debit + credit as one unit) and durability (no lost transactions). A single consistency violation means regulatory issues.

ACID CRITICAL

E-commerce Orders

Order placement: decrement inventory, create order record, charge payment. Partial execution means overselling or lost revenue.

ACID CRITICAL

Healthcare Records

Patient data modifications must be atomic and durable. Isolation prevents concurrent updates from corrupting medical records.

ACID CRITICAL

Booking & Reservations

Hotel/flight bookings need isolation to prevent double-booking and atomicity to ensure seat assignment + payment are linked.

Where You Can Relax ACID

ACID OVERKILL

Analytics / OLAP

Read-heavy analytical queries on historical data. Slightly stale reads are acceptable. Consider column stores or READ UNCOMMITTED.

ACID OVERKILL

Session Storage

User session data is ephemeral. Losing a session on crash is acceptable. MEMORY engine or Redis may be better fits.

ACID OVERKILL

Logging & Metrics

Append-only event streams where individual record loss is tolerable. Batch inserts without per-row transactions improve throughput 10x+.

ACID OVERKILL

Caching Layer

Cached data can be regenerated. No need for durability guarantees. Redis/Memcached are purpose-built for this.

Common Pitfalls

Mistakes that undermine ACID guarantees in MySQL

⚠ Setting innodb_flush_log_at_trx_commit = 0 or 2 without understanding the trade-off ▼
The mistake

Changing this setting to 0 or 2 for performance without realizing it breaks durability. With value 0, up to 1 second of committed transactions can be lost on crash. With 2, they survive mysqld crash but not OS crash.

Why it happens

The fsync on every commit is expensive. Benchmarks show 2-3x throughput improvement with value 2. Teams set it in production without understanding the guarantee they're trading away.

The consequence

A server crash can lose committed transactions that clients believe are permanent. For financial data, this means inconsistency between the application's view and the database's actual state.

The fix

Keep value 1 (default) for any data that must not be lost. Use value 2 only for non-critical data where you have replication as a safety net. Never use 0 in production.

⚠ Long-running transactions holding locks and bloating undo logs ▼
The mistake

Leaving transactions open for minutes or hours (e.g., interactive user sessions holding BEGIN without COMMIT). Or running large batch updates in a single transaction.

Why it happens

ORMs auto-start transactions on first query. Developers forget to commit. Batch jobs "for safety" wrap millions of rows in one transaction.

The consequence

Undo log grows unboundedly (purge thread can't clean old versions). Lock waits cascade. InnoDB history list length grows, degrading all queries. Rollback of a huge transaction can take hours.

The fix

Keep transactions short. Chunk batch operations into 1000-row commits. Set innodb_lock_wait_timeout appropriately. Monitor trx_rows_modified in INFORMATION_SCHEMA.INNODB_TRX.

⚠ Mixing transactional (InnoDB) and non-transactional (MyISAM) tables ▼
The mistake

Having some tables use MyISAM (legacy) while others use InnoDB, then writing transactions that span both.

Why it happens

Migration from MySQL 5.0 era. Some tables never got converted. Full-text search used to require MyISAM (no longer true since 5.6).

The consequence

ROLLBACK only undoes InnoDB changes. MyISAM writes persist regardless. You get partial rollbacks — the exact violation of atomicity.

The fix

Convert all tables to InnoDB: ALTER TABLE t ENGINE=InnoDB. There's virtually no reason to use MyISAM in modern MySQL (8.0+).

⚠ Assuming REPEATABLE READ prevents all concurrency anomalies ▼
The mistake

Believing InnoDB's REPEATABLE READ is equivalent to SERIALIZABLE. Writing application logic that assumes no concurrent modifications can affect outcomes.

Why it happens

InnoDB's RR does prevent phantoms for consistent reads (via MVCC), which goes beyond the SQL standard. But locking reads and write skew anomalies still exist.

The consequence

Write skew: two transactions read the same rows, make decisions based on that read, then write non-conflicting rows. Both commit, but the combined result violates an invariant.

The fix

Use SELECT ... FOR UPDATE when you need to read-then-write atomically. Or use SERIALIZABLE for critical sections. Understand that MVCC snapshot reads don't conflict with concurrent writes.

⚠ Disabling the doublewrite buffer for performance ▼
The mistake

Setting innodb_doublewrite=OFF because benchmarks show 5-10% write throughput improvement.

Why it happens

The doublewrite buffer adds an extra write for every page flush. On fast SSDs, it feels unnecessary.

The consequence

A power failure during a 16KB page flush can result in a torn (partially written) page. The redo log cannot recover a torn page because it stores logical changes, not full page images. Corruption.

The fix

Keep doublewrite enabled. The only safe exception: filesystems with atomic 16KB writes (ZFS) or hardware with battery-backed write cache that guarantees atomic page writes.

⚠ Autocommit confusion and implicit commits ▼
The mistake

Not understanding that DDL statements (ALTER TABLE, CREATE INDEX, TRUNCATE) cause an implicit commit. Running DDL mid-transaction thinking it can be rolled back.

Why it happens

MySQL's autocommit=1 default means each statement is its own transaction unless you explicitly BEGIN. DDL always commits, even inside an explicit transaction.

The consequence

A migration script that does BEGIN; INSERT data; ALTER TABLE; ROLLBACK; — the ALTER committed everything before it. The ROLLBACK has nothing to undo.

The fix

Never mix DDL and DML in the same transaction. Use separate transactions for schema changes. Test migration scripts with ROLLBACK to verify they're actually reversible.

Best Practices

Proven patterns for maintaining ACID guarantees at scale

✓ Transaction Design ▼
✓ Keep transactions as short as possible — acquire locks late, release early
✓ Access rows in a consistent order across transactions to prevent deadlocks
✓ Use SELECT ... FOR UPDATE only on rows you intend to modify
✓ Chunk large batch operations into transactions of 1,000-10,000 rows
✓ Set appropriate lock_wait_timeout (default 50s is often too long for web apps)
✓ Handle deadlock errors (1213) with automatic retry logic in application code
✓ Durability Configuration ▼
✓ innodb_flush_log_at_trx_commit = 1 for critical data (fsync every commit)
✓ sync_binlog = 1 if using replication (prevents binlog/redo log divergence)
✓ Keep doublewrite buffer enabled (innodb_doublewrite = ON)
✓ Size redo logs appropriately: innodb_redo_log_capacity = 1-4GB for write-heavy workloads
✓ Use battery-backed RAID controllers with write-back cache for production
✓ Monitor checkpoint age — if it approaches log capacity, writes stall
✓ Isolation & Concurrency ▼
✓ Understand what your chosen isolation level does and doesn't prevent
✓ Use REPEATABLE READ (default) for most workloads — it's well-balanced
✓ For read-heavy analytics on replicas, READ COMMITTED reduces lock contention
✓ Monitor INNODB_TRX for long-running transactions blocking purge
✓ Use NOWAIT or SKIP LOCKED (MySQL 8.0+) for queue-like access patterns
✓ Watch innodb_history_list_length — high values mean old undo versions aren't being purged
✓ Monitoring & Alerting ▼
✓ Alert on: innodb_history_list_length > 10,000 (undo log backlog)
✓ Alert on: checkpoint_age > 80% of redo log capacity (write stall imminent)
✓ Alert on: lock_wait_timeout exceeded events (Threads_waiting metric)
✓ Alert on: deadlock frequency via SHOW ENGINE INNODB STATUS
✓ Track: buffer pool hit ratio (should be >99% for OLTP)
✓ Track: InnoDB row operations/sec broken down by read/insert/update/delete

Scaling & Trade-offs

How ACID properties interact with scaling strategies

⚡ Performance vs. Durability

  • innodb_flush_log_at_trx_commit=1: Full durability, ~10K TPS (SSD)
  • innodb_flush_log_at_trx_commit=2: OS crash risk, ~30K TPS
  • Group commit: Batches multiple transaction flushes into one fsync, scaling throughput without sacrificing durability
  • Redo log sizing: Larger logs = fewer checkpoints = more write throughput, but longer crash recovery

🔒 Isolation vs. Throughput

  • SERIALIZABLE: Maximum correctness, minimum concurrency
  • REPEATABLE READ: Good balance — MVCC means readers never block
  • READ COMMITTED: Less gap locking, better for high-contention workloads
  • Trade-off: Each step down in isolation increases concurrency but requires more application-level correctness checking

📈 Replication & ACID

  • Async replication: Replica can lag — reads may see stale data (breaks isolation illusion)
  • Semi-sync replication: At least one replica confirms receipt before commit returns — better durability
  • Group Replication: Consensus-based, guarantees committed data exists on majority — strongest guarantees
  • Read replicas: Eventually consistent by nature — application must handle stale reads

🌐 Distributed Transactions

  • XA transactions: Two-phase commit across multiple MySQL instances. Slow but atomic.
  • Saga pattern: Break into local transactions with compensating actions. Higher throughput, eventual consistency.
  • Sharding: Cross-shard transactions are expensive — design schemas to keep related data on the same shard
  • CAP theorem: In network partitions, you choose consistency (block) or availability (risk stale reads)

💾 Buffer Pool Sizing

  • Rule of thumb: Set innodb_buffer_pool_size to 70-80% of available RAM
  • Impact on ACID: Larger pool = more dirty pages in memory = fewer disk writes = better performance with same durability (WAL still protects)
  • Multiple instances: innodb_buffer_pool_instances reduces contention on buffer pool mutex
  • Warmup: After restart, cold buffer pool means high I/O — use innodb_buffer_pool_dump_at_shutdown

🛠 Operational Trade-offs

  • Backup: mysqldump with --single-transaction uses MVCC for consistent backup without locking (REPEATABLE READ snapshot)
  • Schema changes: Online DDL (ALGORITHM=INPLACE) avoids table locks but still takes metadata lock briefly
  • Purge lag: Long-running transactions prevent undo log cleanup, bloating tablespace
  • Recovery time: Larger redo logs improve write performance but increase crash recovery time
