MySQL Table Partitioning

Divide large tables into smaller, manageable pieces to improve query performance, simplify maintenance, and enable efficient data lifecycle management.

Partitioning Architecture

How MySQL organizes data into partitions at the storage engine level

Partition Types

MySQL supports four partitioning strategies, each suited to different access patterns

RANGE Range Partitioning

Rows assigned to partitions based on column values falling within specified ranges. Ideal for time-series data.

CREATE TABLE orders ( id BIGINT, order_date DATE, amount DECIMAL(10,2) ) PARTITION BY RANGE (YEAR(order_date)) ( PARTITION p2022 VALUES LESS THAN (2023), PARTITION p2023 VALUES LESS THAN (2024), PARTITION p2024 VALUES LESS THAN (2025), PARTITION pmax VALUES LESS THAN MAXVALUE );

Best for: Date-based data, log tables, event stores
Pruning: Excellent — date range queries scan only relevant partitions

LIST List Partitioning

Rows assigned based on column values matching a list of discrete values. Great for categorical data.

CREATE TABLE customers ( id BIGINT, region VARCHAR(20), name VARCHAR(100) ) PARTITION BY LIST COLUMNS (region) ( PARTITION p_na VALUES IN ('US','CA'), PARTITION p_eu VALUES IN ('UK','DE','FR'), PARTITION p_asia VALUES IN ('JP','IN','CN') );

Best for: Regional data, status-based tables, multi-tenant
Pruning: Excellent — queries on the list column hit only one partition

HASH Hash Partitioning

Rows distributed evenly using a modulus of the partitioning expression. Ensures uniform data distribution.

CREATE TABLE sessions ( id BIGINT, user_id BIGINT, data TEXT ) PARTITION BY HASH (user_id) PARTITIONS 8;

Best for: Even distribution when no natural range exists
Pruning: Only works with exact-match on partition key

KEY Key Partitioning

Similar to HASH but uses MySQL's internal hashing function. Can partition on non-integer columns and primary keys.

CREATE TABLE logs ( id BIGINT AUTO_INCREMENT, message TEXT, PRIMARY KEY (id) ) PARTITION BY KEY () PARTITIONS 4;

Best for: When you want automatic distribution using the PK
Pruning: Limited — best with primary key lookups

SUB Subpartitioning (Composite)

Partitions are further divided into subpartitions. Combines two strategies for fine-grained control.

CREATE TABLE events ( id BIGINT, event_date DATE, user_id BIGINT ) PARTITION BY RANGE (YEAR(event_date)) SUBPARTITION BY HASH (user_id) SUBPARTITIONS 4 ( PARTITION p2023 VALUES LESS THAN (2024), PARTITION p2024 VALUES LESS THAN (2025) );

Best for: Very large tables needing multi-dimensional splitting
Pruning: Can prune on both dimensions for highly selective queries

COLUMNS Range/List COLUMNS

Enhanced version of RANGE/LIST that supports multiple columns and non-integer types directly (no expression needed).

CREATE TABLE sales ( id BIGINT, region VARCHAR(10), sale_date DATE ) PARTITION BY RANGE COLUMNS (sale_date) ( PARTITION q1 VALUES LESS THAN ('2024-04-01'), PARTITION q2 VALUES LESS THAN ('2024-07-01') );

Best for: DATE/DATETIME columns without wrapping in YEAR()/TO_DAYS()
Pruning: Native comparison — efficient for date ranges

Comparisons with Alternatives

Partitioning vs. other strategies for managing large tables

Approach Key Idea Pros Cons Best Suited For
Table Partitioning Chosen Divide one logical table into physical segments by a partition key Transparent to app; partition pruning; instant DROP PARTITION for archival Partition key must be in every unique index; limited to 8192 partitions; overhead per partition Time-series, append-heavy workloads, data lifecycle management
Manual Sharding (application-level) App routes queries to separate physical tables or databases Full control; can shard across machines; no MySQL limitations Complex app logic; cross-shard queries difficult; schema changes multiply Multi-tenant SaaS; extreme scale beyond single server
Archival Tables Periodically move old data to a separate archive table Simple concept; keeps main table lean; archive can use different engine Requires scheduled jobs; queries spanning active+archive are complex Simple retention policies; cold data rarely queried
Indexing Optimization Add covering indexes, composite indexes, or index-only scans No schema restructuring; immediate query improvement Indexes grow with data; doesn't solve storage/maintenance at scale Tables under 100M rows; targeted query optimization

When to pick each

Choose Partitioning when...

Table exceeds 50-100M rows; you have a natural partition key (date, region); you need fast data purging (DROP PARTITION vs DELETE); queries always include the partition key.

Choose Manual Sharding when...

Single server can't handle write throughput; data exceeds single-machine storage; you need geographic data locality across regions.

Choose Archival Tables when...

Old data is rarely accessed; you want different storage engines for hot/cold data; partitioning key constraints are too restrictive.

Choose Better Indexing when...

Table is under 100M rows; slow queries are caused by missing indexes not data volume; you can't modify the schema significantly.

Use Cases & Common Pitfalls

Where partitioning shines and where it can backfire

Primary Use Cases

Time-Series / Event Data

Application logs, IoT events, financial transactions. RANGE partition by date enables efficient retention (DROP old partitions) and query pruning on time ranges. Scale: billions of rows, months/years of data.

Multi-Tenant Platforms

SaaS applications with tenant isolation. LIST partition by tenant_id for logical separation, simpler backups per tenant, and balanced I/O when tenants vary in size.

E-commerce Order History

Large order tables where recent orders are queried frequently. RANGE by order_date keeps hot partitions in buffer pool while old partitions can live on slower storage.

Data Warehousing / Reporting

Fact tables partitioned by date for ETL parallelism. Load data into new partitions via EXCHANGE PARTITION for instant, lock-free bulk loads.

Anti-Use-Cases

Small Tables (< 10M rows)

Partitioning overhead (metadata, file handles, optimizer complexity) exceeds benefits. A well-indexed table at this size is faster.

Queries That Never Include Partition Key

If your workload queries by columns OTHER than the partition key, every query scans ALL partitions — worse than no partitioning.

High-Concurrency OLTP with Many Partitions

Each partition has its own internal mutex. 1000+ partitions with high concurrency can cause contention on partition open/close operations.

Common Pitfalls

▸ Partition key not in unique indexes

The mistake: Creating a partitioned table where the unique/primary key doesn't include the partition column.
Why it happens: Developers design the schema first, add partitioning later, and don't realize MySQL requires the partition expression columns in every unique key.
The consequence: ALTER TABLE fails with error 1503: "A PRIMARY KEY must include all columns in the table's partitioning function."
The fix: Design the primary key as a composite that includes the partition column. Example: PRIMARY KEY (id, order_date) for RANGE partitioning on order_date.

▸ Too many partitions (over 1000)

The mistake: Creating daily partitions for years of data, reaching thousands of partitions.
Why it happens: "More partitions = more granular = better" seems logical but ignores MySQL internals.
The consequence: Each partition holds file descriptors, memory for metadata, and adds to optimizer cost. DDL operations (ALTER TABLE) become extremely slow. Server startup slows as all partition metadata is loaded.
The fix: Use monthly or quarterly partitions instead of daily. For truly granular needs, combine with subpartitions (max ~100 partitions x ~10 subpartitions).

▸ Forgetting MAXVALUE / catch-all partition

The mistake: Creating RANGE partitions without a MAXVALUE partition.
Why it happens: You define partitions for known ranges (2022, 2023, 2024) and forget about future data.
The consequence: INSERTs with dates beyond the last partition boundary fail with error 1526: "Table has no partition for value."
The fix: Always include a PARTITION pmax VALUES LESS THAN MAXVALUE. Or implement a scheduled job to ADD PARTITION before data arrives. The MAXVALUE approach is simpler and safer.

▸ Using expressions that prevent pruning

The mistake: Partitioning by YEAR(created_at) but querying with WHERE created_at > '2024-01-01'.
Why it happens: The partition expression and query predicate don't match forms, so the optimizer can't prove which partitions to skip.
The consequence: Full partition scan on every query — negating the primary benefit of partitioning.
The fix: Use RANGE COLUMNS(created_at) instead — it supports native date comparisons. Or rewrite queries to match: WHERE YEAR(created_at) = 2024. Always check with EXPLAIN PARTITIONS.

▸ Not testing with EXPLAIN PARTITIONS

The mistake: Assuming partition pruning happens without verifying.
Why it happens: Developers trust that "I partitioned by date and query by date, so it must prune."
The consequence: Subtle mismatches (type casts, function wrapping, OR clauses) cause all-partition scans silently.
The fix: Always run EXPLAIN SELECT ... and check the partitions column. In MySQL 8.0+, use EXPLAIN FORMAT=JSON for detailed pruning info.

▸ Partition maintenance blocking production

The mistake: Running ALTER TABLE ... REORGANIZE PARTITION on a busy production table.
Why it happens: REORGANIZE copies data between partitions and acquires metadata locks, but this isn't obvious from the DDL syntax.
The consequence: Long-running metadata lock blocks all queries on the table. Application queries queue up and timeout.
The fix: Use pt-online-schema-change or gh-ost for partition changes on live tables. For simple ADD/DROP PARTITION (which are instant for RANGE/LIST), these are safe without tools.

Best Practices

Proven patterns for successful MySQL partitioning implementations

Design Phase

  • Choose partition key based on your most common query patterns, not just data characteristics
  • Ensure the partition key is included in every UNIQUE and PRIMARY KEY constraint
  • Target 20-100 partitions as the sweet spot — enough for pruning benefit, not so many to cause overhead
  • Plan partition granularity to match your data retention policy (if you purge monthly, partition monthly)
  • Always define a MAXVALUE/catch-all partition to prevent INSERT failures

Implementation

  • Use RANGE COLUMNS for date columns — avoids function wrapping and enables native date pruning
  • Validate pruning with EXPLAIN SELECT ... — check the partitions column shows only target partitions
  • Use EXCHANGE PARTITION for zero-downtime bulk data loads into partitioned tables
  • Implement automated scripts to ADD PARTITION ahead of incoming data (e.g., create next month's partition on the 25th)
  • For hash partitions, choose a power-of-2 count (4, 8, 16) for even distribution with modulus

Operations

  • Monitor partition sizes: SELECT PARTITION_NAME, TABLE_ROWS FROM INFORMATION_SCHEMA.PARTITIONS
  • Use DROP PARTITION (instant) instead of DELETE (row-by-row) for data purging — orders of magnitude faster
  • ADD PARTITION and DROP PARTITION are metadata-only operations for RANGE/LIST — safe online
  • REORGANIZE PARTITION copies data — use online DDL tools (pt-osc, gh-ost) for production changes
  • Schedule ANALYZE TABLE per partition after large data loads to update statistics

Scaling

  • Combine partitioning with read replicas: partition for write performance and purging, replicas for read scaling
  • Use tablespace-per-partition (default in InnoDB) to enable per-partition backup/restore
  • For tables exceeding single-server capacity, partition first then shard — partitioning within each shard
  • Consider partition-wise joins: if two tables share the same partition key, joins can be parallelized per partition
  • Monitor buffer pool hit rate per partition — hot partitions should fit in memory

Scaling & Trade-offs

How partitioning handles growth and the trade-offs involved

Capacity Estimation

Scenario: E-commerce with 50M orders/year, 500 bytes/row average.

Storage: ~25 GB/year raw + indexes (~2x) = ~50 GB/year

Partition sizing: Monthly = ~4 GB/partition (12 partitions/year). Quarterly = ~12 GB/partition. Sweet spot for buffer pool caching of recent data.

5-year retention: 60 monthly partitions, 250 GB total. Manageable on single server with partitioning for fast purge of oldest month.

10x Growth Strategy

From 50M to 500M rows/year:

1. Keep monthly RANGE partitions (still only 12/year)
2. Each partition grows to ~40 GB — still fits InnoDB well
3. Add read replicas for reporting queries
4. Use EXCHANGE PARTITION for ETL loads
5. Consider subpartitioning by hash(customer_id) if single-partition scans become slow

100x Growth Strategy

From 50M to 5B rows/year:

Partitioning alone isn't enough. Strategy:
1. Shard across multiple MySQL instances by customer_id
2. Within each shard, RANGE partition by date for retention
3. Weekly partitions within shards (52/year, manageable)
4. Consider moving analytics to a columnar store (ClickHouse, BigQuery)
5. Keep MySQL partitioned tables for OLTP, replicate to analytics

Trade-off: Pruning vs. Flexibility

Partitioning forces all unique indexes to include the partition key. This means:

- You can't have a globally unique email column without including the partition key
- Foreign keys referencing the table need the partition key in the reference
- Cross-partition queries (no WHERE on partition key) are SLOWER than no partitioning

Mitigation: Use a separate lookup table for global uniqueness constraints if needed.

Trade-off: Maintenance Cost

Partitioning adds operational complexity:

- Need automated scripts for ADD/DROP partitions
- Schema migrations are more complex (must maintain partition structure)
- Backup strategies may need adjustment (per-partition vs full)
- Monitoring: check for partition skew, oversized partitions

Payoff: DROP PARTITION is O(1) vs DELETE is O(n). For a 100M row partition, that's hours saved in purge operations.

Failure Scenarios

Disk full on one partition's tablespace: Only writes to that partition fail. Other partitions continue working. Fix: expand storage or DROP the partition.

Corrupted partition file: Only that partition's data is lost. Restore from backup of just that .ibd file (partial restore).

Partition skew (one partition 10x larger): Uneven query performance. Fix: REORGANIZE or adjust boundaries.
