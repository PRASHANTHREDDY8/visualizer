Component Breakdown

Deep dive into each component's responsibilities, technology choices, and scaling strategy.

LB

Load Balancer

Distributes incoming traffic across multiple API servers evenly.

Technology
Nginx AWS ALB
Key Decisions
Round-robin with health checks. L7 load balancing to route /api/* vs static assets. SSL termination here to offload crypto from app servers.
Scaling
Horizontally scaled with DNS round-robin or AWS Global Accelerator for geo-routing. Active-passive failover for HA.
GW

API Gateway

Single entry point handling authentication, routing, and request validation.

Technology
Kong AWS API Gateway
Key Decisions
Validates API keys, enforces rate limits (via token bucket), and routes to the correct microservice. Strips sensitive headers before forwarding.
Scaling
Stateless — easily horizontally scaled. Rate limit counters stored in Redis (shared across instances).
RL

Rate Limiter

Prevents abuse by capping requests per user/IP within time windows.

Technology
Redis Token Bucket
Key Decisions
Token bucket algorithm with per-user and per-IP limits. Free tier: 100 shortens/hour. Paid tier: 10K/hour. Returns 429 with Retry-After header.
Scaling
Redis cluster with consistent hashing. Sliding window counters for accuracy. <2ms lookup per request.
US

URL Shortening Service

Core business logic: creates short URLs, resolves them, handles 301/302 redirects.

Technology
Go Node.js
Key Decisions
Uses Base62 encoding of a unique counter-based ID to generate 7-character short codes. Checks for collisions on custom aliases. Returns 301 (permanent) for SEO or 302 (temporary) for analytics tracking.
Scaling
Stateless workers behind LB. Each instance pre-fetches ID ranges from the counter service to avoid contention. Horizontal scaling with auto-scaling groups.
ID

ID Generator

Generates globally unique, monotonically increasing IDs for short URL encoding.

Technology
Snowflake ID Counter Service ZooKeeper
Key Decisions
Range-based approach: a counter service allocates ranges (e.g., 1M IDs at a time) to each URL service instance. Eliminates single point of contention. IDs are Base62-encoded: 7 chars supports 62^7 = 3.5 trillion URLs.
Scaling
Counter service backed by ZooKeeper for coordination. Each app server has a local counter within its allocated range — no network call per URL creation.
RC

Redis Cache

Caches hot URL mappings to serve redirects in sub-millisecond time.

Technology
Redis Cluster LRU Eviction
Key Decisions
80/20 rule: 20% of URLs generate 80% of traffic. Cache the top 20% with a 24h TTL. LRU eviction when memory is full. Write-around strategy: new URLs go to DB first, cached on first read.
Scaling
Redis Cluster with 6+ nodes for sharding and replication. ~70GB memory caches ~350M mappings. Expected 90%+ hit rate.
DB

URL Database

Persistent storage for all URL mappings with high write throughput.

Technology
Cassandra DynamoDB
Key Decisions
NoSQL for horizontal scalability. Schema: {short_url (PK), long_url, user_id, created_at, expiry, click_count}. Partition key = short_url for even distribution. Eventual consistency is acceptable for analytics; strong consistency for redirects.
Scaling
Range-based sharding on the first character of short_url. Replication factor of 3. Auto-scaling read/write capacity. ~500 bytes per record, 365 billion records in 10 years = ~170 TB.
AN

Analytics Service

Tracks clicks, geographic data, referrer sources, and device information.

Technology
Kafka ClickHouse Flink
Key Decisions
Async pipeline: redirect fires a Kafka event, Flink processes in real-time and batches to ClickHouse. No impact on redirect latency. Captures: timestamp, geo (via IP), user-agent, referrer.
Scaling
Kafka partitioned by short_url hash for ordering. ClickHouse columnar storage is optimized for aggregation queries. 30-day hot storage, older data in S3/Glacier.

⚖ Trade-off Analysis

301 vs 302 Redirects
301 (permanent) is faster for users and better for SEO, but browsers cache it — making analytics inaccurate. 302 (temporary) ensures every click is trackable. We use 302 for analytics-enabled links, 301 for SEO-optimized ones.
Consistency vs Availability
We favor availability (AP in CAP). A short URL that resolves 50ms late is better than one that errors out. Eventual consistency is fine for click counts; strong consistency only needed during URL creation to prevent duplicate short codes.
Counter vs Hash-based IDs
Counter-based IDs are shorter and sequential but reveal volume. Hash-based (MD5/SHA) are random but may collide. We chose counter + Base62 for minimal length with range partitioning to eliminate contention.
SQL vs NoSQL
URL mappings are simple key-value lookups with massive scale. NoSQL (Cassandra/DynamoDB) excels here: no joins needed, linear horizontal scaling, tunable consistency. SQL would require manual sharding at this scale.

⚠ Failure Scenarios

1
Cache (Redis) goes down

All reads hit the database directly. Latency increases from ~2ms to ~20ms. DB handles it with read replicas. Cache rebuilds automatically on restart via read-through pattern.

2
Database node failure

Cassandra replication factor 3 means any 1 node failure is transparent. Cluster self-heals via hinted handoff. If multiple nodes fail in same partition, reads degrade but don't fail entirely.

3
ID Generator service down

URL service nodes have pre-fetched ranges (1M IDs each). Can continue creating URLs for hours without the counter service. Fallback: UUID-based generation with collision checking.

4
Entire region outage

Global DNS failover routes to secondary region in <60 seconds. Active-active setup means secondary already has replicated data. RPO near zero, RTO < 1 minute.
