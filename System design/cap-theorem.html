CAP Theorem

In a distributed data store, you can only guarantee two out of three properties: Consistency, Availability, and Partition Tolerance. Since network partitions are inevitable, the real choice is between CP and AP.

Component Breakdown

Property

Consistency (C)

Every read receives the most recent write or an error. All nodes see the same data at the same time.

  • Mechanism: Synchronous replication, consensus protocols (Raft, Paxos)
  • Trade-off: Higher latency — must wait for all replicas to acknowledge
  • Examples: ZooKeeper, etcd, HBase, Google Spanner
Property

Availability (A)

Every request receives a non-error response, without guarantee that it contains the most recent write.

  • Mechanism: Asynchronous replication, eventual consistency, multi-master
  • Trade-off: May return stale data during partitions
  • Examples: Cassandra, DynamoDB, CouchDB, Riak
Property

Partition Tolerance (P)

The system continues to operate despite arbitrary message loss or failure of part of the network.

  • Reality: Network partitions will happen — P is not optional in distributed systems
  • Implication: The real choice is between CP and AP during a partition
  • Scope: Applies to any system with >1 node
System Type

CP Systems

Sacrifice availability during partitions to maintain consistency. Reject requests when nodes can't reach consensus.

  • Behavior during partition: Returns errors or blocks until partition heals
  • Use when: Correctness is critical (financial transactions, leader election, config management)
  • Tech: ZooKeeper, etcd, Redis (with WAIT), MongoDB (majority write concern), HBase
System Type

AP Systems

Sacrifice consistency during partitions to remain available. Every node responds, but may return stale data.

  • Behavior during partition: All nodes respond, conflict resolution happens later
  • Use when: Uptime is critical (social media feeds, DNS, shopping carts)
  • Tech: Cassandra, DynamoDB, CouchDB, Riak, DNS

Comparisons with Alternatives

Approach Trade-off Behavior During Partition Consistency Model Real-World Examples
CP Consistency + Partition Tolerance Sacrifices availability Blocks or returns errors until partition heals; refuses stale reads Strong / Linearizable ZooKeeper, etcd, HBase, Spanner
AP Availability + Partition Tolerance Sacrifices consistency All nodes respond; may return stale data; conflicts resolved later Eventual consistency Cassandra, DynamoDB, CouchDB, DNS
CA Consistency + Availability No partition tolerance Cannot handle partitions — only valid for single-node systems Strong (single-node) Single-node PostgreSQL, single-node MySQL

When to Pick Each

CP Choose CP when...

  • Data correctness is non-negotiable (banking, inventory, leader election)
  • You'd rather reject a request than return wrong data
  • Clients can tolerate brief unavailability or retries
  • Coordination services: distributed locks, config stores

AP Choose AP when...

  • User-facing uptime is critical — downtime costs more than stale data
  • The domain tolerates eventual consistency (social feeds, analytics)
  • You can design conflict resolution (last-write-wins, CRDTs, merge functions)
  • Global distribution with low latency matters

CA Choose CA when...

  • Your system runs on a single node (no distribution needed)
  • It's behind a reliable local network with no realistic partition risk
  • Prototype / MVP stage where simplicity outweighs resilience
  • Note: Not viable for truly distributed systems

Use Cases & Common Pitfalls

Primary Use Cases

Financial Transactions

CP Account balances, transfers, and ledger entries require strong consistency. A stale read could mean double-spending.

Distributed Coordination

CP Leader election, distributed locks, and service discovery (ZooKeeper, etcd) must never disagree on who holds a lock.

Social Media Feeds

AP A slightly stale timeline is far better than showing users an error page. Eventual consistency is perfectly fine.

Shopping Cart / Wishlist

AP Cart should always be accessible. Conflict resolution via merge (union of items) handles partitions gracefully.

DNS & CDN

AP Must always respond. TTL-based eventual consistency is the core design — propagation delays are expected and acceptable.

Inventory Management

CP Overselling is expensive. Stock counts must be consistent to prevent selling the last item twice.

Anti-Use-Cases

Don't use CP for analytics dashboards

Dashboards showing metrics from 5 minutes ago don't need strong consistency. CP adds latency for zero benefit here.

Don't use AP for financial ledgers

Eventual consistency on money is a lawsuit. Use CP with well-designed retry logic instead.

Don't use CA for multi-region

CA assumes no partitions. Cross-datacenter links will fail. You must choose CP or AP.

Common Pitfalls

Treating CAP as a permanent, system-wide choice ▼
The Mistake
Labeling an entire system as "CP" or "AP" and applying that uniformly to all data paths.
Why It Happens
The CAP triangle is often taught as a single choice. In reality, different data in the same system can have different requirements.
Consequence
Over-engineering low-value reads with strong consistency (added latency) or under-protecting critical writes with eventual consistency (data loss).
The Fix
Design per-data-path. User profiles can be AP (eventual), while payment records must be CP (strong). Many databases (Cassandra, MongoDB) let you tune consistency per-query.
Ignoring partition tolerance ("we have reliable networking") ▼
The Mistake
Designing a distributed system as CA, assuming the network won't partition.
Why It Happens
Cloud networks feel reliable. Partitions are rare but real — cable cuts, DNS failures, firewall misconfigs, GC pauses, asymmetric partitions.
Consequence
When a partition happens (and it will), the system exhibits undefined behavior — split-brain, data corruption, or total outage.
The Fix
Accept P as given in any multi-node system. Design and test your partition behavior explicitly. Use chaos engineering (Jepsen, Chaos Monkey) to verify.
Conflating consistency in CAP with ACID consistency ▼
The Mistake
Assuming "consistent" in CAP means the same as the "C" in ACID transactions.
Why It Happens
Same letter, similar-sounding concept. But ACID consistency means "valid state transitions" (constraints, triggers), while CAP consistency means "linearizability" (all nodes see the same data).
Consequence
Designing for the wrong guarantee. You might get ACID compliance but still have stale reads across replicas.
The Fix
Be precise: CAP-C = linearizability (every read reflects the latest write). ACID-C = integrity constraints. They're orthogonal concerns.
Not designing conflict resolution for AP systems ▼
The Mistake
Choosing AP for availability but having no strategy for resolving conflicting writes after a partition heals.
Why It Happens
Teams focus on the happy path. During a partition, both sides accept writes. When the partition heals, those writes may conflict.
Consequence
Data loss — one side's writes silently overwritten, or corrupt merged state.
The Fix
Choose a conflict resolution strategy upfront: last-write-wins (LWW), vector clocks, CRDTs, or application-level merge. Amazon's shopping cart uses union-merge; Riak supports CRDTs natively.
Jumping to "we need Spanner" in interviews ▼
The Mistake
Name-dropping Google Spanner (which appears to offer C+A+P) without understanding its constraints and cost.
Why It Happens
Spanner is often cited as "beating" CAP. It achieves very high availability with strong consistency by using atomic clocks (TrueTime), but it still sacrifices availability during severe partitions.
Consequence
Looks like you don't understand the theorem. Interviewers want to see you reason about trade-offs, not name-drop solutions.
The Fix
Acknowledge Spanner is CP — it minimizes unavailability windows through engineering, but still chooses consistency over availability during partitions. Discuss the trade-off reasoning, not just the database name.

Best Practices

Design Phase

  • Classify every data entity as CP or AP based on its business impact, not a blanket system choice
  • Define your consistency SLA: linearizable, causal, session, or eventual — most data doesn't need linearizable
  • Map out partition scenarios and document expected behavior for each (error vs. stale data vs. queue-and-retry)
  • Use the PACELC extension: during Partition choose A or C; Else (normal operation) choose Latency or Consistency

Implementation

  • Use tunable consistency where available (Cassandra's CL, MongoDB's write concern) — default to eventual, tighten for critical paths
  • Implement idempotent writes so retries after partition recovery don't create duplicates
  • Design conflict resolution before you need it: LWW with vector clocks, CRDTs for counters/sets, or application-level merge functions
  • Use read-repair and anti-entropy protocols to speed convergence in AP systems
  • Add consistency health checks: compare replica states periodically and alert on drift

Operations

  • Monitor replication lag as a first-class metric — it's the live indicator of consistency health
  • Run chaos engineering tests (Jepsen, Chaos Monkey) to verify partition behavior matches your design
  • Implement circuit breakers at service boundaries to fail fast during partitions rather than hanging
  • Set up split-brain detection and automated remediation for CP systems
  • Document your runbook: what operators should do when a partition is detected

Scaling

  • Multi-region deployments make partitions more likely — plan for cross-region latency and asymmetric failures
  • Use quorum-based replication (N=3, W=2, R=2) for tunable consistency without full synchronous overhead
  • Consider CRDT-based data types for naturally mergeable data (counters, sets, registers)
  • Cache aggressively at the edge for AP reads — stale cache is often acceptable, and it absorbs partition impact

Failure Scenarios

Network Partition

Nodes can't communicate. CP: minority partition refuses writes, majority continues. AP: both sides accept writes, merge later.

Node Failure

CP: if failed node was part of quorum, system may become unavailable until replacement joins. AP: remaining nodes absorb traffic seamlessly.

Split Brain

Both sides of a partition believe they're the leader. CP prevents this via quorum/fencing. AP accepts it and resolves conflicts after.

Cascading Failure

One component's failure causes others to fail. CP systems are more vulnerable — a partition can cause an availability cascade. AP systems degrade more gracefully.
