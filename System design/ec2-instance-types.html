Pricing Models

EC2 offers multiple purchasing options — the right choice can reduce costs by up to 90%.

On-Demand

Pay by the second, no commitment
Full flexibility. No upfront cost. Use for unpredictable workloads, dev/test, or short-term spikes.

Reserved Instances

1 or 3 year commitment
Predictable, steady-state workloads. Commit to a specific instance type in a region.
Up to 72% savings

Savings Plans

$/hr commitment, flexible type
Like Reserved but flexible across instance families, sizes, OS, and regions within a family.
Up to 72% savings

Spot Instances

Bid on spare capacity
Fault-tolerant, flexible workloads. Can be interrupted with 2-min notice. Great for batch, CI/CD, ML training.
Up to 90% savings

Common Pitfalls

Mistakes teams frequently make when selecting and managing EC2 instances.

⚠

Choosing instance type based on name familiarity alone

▼

The mistake: Defaulting to m5.xlarge because "it's what we always use" without evaluating newer generations or Graviton.

Why it happens: Teams copy-paste infrastructure configs without re-evaluating. Newer generations aren't always well-publicized.

The consequence: Paying 20-40% more for equivalent or worse performance. M7g offers ~25% better perf than M5 at ~20% lower cost.

The fix: Regularly audit instance generations. Default to the latest Graviton variant (e.g., m7g over m5) unless you have a specific x86 dependency.

⚠

Over-provisioning "just in case"

▼

The mistake: Running c5.4xlarge instances at 15% average CPU utilization because "we might need the headroom."

Why it happens: Fear of performance issues. No autoscaling configured. One-time spikes that never recurred.

The consequence: Wasting 60-80% of compute spend. Over a year, this can be tens of thousands of dollars per instance.

The fix: Use CloudWatch + Compute Optimizer. Right-size based on P95 utilization. Implement autoscaling for variable workloads. Use T3/T4g burstable instances for low-average, occasional-spike patterns.

⚠

Using compute-optimized instances for memory-bound workloads

▼

The mistake: Running Redis or Elasticsearch on C-family instances because "they're fast," then running out of memory.

Why it happens: Conflating "fast CPU" with "fast overall." Not profiling actual resource consumption.

The consequence: OOM kills, swap thrashing, forced vertical scaling to absurdly large C instances when an R instance at half the cost would suffice.

The fix: Profile your workload first. If memory utilization is >60% while CPU is <30%, switch to R-family. The 8:1 memory-to-vCPU ratio of R instances is purpose-built for this.

⚠

Ignoring network bandwidth limits on smaller instances

▼

The mistake: Running high-throughput services on t3.large and experiencing mysterious latency spikes.

Why it happens: Smaller instances have "Up to X Gbps" network — the "up to" means burst, not sustained. Baseline can be much lower.

The consequence: Intermittent network throttling that doesn't show up in CPU/memory metrics. Looks like application bugs.

The fix: Check the "Baseline bandwidth" column in AWS docs, not just the "Up to" value. For sustained high-throughput, use instances with dedicated (not burst) network bandwidth. Monitor NetworkIn/Out and NetworkPacketsIn/Out CloudWatch metrics.

⚠

Not using Spot for fault-tolerant workloads

▼

The mistake: Running all CI/CD, batch processing, and stateless workers on On-Demand because "Spot is unreliable."

Why it happens: Early Spot experiences with aggressive bidding and frequent interruptions. Lack of diversification across instance types.

The consequence: Paying 3-10x more than necessary for workloads that can tolerate interruption.

The fix: Use Spot Fleet with capacity-optimized allocation across multiple instance types. Implement graceful shutdown handlers (2-min warning). For batch: use AWS Batch with Spot. For containers: use Spot with ECS/EKS + Karpenter.

Best Practices

Proven strategies for optimal EC2 usage across selection, operation, and cost management.

Instance Selection

  • Start with Graviton (ARM) unless you have a specific x86 requirement — best price/performance ratio
  • Always use latest generation (7th gen in 2024/2025) — better perf at same or lower cost
  • Profile your workload before choosing: is it CPU, memory, I/O, or GPU bound?
  • Use AWS Compute Optimizer for data-driven right-sizing recommendations
  • Consider T3/T4g burstable for workloads with <40% average CPU utilization

Cost Optimization

  • Layer purchasing: Reserved/Savings Plans for baseline + On-Demand for peaks + Spot for fault-tolerant
  • Use Spot for: CI/CD runners, batch jobs, dev environments, stateless workers, ML training
  • Implement aggressive autoscaling — scale to zero when possible (ECS Fargate, Lambda for sporadic loads)
  • Schedule non-production instances to stop nights/weekends (saves ~65% on dev/staging)
  • Monitor with Cost Explorer; set budgets and alerts before bills surprise you

Operational Excellence

  • Use Instance Metadata Service v2 (IMDSv2) — enforce hop limit of 1 to prevent SSRF attacks
  • Never embed credentials in instances — use IAM roles and instance profiles
  • Enable detailed CloudWatch monitoring for production (1-min intervals vs default 5-min)
  • Use placement groups: cluster for low-latency HPC, spread for high availability
  • Implement health checks and auto-recovery — instances can be replaced automatically on hardware failure

Storage & Performance

  • EBS-optimized is default on current gen — but verify your IOPS/throughput aren't hitting EBS limits
  • Use gp3 over gp2 for EBS — independently configure IOPS and throughput at lower cost
  • Instance store (NVMe) is ephemeral — perfect for caches, temp data, buffers. Never for durable data.
  • For high IOPS workloads, match your instance size to your EBS volume capability — small instances throttle EBS
  • Enable EBS encryption by default in your account settings — zero performance impact on modern instances
