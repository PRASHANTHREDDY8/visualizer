Component Breakdown

Deep dive into each Kinesis service and its role in the streaming architecture.

Kinesis Data Streams

The core streaming service. Data is ingested into shards — each shard supports 1 MB/s writes and 2 MB/s reads. Records are stored for 24 hours by default (up to 365 days). Partition keys determine shard routing via MD5 hashing.

Core Service Provisioned or On-Demand

Kinesis Data Firehose

Fully managed delivery pipeline. Automatically batches, compresses, transforms (via Lambda), and delivers data to S3, Redshift, OpenSearch, or HTTP endpoints. Near real-time with 60-900 second buffering.

Fully Managed No Shards to Manage

Kinesis Data Analytics

Run SQL queries or Apache Flink applications on streaming data in real-time. Supports windowed aggregations, anomaly detection, and stream-to-stream joins. Auto-scales processing capacity.

SQL or Flink Real-time Analytics

Kinesis Video Streams

Capture, process, and store media streams from cameras and audio devices. Supports WebRTC for real-time two-way communication. Integrates with Rekognition for video analytics.

Media Streaming WebRTC

Enhanced Fan-Out

Dedicated 2 MB/s throughput per consumer via HTTP/2 push. Records are pushed to consumers within ~70ms (vs. ~200ms with polling). Supports up to 20 registered consumers per stream.

HTTP/2 Push ~70ms Latency

KCL (Consumer Library)

Java library (with multilanguage daemon) that handles shard leasing, checkpointing, and load balancing across consumer instances. Uses DynamoDB for coordination and lease management.

Auto Load Balancing DynamoDB Lease Table

Comparisons with Alternatives

How Kinesis stacks up against other streaming and messaging platforms.

Platform Key Differentiator Pros Cons Best For
AWS Kinesis AWS Native Fully managed, tight AWS integration, on-demand capacity mode Zero ops overhead, IAM security, Firehose for zero-code delivery, Lambda triggers Vendor lock-in, limited throughput per shard, 7-day max retention (365 with extended) AWS-native real-time pipelines with moderate throughput needs
Apache Kafka (MSK) High throughput, infinite retention, rich ecosystem (Connect, Streams, ksqlDB) Massive throughput, compacted topics, broad community, multi-DC replication Operational complexity (even MSK), partition rebalancing, higher cost at low scale High-throughput event backbones, event sourcing, long-term replay
Amazon SQS Message queue (not stream), at-least-once delivery, no ordering guarantee (standard) Simplest to operate, serverless, infinite scale, dead-letter queues No replay, no ordering (standard), consumer deletes messages, not a true stream Decoupling microservices, task queues, when replay isn't needed
Apache Pulsar Unified messaging + streaming, tiered storage, multi-tenancy Infinite retention via tiered storage, geo-replication, topic compaction + queuing Smaller community, more complex architecture (BookKeeper), fewer managed options Multi-tenant platforms needing both queuing and streaming semantics

When to pick each

Choose Kinesis when...

You're already on AWS, need managed streaming with sub-second latency, want tight integration with Lambda/S3/Redshift, and your throughput is under ~10 GB/s per stream.

Choose Kafka when...

You need extreme throughput (100K+ msgs/sec), infinite retention, compacted topics for materialized views, or multi-cloud portability.

Choose SQS when...

You need simple async task processing, don't need stream replay, want zero infrastructure management, or are building request-response patterns.

Choose Pulsar when...

You need multi-tenancy isolation, unified queue + stream APIs, geo-replicated topics, or tiered storage for cost-effective long retention.

Use Cases & Pitfalls

Where Kinesis shines, where it doesn't, and common mistakes to avoid.

Primary Use Cases

Real-Time Analytics

Clickstream analysis, dashboards, and metrics aggregation with sub-second latency. 100K-1M events/sec typical.

Log & Event Aggregation

Centralize application logs from hundreds of microservices into S3/OpenSearch via Firehose. Replace complex log pipelines.

IoT Data Ingestion

Ingest telemetry from millions of IoT devices. Partition by device ID for ordered per-device processing.

Real-Time ML Inference

Feed streaming features into SageMaker models for fraud detection, recommendations, or anomaly detection.

Anti-Use-Cases

Transactional Messaging

If you need exactly-once delivery with acknowledgment, use SQS or a message broker. Kinesis is at-least-once.

Long-Term Event Store

365-day max retention. For permanent event sourcing, use Kafka with infinite retention or write to S3/DynamoDB.

Low-Volume Request/Response

For simple async request/response at low volume, SQS or Step Functions are simpler and cheaper.

Common Pitfalls

Hot Shard / Uneven Partition Key Distribution ▶
The mistake: Using a low-cardinality partition key (e.g., country code with 80% traffic from one country), causing one shard to throttle while others sit idle. Why it happens: Developers pick semantically meaningful keys without analyzing distribution. The consequence: ProvisionedThroughputExceededException on the hot shard; data loss or backpressure. The fix: Use high-cardinality keys (user ID, device ID) or add random suffixes. Monitor per-shard metrics via CloudWatch IncomingBytes per shard.
Ignoring Iterator Age (Consumer Falling Behind) ▶
The mistake: Not monitoring GetRecords.IteratorAgeMilliseconds, so consumers fall hours behind without anyone noticing. Why it happens: System works fine initially; only becomes visible under load or after a consumer restart. The consequence: Data processed hours or days late. With default 24h retention, data can expire before being consumed. The fix: Alert on IteratorAge > 60 seconds. Scale consumers or upgrade to enhanced fan-out. Extend retention as a safety net.
Using GetRecords API Polling with Multiple Consumers ▶
The mistake: Having 5+ consumers polling the same shard, hitting the 5 GetRecords calls/sec limit and the shared 2 MB/s read throughput. Why it happens: Works fine with one consumer; breaks when teams add more without understanding the shared limit. The consequence: ReadProvisionedThroughputExceeded errors, increased latency, consumers stepping on each other. The fix: Use Enhanced Fan-Out for multiple consumers (dedicated 2 MB/s each). Or fan out via a single consumer that writes to SNS/SQS for downstream services.
Not Handling Resharding Correctly ▶
The mistake: Splitting or merging shards without understanding that consumers must process parent shards before children to maintain ordering. Why it happens: Resharding seems like a simple capacity change, but it's actually a data topology change. The consequence: Out-of-order processing, duplicate records, or records stuck in parent shards never consumed. The fix: Use KCL (handles resharding automatically). If custom consumer: detect SHARD_END, find child shards, process them only after parent is fully consumed.
Record Size Exceeding 1 MB Limit ▶
The mistake: Sending records larger than 1 MB (the hard API limit) or not accounting for base64 overhead in the API call. Why it happens: Data grows over time (adding fields), or batching logic creates oversized aggregated records. The consequence: PutRecord fails with ValidationException. If not handled, data is lost. The fix: Validate record size before sending. For large payloads, store in S3 and send a pointer record. Use KPL aggregation to pack many small records efficiently.

Best Practices

Proven patterns for building robust Kinesis streaming pipelines.

Design Phase ▶
  • Start with capacity math: peak events/sec x avg record size = required shards (1 MB/s each)
  • Choose On-Demand mode for unpredictable traffic; Provisioned for cost optimization at steady-state
  • Design partition keys for even distribution — analyze your key cardinality before deployment
  • Plan retention period based on your recovery SLA, not just processing speed
  • Decide between standard consumers (shared 2 MB/s) vs. Enhanced Fan-Out (dedicated 2 MB/s per consumer) upfront
Producer Implementation ▶
  • Use KPL for high-throughput producers — it handles batching, aggregation, retries, and CloudWatch metrics
  • Implement exponential backoff with jitter for ProvisionedThroughputExceededException
  • Use PutRecords (batch) instead of PutRecord (single) for better throughput and fewer API calls
  • Handle partial failures in PutRecords: check FailedRecordCount and retry only failed records
  • Add a unique deduplication ID to records if your consumer needs idempotency
# PutRecords with partial failure handling response = kinesis.put_records( StreamName='my-stream', Records=records ) if response['FailedRecordCount'] > 0: failed = [r for i, r in enumerate(records) if response['Records'][i].get('ErrorCode')] # Retry with backoff retry_with_backoff(failed)
Consumer Implementation ▶
  • Use KCL 2.x for complex consumers — it handles shard discovery, load balancing, checkpointing, and resharding
  • Checkpoint frequently but not after every record (batch checkpoints every N records or M seconds)
  • Make processing idempotent: Kinesis guarantees at-least-once delivery, not exactly-once
  • For Lambda consumers: configure batch size, parallelization factor, and bisect-on-error for optimal processing
  • Set MaxRecords wisely: larger batches = higher throughput but more memory; smaller = lower latency
Operational Excellence ▶
  • Alert on: IteratorAgeMilliseconds > threshold, WriteProvisionedThroughputExceeded, ReadProvisionedThroughputExceeded
  • Monitor per-shard metrics to detect hot shards early (not just stream-level aggregates)
  • Use enhanced monitoring (shard-level metrics) for production streams
  • Enable server-side encryption (SSE) with KMS for sensitive data streams
  • Implement a dead-letter mechanism: on repeated processing failures, write the record to a DLQ (SQS/S3) rather than blocking the shard
  • Test resharding in staging — understand how your consumers handle shard splits/merges
Cost Optimization ▶
  • Use On-Demand for spiky/unpredictable workloads; switch to Provisioned when traffic stabilizes (can be 50%+ cheaper)
  • Aggregate small records with KPL — you pay per shard-hour and per 25KB PUT payload unit
  • Right-size shard count: over-provisioning wastes money; CloudWatch data helps find the sweet spot
  • Use Firehose instead of custom consumers for simple S3/Redshift delivery — eliminates EC2/Lambda costs
  • Set retention to minimum needed (24h default is often sufficient with checkpointing)

Key Trade-offs

Latency vs. Cost

Enhanced Fan-Out gives ~70ms delivery latency but costs ~$0.015/shard-hour extra + $0.013/GB. Standard polling is included but adds 200-1000ms latency and shares the 2 MB/s limit.

On-Demand vs. Provisioned

On-Demand auto-scales and charges per GB (~$0.08/GB) — great for variable workloads. Provisioned is ~$0.015/shard-hour — cheaper at steady state but requires manual scaling.

Ordering vs. Throughput

Kinesis guarantees ordering within a shard (by partition key). If you need global ordering, you're limited to one shard (1 MB/s). Most designs trade global order for parallelism.

Simplicity vs. Control

Firehose is zero-code delivery to S3/Redshift but offers limited processing (Lambda transform only). KCL gives full control but requires EC2/ECS infrastructure and DynamoDB for leases.
