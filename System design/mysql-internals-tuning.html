MySQL Internals & Performance Tuning

Deep dive into MySQL architecture, InnoDB storage engine, query execution pipeline, and critical tuning parameters

MySQL Server Architecture

MySQL is structured in three primary layers. Each layer has distinct responsibilities and tuning opportunities.

Component Details

Thread Pool / Connection Handling

Manages client connections with one thread per connection (default) or a thread pool (Enterprise).

Key insight: Each connection consumes ~256KB–1MB of RAM. At 1000+ connections, memory becomes a bottleneck even before CPU.
Tuning: max_connections, thread_cache_size, wait_timeout
Best practice: Use connection pooling (ProxySQL, PgBouncer equivalent) to keep active connections low.

Query Parser

Converts SQL text into an Abstract Syntax Tree (AST). Validates syntax and resolves table/column names.

What can go wrong: Complex queries with many JOINs or subqueries increase parse time.
Optimization: Prepared statements skip re-parsing. Keep SQL simple and avoid deeply nested subqueries.

Query Optimizer

Evaluates multiple execution plans and picks the cheapest one based on cost estimates.

Uses: Index statistics, cardinality estimates, join ordering heuristics.
Tuning: optimizer_switch, ANALYZE TABLE to refresh stats, index hints.
Pitfall: Stale statistics lead to bad plans. Run ANALYZE TABLE after bulk loads.

InnoDB Buffer Pool

The single most important structure — caches data pages and index pages in RAM to avoid disk I/O.

Size rule: Set to 70-80% of available RAM on dedicated DB servers.
Internals: LRU list with midpoint insertion (3/8 from head). Young and old sublists.
Tuning: innodb_buffer_pool_size, innodb_buffer_pool_instances

Redo Log (WAL)

Write-Ahead Log ensures crash recovery. All changes are written to redo log before disk pages are updated.

How it works: Sequential writes to circular log files → extremely fast. Dirty pages are flushed later.
Tuning: innodb_log_file_size (larger = fewer checkpoints, better write throughput), innodb_log_buffer_size
Trade-off: Larger redo log = faster writes but longer crash recovery time.

Binary Log

Records all data-modifying statements for replication and point-in-time recovery.

Formats: STATEMENT (SQL text), ROW (actual row changes), MIXED (auto-selects).
Performance: ROW format is safest but generates more I/O. MIXED balances safety and performance.
Tuning: binlog_format, sync_binlog, expire_logs_days

B+ Tree Clustered Index

Core Data Structure

All InnoDB data is stored in B+ trees. The primary key IS the clustered index — row data is stored in leaf nodes ordered by PK.

Why it matters: Sequential PK access is extremely fast (data locality). Random UUIDs as PKs cause massive page splits and fragmentation.
Secondary indexes: Leaf nodes store the PK value (not a row pointer). Lookups require a "bookmark lookup" back to the clustered index.
Page size: Default 16KB pages. Each leaf page holds many rows. Larger rows = fewer rows per page = more I/O.

MVCC (Multi-Version Concurrency Control)

Concurrency

Readers never block writers and vice versa. Each row has a hidden transaction ID and rollback pointer.

How it works: Each transaction sees a "snapshot" of data at its start time. Old versions stored in undo logs.
Read views: Consistent reads use the snapshot. No locks needed for SELECT.
Pitfall: Long-running transactions hold undo log space and prevent purging → undo tablespace bloat.
Tuning: Keep transactions short. Monitor trx_rows_locked, history_list_length.

Redo Log (Write-Ahead Log)

Durability

Circular log files that record all page modifications before they hit the actual data files.

Write path: Modify page in buffer pool → write redo log entry → acknowledge commit → flush dirty page later (checkpoint).
Why sequential: Disk sequential writes are 100x faster than random writes. Redo log converts random writes to sequential.
Sizing: Total redo log size should hold ~1 hour of writes. Too small = aggressive checkpointing = I/O spikes.
Key params: innodb_log_file_size, innodb_flush_log_at_trx_commit

Change Buffer

Write Optimization

Caches changes to secondary index pages that aren't in the buffer pool, merging them later during reads.

Benefit: Avoids random I/O for secondary index updates. Especially valuable for write-heavy workloads with many indexes.
When it helps: Tables with many secondary indexes, inserts/updates that don't immediately read the affected index pages.
Tuning: innodb_change_buffer_max_size (default 25% of buffer pool). Disable for SSDs with fast random I/O.

Doublewrite Buffer

Data Integrity

Protects against partial page writes (torn pages) during crashes by writing pages to a sequential area first.

Problem solved: If MySQL crashes mid-write of a 16KB page, the page is corrupt. Doublewrite ensures a good copy exists.
Performance cost: ~5-10% write overhead. Each page is written twice (doublewrite buffer → final location).
When to disable: On file systems with atomic writes (ZFS, certain SSDs with power-loss protection), or on replicas where you can rebuild.

Adaptive Hash Index (AHI)

Auto-Optimization

InnoDB automatically builds in-memory hash indexes for frequently accessed B+ tree pages.

How it works: Monitors access patterns. If a page is accessed via the same index prefix repeatedly, builds a hash for O(1) lookup.
When it helps: Point lookups (WHERE id = ?) on hot data. Can reduce B+ tree traversal from O(log n) to O(1).
When it hurts: Contention on AHI latches under high concurrency. Range scans don't benefit.
Tuning: innodb_adaptive_hash_index (on/off), monitor via SHOW ENGINE INNODB STATUS.

Scaling MySQL for Traffic

Strategies for handling 10x, 100x, and 1000x traffic growth.

📊 Read Scaling

  • Add read replicas (async replication) — each replica handles a portion of read traffic
  • Use connection-level routing: writes → primary, reads → replicas (ProxySQL, application-level)
  • Implement read-after-write consistency with GTID tracking when needed
  • Cache hot queries in Redis/Memcached — cache invalidation on write
  • Use semi-synchronous replication for strong-read replicas (higher latency)

✍️ Write Scaling

  • Vertical scaling first — faster CPUs, NVMe SSDs, more RAM for buffer pool
  • Horizontal sharding — split data across multiple MySQL instances by a shard key
  • Batch small writes — group INSERTs into multi-row statements (10-100x faster)
  • Use innodb_flush_log_at_trx_commit=2 for non-critical data (1 second durability window)
  • Partition large tables — prune partitions during queries, parallelize maintenance

🔌 Connection Scaling

  • ProxySQL for connection multiplexing — 10,000 app connections → 100 MySQL connections
  • Tune wait_timeout to kill idle connections quickly (default 28800s is too long)
  • Thread pool (MySQL Enterprise or Percona) — handle more connections with fewer OS threads
  • Application-side connection pooling (HikariCP, SQLAlchemy pool)
  • Monitor Threads_running not Threads_connected — active matters, idle doesn't

💾 Storage Scaling

  • NVMe SSDs eliminate I/O bottleneck — InnoDB designed for spinning disks, SSDs unlock full potential
  • Separate redo log and data files on different I/O paths
  • InnoDB compression (ROW_FORMAT=COMPRESSED) for cold data — saves space, costs CPU
  • Archive old data to cheaper storage (partitioning + partition exchange)
  • Use innodb_page_size=4K for SSD workloads (matches SSD page size)

⚡ Query Optimization

  • EXPLAIN ANALYZE every slow query — understand actual vs estimated rows
  • Covering indexes: include all columns in the index → skip clustered index lookup
  • Avoid SELECT * — fetch only needed columns, reduces I/O and network
  • Use index condition pushdown (ICP) — filter at storage engine level, not server level
  • Optimize ORDER BY with proper indexes to avoid filesort (sort buffer → temp files)

🛡️ High Availability

  • InnoDB Cluster (Group Replication) — automatic failover, consensus-based
  • Semi-synchronous replication — at least one replica confirms before commit ACK
  • ProxySQL for transparent failover — app doesn't know the primary changed
  • PITR (Point-In-Time Recovery) via binlog replay — recover to any second
  • Regular backup testing — a backup that hasn't been restored is not a backup

Traffic Handling Checklist by Scale

100-1K QPS

Single Server
Enough for: Most apps. Focus on proper indexing and buffer pool sizing.
Actions: Set buffer pool to 70-80% RAM. Add indexes for slow queries. Connection pooling. Enable slow query log.

1K-10K QPS

Read Replicas
Add: 2-4 read replicas. ProxySQL for routing. Redis for hot query caching.
Actions: Split read/write traffic. Optimize top 10 queries. Consider table partitioning for large tables.

10K-100K+ QPS

Sharding Required
Architecture: Horizontal sharding by tenant/user/geo. Vitess or custom shard router.
Actions: Shard large tables. Cross-shard queries via scatter-gather. Consider moving analytics to a separate system (ClickHouse, BigQuery).
