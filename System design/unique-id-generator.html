Component Breakdown

Key components of the Range Handler architecture

🎯 Range Handler

Central microservice that exclusively manages range allocation. Maintains a global counter and hands out non-overlapping ranges to application servers on demand.

Go / Rust gRPC Leader election
Scaling: Active-passive with automatic failover. Low request rate (only called when ranges exhaust).

🖥 Application Servers

Stateless services that hold a local range. Assign IDs by incrementing a local counter — zero network overhead per ID generation.

Horizontal scale Stateless In-memory counter
Scaling: Add more instances freely. Each gets its own range with no coordination.

💾 Replicated Storage

Persists range allocation state (which ranges are taken, current high-water mark). Enables recovery after Range Handler failure.

etcd / ZooKeeper Strong consistency WAL
Scaling: Raft/Paxos consensus. 3-5 node cluster handles the low write volume easily.

⚖ Load Balancer

Distributes incoming ID requests across application servers. Ensures even utilization and handles server health checks.

Round-robin Health checks L4/L7
Scaling: DNS-based or hardware LB. Standard horizontal scaling patterns apply.

🛡 Failover Server

Hot standby for the Range Handler. Monitors primary health and takes over range allocation if the primary fails, reading last state from storage.

Hot standby Heartbeat Auto-promote
Scaling: Single standby sufficient due to low primary load. Sub-second failover target.

📊 Monitoring

Tracks range consumption rate, server health, allocation latency, and remaining ID capacity to predict exhaustion and trigger alerts.

Prometheus Grafana PagerDuty
Alert on: Range exhaustion rate, failover events, storage replication lag.

Scaling & Trade-offs

Capacity planning, growth strategies, and failure analysis

Back-of-Envelope Capacity Estimation

Total 64-bit ID space 2^64 = 1.84 x 10^19
Target throughput 1,000,000,000 IDs/day
Per-second rate ~11,574 IDs/sec
With 10 servers (range=1M) ~1 range request / 86 sec / server
Range Handler load ~10 req/86s = 0.12 QPS
Years until ID exhaustion ~50.5 million years

📈 Growth Strategies

  • 10x load: Add more app servers, each gets independent ranges
  • 100x load: Shard range handler by region/data center
  • New data center: Allocate dedicated range partitions per DC
  • Burst handling: Pre-fetch next range before current exhausts

⚖ Key Trade-offs

  • Range size: Large = fewer handler calls, but more waste on failure
  • Consistency: Strong consistency at handler, eventual at app layer
  • Ordering: IDs are unique but NOT globally ordered by time
  • Gaps: Acceptable — not sequential, just unique

🌐 Multi-Region Strategy

  • Partition the 64-bit space by region prefix bits
  • Each region's range handler owns a non-overlapping slice
  • No cross-region coordination needed for ID generation
  • Example: 4-bit prefix = 16 regions, each with 2^60 IDs

Failure Scenarios & Mitigations

App Server Crash

Unassigned IDs in the server's current range are permanently lost (gaps in sequence).

Mitigation: Use smaller ranges (e.g., 10K–100K) to minimize waste. Gaps are acceptable — they don't violate uniqueness.
Range Handler Down

App servers cannot get new ranges. Existing servers continue until their current range exhausts.

Mitigation: Hot standby with sub-second failover. Pre-fetch next range while current is 80% consumed.
Storage Corruption

Range allocation state lost — risk of duplicate range assignments.

Mitigation: Replicated storage (etcd/ZooKeeper) with WAL. On recovery, skip ahead by a safety margin to avoid overlaps.
