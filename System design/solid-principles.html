SOLID Principles

Five fundamental principles of object-oriented design that make Python code more maintainable, flexible, and understandable.

SSingle Responsibility OOpen/Closed LLiskov Substitution IInterface Segregation DDependency Inversion
S

Single Responsibility Principle "A class should have only one reason to change."

What It Means

Every class should do one thing and do it well. If a class has multiple responsibilities, changes to one responsibility may break the other.

Analogy: A chef cooks food. A waiter serves food. A cashier handles payment. You wouldn't want one person doing all three — when the menu changes, it shouldn't affect how bills are processed.
  • A class that both handles business logic AND writes to database
  • A class that validates input AND sends emails AND generates reports
  • A "God class" that does everything related to a domain entity
  • Each class is easier to understand and test
  • Changes are isolated — less chance of unintended side effects
  • Classes can be reused independently
Violation
Correct
# BAD: One class with multiple responsibilities class Employee: def __init__(self, name, salary): self.name = name self.salary = salary def calculate_pay(self): # Business logic return self.salary * 1.1 def save_to_database(self): # Persistence logic db.execute(f"INSERT INTO employees...") def generate_report(self): # Reporting logic return f"Report for {self.name}" def send_email(self, message): # Communication logic smtp.send(self.email, message)
# GOOD: Each class has one responsibility class Employee: """Holds employee data only.""" def __init__(self, name, salary): self.name = name self.salary = salary class PayCalculator: """Handles pay computation.""" def calculate(self, employee: Employee) -> float: return employee.salary * 1.1 class EmployeeRepository: """Handles persistence.""" def save(self, employee: Employee): db.execute(f"INSERT INTO employees...") class ReportGenerator: """Handles report creation.""" def generate(self, employee: Employee) -> str: return f"Report for {employee.name}"
O

Open/Closed Principle "Open for extension, closed for modification."

What It Means

You should be able to add new behavior without changing existing code. Use abstractions (abstract classes, protocols) so new features plug in without modifying what's already working.

Analogy: A power strip is open for extension (plug in new devices) but closed for modification (you don't rewire it for each new appliance).
  • Adding if/elif chains every time a new type is introduced
  • Modifying a working function to handle a new case
  • Type-checking with isinstance() throughout the codebase
  • Existing tested code stays untouched
  • New features added by writing new classes, not editing old ones
  • Follows the "plugin" architecture pattern
Violation
Correct
# BAD: Must modify this function for every new shape class AreaCalculator: def calculate(self, shape): if shape.type == "circle": return 3.14 * shape.radius ** 2 elif shape.type == "rectangle": return shape.width * shape.height elif shape.type == "triangle": # Added later - modifying existing code! return 0.5 * shape.base * shape.height # Every new shape = modify this method # Risk breaking existing shapes!
from abc import ABC, abstractmethod import math class Shape(ABC): @abstractmethod def area(self) -> float: ... class Circle(Shape): def __init__(self, radius: float): self.radius = radius def area(self) -> float: return math.pi * self.radius ** 2 class Rectangle(Shape): def __init__(self, width, height): self.width = width self.height = height def area(self) -> float: return self.width * self.height # Adding a new shape: NO existing code modified! class Triangle(Shape): def __init__(self, base, height): self.base = base self.height = height def area(self) -> float: return 0.5 * self.base * self.height # Works with any shape — past, present, future def total_area(shapes: list[Shape]) -> float: return sum(s.area() for s in shapes)
💡
Key Pattern: Strategy via Abstraction Use Python's ABC + @abstractmethod or Protocol to define contracts. New behaviors become new classes — not new branches in existing code.
L

Liskov Substitution Principle "Subtypes must be substitutable for their base types."

What It Means

If class B extends class A, you should be able to use B everywhere A is expected without anything breaking. Subclasses must honor the parent's contract — same inputs, compatible outputs, no surprise exceptions.

Analogy: If you order a "car" and get a sports car or an SUV, both should still drive forward, brake, and turn. A "car" that can't reverse violates expectations.
  • A subclass that raises NotImplementedError for inherited methods
  • A subclass that narrows accepted input types (stricter preconditions)
  • The classic: Square inheriting Rectangle and breaking set_width/set_height
  • Polymorphism actually works — no isinstance checks needed
  • Code using the base type is safe with any subtype
  • Tests for the base class also validate subtypes
Violation
Correct
# BAD: Square violates Rectangle's contract class Rectangle: def __init__(self, width, height): self._width = width self._height = height def set_width(self, w): self._width = w def set_height(self, h): self._height = h def area(self): return self._width * self._height class Square(Rectangle): def set_width(self, w): self._width = w self._height = w # Surprise! def set_height(self, h): self._width = h # Surprise! self._height = h # This function BREAKS with Square: def resize(rect: Rectangle): rect.set_width(5) rect.set_height(10) assert rect.area() == 50 # FAILS! Gets 100
# GOOD: Use a common abstraction from abc import ABC, abstractmethod class Shape(ABC): @abstractmethod def area(self) -> float: ... class Rectangle(Shape): def __init__(self, width: float, height: float): self.width = width self.height = height def area(self) -> float: return self.width * self.height class Square(Shape): def __init__(self, side: float): self.side = side def area(self) -> float: return self.side ** 2 # Both work anywhere a Shape is expected def print_area(shape: Shape): print(f"Area: {shape.area()}") print_area(Rectangle(5, 10)) # Area: 50 print_area(Square(7)) # Area: 49
🧪
LSP Test: The "Behavioral Subtyping" Check For every method: Does the subclass accept the same (or wider) inputs? Does it return the same (or narrower) output types? Does it throw the same (or fewer) exceptions? If yes, LSP holds.
I

Interface Segregation Principle "No client should be forced to depend on methods it doesn't use."

What It Means

Instead of one large interface (abstract class), create smaller, focused ones. Classes should only implement the methods they actually need.

Analogy: A restaurant menu with 200 items is overwhelming. Better: separate breakfast, lunch, and dinner menus. Each customer sees only what's relevant.
  • A "Worker" interface that forces robots to implement eat()
  • Fat interfaces where implementers raise NotImplementedError
  • Forcing a read-only service to implement write() and delete()
  • Classes are simpler — only implement what they need
  • Changes to one interface don't ripple to unrelated implementers
  • Easy to compose behaviors: a class can implement multiple small interfaces
Violation
Correct
# BAD: Fat interface forces irrelevant methods from abc import ABC, abstractmethod class Worker(ABC): @abstractmethod def work(self): ... @abstractmethod def eat(self): ... @abstractmethod def sleep(self): ... class Human(Worker): def work(self): print("Working...") def eat(self): print("Eating...") def sleep(self): print("Sleeping...") class Robot(Worker): def work(self): print("Working...") def eat(self): raise NotImplementedError # Robots don't eat! def sleep(self): raise NotImplementedError # Robots don't sleep!
# GOOD: Segregated interfaces (using Protocols) from typing import Protocol class Workable(Protocol): def work(self) -> None: ... class Eatable(Protocol): def eat(self) -> None: ... class Sleepable(Protocol): def sleep(self) -> None: ... class Human: """Implements all three — naturally.""" def work(self): print("Working...") def eat(self): print("Eating...") def sleep(self): print("Sleeping...") class Robot: """Only implements what makes sense.""" def work(self): print("Working...") # Functions accept only what they need def assign_task(worker: Workable): worker.work() # Works for Human AND Robot def lunch_break(entity: Eatable): entity.eat() # Only accepts things that can eat
🎯
Python Tip: Protocol vs ABC Use typing.Protocol for structural subtyping (duck typing formalized) — classes don't need to explicitly inherit. Use ABC when you want enforced inheritance and shared implementation.
D

Dependency Inversion Principle "Depend on abstractions, not concretions."

What It Means

High-level modules should not import low-level modules directly. Both should depend on abstractions (interfaces/protocols). This makes your system flexible and testable.

Analogy: A lamp doesn't care if electricity comes from solar, wind, or coal. It depends on the "power outlet" abstraction — not a specific power plant.
  • OrderService directly instantiating MySQLDatabase()
  • Business logic importing a specific email library
  • Tight coupling: changing the database requires changing business logic
  • Swap implementations without touching business logic (e.g., MySQL to PostgreSQL)
  • Easy to test with mocks/fakes
  • High-level policy is protected from low-level detail changes
Violation
Correct
# BAD: High-level depends directly on low-level import smtplib class MySQLDatabase: def save_order(self, order): # MySQL-specific code ... class OrderService: def __init__(self): # Directly coupled to MySQL! self.db = MySQLDatabase() # Directly coupled to SMTP! self.mailer = smtplib.SMTP('smtp.gmail.com') def place_order(self, order): self.db.save_order(order) self.mailer.send(...) # Can't test without a real MySQL + SMTP server! # Can't switch to PostgreSQL without rewriting OrderService
# GOOD: Depend on abstractions, inject dependencies from typing import Protocol class Database(Protocol): def save_order(self, order) -> None: ... class Notifier(Protocol): def send(self, recipient: str, msg: str) -> None: ... class OrderService: def __init__(self, db: Database, notifier: Notifier): self.db = db self.notifier = notifier def place_order(self, order): self.db.save_order(order) self.notifier.send(order.email, "Order placed!") # Concrete implementations class PostgresDB: def save_order(self, order): ... class SlackNotifier: def send(self, recipient, msg): ... # Inject at composition root service = OrderService(db=PostgresDB(), notifier=SlackNotifier()) # Testing with fakes — no real DB needed! class FakeDB: def save_order(self, order): self.saved = order test_service = OrderService(db=FakeDB(), notifier=FakeNotifier())

When to Apply SOLID

Do Apply

  • Production code that will be maintained long-term
  • Libraries or frameworks used by multiple teams
  • Code that needs to be unit-testable in isolation
  • Areas where requirements change frequently

Don't Over-Apply

  • One-off scripts or throwaway prototypes
  • Simple CRUD with no business logic
  • When it adds complexity without flexibility benefit
  • Premature abstraction for hypothetical future needs
