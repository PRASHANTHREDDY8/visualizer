AWS SQS & SNS Architecture

Decoupled messaging with publish/subscribe and point-to-point queuing patterns

Component Breakdown

Core services and their roles in the messaging architecture

S
Amazon SNS
Pub/Sub

Fully managed publish/subscribe messaging that delivers messages to multiple subscribers simultaneously.

Model: Fan-out (one-to-many). A single published message is delivered to all subscribed endpoints.
Delivery: Push-based. SNS pushes messages to subscribers (HTTP, Lambda, SQS, email, SMS).
Retention: No persistence. If a subscriber is unavailable, messages may be lost (unless backed by SQS).
Ordering: FIFO topics available for strict ordering with deduplication.
Q
Amazon SQS
Queue

Fully managed message queuing service for decoupling and scaling microservices, distributed systems, and serverless apps.

Model: Point-to-point (one-to-one). Each message is consumed by exactly one consumer.
Delivery: Pull-based. Consumers poll the queue for messages.
Retention: Up to 14 days. Messages persist until consumed or expired.
Types: Standard (at-least-once, best-effort ordering) and FIFO (exactly-once, strict ordering at 300 msg/s).
F
Fan-out Pattern
SNS + SQS

Combine SNS with SQS to fan out messages to multiple independent consumers with guaranteed delivery.

How: Publish to SNS topic → SNS delivers to multiple SQS queues → each queue has its own consumer.
Benefit: Adds durability to pub/sub. If a consumer is down, messages wait in its queue.
Filtering: SNS subscription filter policies route only relevant messages to each queue.
Use case: Order placed → notify inventory, billing, shipping, and analytics independently.
D
Dead Letter Queue (DLQ)
Error Handling

A secondary SQS queue that captures messages that fail processing after a configured number of retries.

Trigger: After maxReceiveCount failures, message is moved to DLQ automatically.
Purpose: Isolate poison messages, enable debugging, prevent infinite retry loops.
Recovery: DLQ redrive lets you move messages back to the source queue after fixing the issue.
Monitoring: Alarm on DLQ depth > 0 to catch processing failures early.
V
Visibility Timeout
Concurrency

SQS mechanism that temporarily hides a message from other consumers while one is processing it.

Default: 30 seconds. Should be set to your worst-case processing time + buffer.
If too short: Message reappears and gets processed by another consumer → duplicates.
If too long: If consumer crashes, message stays hidden too long → increased latency for retry.
Extension: Use ChangeMessageVisibility API to extend timeout for long-running tasks.
P
Message Filtering
Routing

SNS subscription filter policies let subscribers receive only messages matching specific attribute patterns.

Scope: Filter on message attributes (key-value) or message body (JSON payload).
Operators: Exact match, prefix, numeric range, exists/not-exists, anything-but.
Benefit: Reduces consumer load. Subscribers don't receive irrelevant messages.
Cost: Filtered-out messages aren't charged to the subscriber. Only matches incur delivery cost.

Comparisons & Alternatives

When to use SQS/SNS vs. other AWS messaging services

Service Model Pros Cons Best For
SNS + SQSRecommended Fan-out with durable queues Serverless, no ops overhead, pay-per-message, filter policies, DLQ support, massive scale Limited to 256KB messages, no replay, eventual consistency in Standard mode Event-driven microservices, async workflows, notifications
Amazon EventBridge Event bus with rules Rich filtering (content-based), schema registry, cross-account, SaaS integrations Higher latency (~500ms), lower throughput than SNS, more complex pricing Event-driven architectures, SaaS integrations, complex routing
Amazon Kinesis Streaming (ordered shards) Ordered by partition key, replay up to 365 days, multiple consumers per shard Shard management overhead, provisioned capacity, 1MB record limit Real-time analytics, log aggregation, clickstream, IoT telemetry
Amazon MQ (ActiveMQ/RabbitMQ) Traditional broker JMS/AMQP/MQTT support, lift-and-shift from on-prem, rich routing Not serverless (broker instances), limited scaling, higher cost at scale Migrating legacy apps using standard protocols without code changes

When to pick each

SNS + SQS

Choose when you need serverless, massive throughput, and simple fan-out with durability. No broker to manage. Works best for decoupled microservices and event notifications.

EventBridge

Choose when you need content-based filtering on event payload, schema evolution, or need to react to events from SaaS providers (Shopify, Zendesk, etc.).

Kinesis

Choose when ordering matters, you need to replay events, or multiple consumers need to process the same stream independently (like Kafka).

Amazon MQ

Choose only for lift-and-shift migrations where existing apps use JMS, AMQP, or MQTT protocols and cannot be rewritten.

Use Cases & Common Pitfalls

Where SQS/SNS excels, and mistakes to avoid

Primary Use Cases

📦 Order Processing Pipeline

Order placed → SNS fans out to payment, inventory, shipping, and notification services. Each has its own SQS queue for independent processing and retry.

⚡ Lambda Event Processing

SQS triggers Lambda with batches of messages. Lambda processes and deletes. Failed messages go to DLQ. Scales from 0 to thousands automatically.

🔔 Multi-channel Notifications

SNS delivers alerts to email, SMS, mobile push, HTTP endpoints, and Lambda simultaneously from a single publish call.

🔀 Work Queue Load Leveling

Bursty producer writes to SQS. Consumers process at a steady rate. Queue absorbs spikes without overloading downstream services.

🔗 Cross-service Integration

S3 event → SNS → multiple SQS queues. Image upload triggers thumbnail generation, metadata extraction, and virus scanning in parallel.

🔒 Audit & Compliance Logging

All API mutations published to SNS. Compliance service subscribes via SQS FIFO for ordered, exactly-once audit trail. No events lost.

Anti-Use-Cases

Don't use SQS/SNS when...

Real-time streaming analytics

SQS has no ordering guarantee in Standard mode and can't replay. Use Kinesis Data Streams or MSK for ordered, replayable event streams.

Request/response (synchronous)

SQS/SNS are for async decoupling. If you need a response within the same HTTP request, use API Gateway + Lambda or direct service calls.

Large payloads (>256KB)

SQS/SNS limit messages to 256KB. For larger payloads, store in S3 and send a reference. Use the SQS Extended Client Library for this pattern.

Common Pitfalls

⚠️ Not configuring Dead Letter Queues ▼
The mistakeProcessing fails silently, messages return to the queue and retry infinitely, wasting compute and hiding bugs.
Why it happensDLQ is optional and easy to skip during initial setup. "We'll add it later."
ConsequencePoison messages consume all processing capacity. The queue grows. Legitimate messages are delayed or lost when retention expires.
The fixAlways configure a DLQ with maxReceiveCount of 3-5. Set CloudWatch alarm on DLQ ApproximateNumberOfMessagesVisible > 0. Build a redrive workflow.
⚠️ Setting visibility timeout too short ▼
The mistakeVisibility timeout is shorter than processing time. Message becomes visible again. Another consumer picks it up. Duplicate processing.
Why it happensDefault is 30s which is fine for fast tasks. But when processing involves external API calls or heavy computation, it's insufficient.
ConsequenceDuplicate processing, race conditions, data corruption, wasted compute, potential financial loss (double charges).
The fixSet visibility timeout to 6x your average processing time. Use ChangeMessageVisibility to extend for long tasks. Make consumers idempotent regardless.
⚠️ Assuming Standard SQS is exactly-once ▼
The mistakeBuilding non-idempotent consumers for Standard queues, assuming each message is delivered exactly once.
Why it happensThe word "queue" implies ordered, single-delivery semantics. Standard SQS is actually at-least-once with best-effort ordering.
ConsequenceDuplicate charges, double notifications, corrupted counters, inconsistent state.
The fixAlways design idempotent consumers (use message deduplication IDs + database upserts). Or use FIFO queues for exactly-once (at lower throughput).
⚠️ Using SNS without SQS for critical messages ▼
The mistakeSubscribing HTTP endpoints directly to SNS for critical business events without a queue buffer.
Why it happensDirect HTTP subscription is simpler to set up. "Our endpoint is always up."
ConsequenceIf the HTTP endpoint is down during delivery, SNS retries per its retry policy (3 attempts for HTTP). After that, the message is lost forever.
The fixFor critical messages, always use SNS → SQS → Consumer pattern. SQS provides durability (14-day retention) even if the consumer is down for hours.
⚠️ Ignoring long polling — using short polling ▼
The mistakePolling SQS with WaitTimeSeconds=0 (short poll). Most responses are empty. Burning money on empty receives.
Why it happensShort polling is the default. Documentation buries long polling configuration.
ConsequenceExcessive API calls (you're charged per request), increased cost, unnecessary network traffic, and slightly higher latency (messages found on next poll cycle).
The fixSet WaitTimeSeconds=20 (max) on ReceiveMessage calls or at the queue level. Reduces empty responses by 90%+ and saves significant cost.

Best Practices

Proven patterns for production SQS/SNS systems

◆ Design Phase

✓
Define message schema upfront with versioning (include a "version" field in every message body)
✓
Choose Standard vs. FIFO based on ordering needs, not defaults. FIFO has 300 msg/s limit (3000 with batching)
✓
Plan DLQ strategy from day one — what triggers a dead letter, who monitors it, how messages get redriven
✓
Design consumers to be idempotent regardless of queue type. Duplicates will happen
✓
Use SNS filter policies to reduce fan-out noise — don't make every subscriber filter client-side

◆ Implementation

✓
Use long polling (WaitTimeSeconds=20) to minimize empty responses and reduce cost
✓
Batch operations: SendMessageBatch and DeleteMessageBatch (up to 10) for throughput and cost savings
✓
Delete messages only after processing succeeds. If the delete fails, the message will be reprocessed (which is fine if idempotent)
✓
For payloads > 256KB, store in S3 and send a reference. Use SQS Extended Client Library
✓
Set message attributes for filtering and routing — keep the body for data, attributes for metadata

◆ Operations

✓
Monitor ApproximateAgeOfOldestMessage to detect consumer lag. Alert when age exceeds your SLA
✓
Alert on NumberOfMessagesSent vs. NumberOfMessagesDeleted divergence (indicates failed processing)
✓
Use DLQ redrive API for recovery — don't manually read and re-publish messages
✓
Enable server-side encryption (SSE-SQS or SSE-KMS) for sensitive messages. It's one checkbox
✓
Set IAM policies with least privilege — separate publish and consume permissions across services

◆ Scaling

✓
SQS scales automatically — no provisioning. Standard: unlimited throughput. Focus on consumer scaling
✓
Use SQS as Lambda event source with batch size tuning (1-10000). Lambda auto-scales consumers
✓
For EC2/ECS consumers, auto-scale based on ApproximateNumberOfMessages / number_of_consumers
✓
FIFO: use distinct MessageGroupIds to parallelize ordered processing across message groups
✓
SNS: no limits to worry about for topics/subscriptions. Focus on subscriber scaling instead
