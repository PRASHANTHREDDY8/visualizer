Component Breakdown

Each component's role in ensuring idempotent request handling

🔑

Idempotency Key

A client-generated unique identifier (UUID v4) sent as a header with each request. The same key on a retry signals "this is the same operation."

UUID v4 Client-Generated Header: Idempotency-Key
Keys should be generated before the first attempt and reused on all retries of that specific operation.
⚡

Idempotency Store

A fast key-value store that maps idempotency keys to their processing status and cached responses. Must support atomic operations for locking.

Redis SETNX (distributed lock) TTL: 24-48h
Redis SETNX provides atomic check-and-set needed for the distributed lock. TTL prevents unbounded growth.
🛡️

Idempotency Middleware

Intercepts requests before reaching business logic. Implements the full lifecycle: lookup → lock → delegate → store → respond.

Middleware Pattern Lock Timeout: 10s Retry-After Header
Returns 409 Conflict if a concurrent request is still processing, with a Retry-After header for the client.
🔒

Distributed Lock

Prevents race conditions when two identical requests arrive simultaneously. Only the first acquires the lock; the second waits or gets 409.

Redis SETNX Lock TTL: 30s Fencing Tokens
Lock auto-expires to prevent deadlocks if the holder crashes mid-processing.
📋

Request Fingerprint

Hash of the request body tied to the idempotency key. Detects misuse where the same key is sent with different payloads (returns 422).

SHA-256 Body Hash Mismatch → 422
Prevents accidental key reuse across different operations — a common integration mistake.
🔄

State Machine

Each idempotency record transitions through states: STARTED → PROCESSING → COMPLETED/FAILED. Enables proper handling at each stage.

STARTED PROCESSING COMPLETED FAILED
FAILED state allows retries — only COMPLETED responses are cached and returned to clients.

Idempotency Strategies

Common patterns for implementing idempotency at different layers

1 Idempotency Key in Middleware

The most common approach — a middleware layer checks/stores keys in Redis before delegating to business logic.

async function idempotencyMiddleware(req, res, next) { const key = req.headers['idempotency-key']; const cached = await redis.get(`idem:${key}`); if (cached?.status === 'completed') { return res.json(cached.response); // Return cached } // Acquire lock, process, store result const lock = await redis.setnx(`lock:${key}`, '1', 'EX', 30); if (!lock) return res.status(409).json({...}); next(); // Proceed to handler }
2 Database Unique Constraint

Use the idempotency key as a unique constraint in the database. The DB rejects duplicate inserts atomically.

-- Schema CREATE TABLE payments ( id UUID PRIMARY KEY, idempotency_key VARCHAR(255) UNIQUE, amount DECIMAL, status VARCHAR(20) ); -- Insert (rejects duplicates automatically) INSERT INTO payments (id, idempotency_key, amount) VALUES ($1, $2, $3) ON CONFLICT (idempotency_key) DO NOTHING RETURNING *;
3 Conditional Writes (Optimistic)

Use version numbers or ETags to ensure writes are applied only if the resource hasn't changed since the client last read it.

async function updateBalance(accountId, amount, version) { const result = await db.query(` UPDATE accounts SET balance = balance + $1, version = version + 1 WHERE id = $2 AND version = $3 `, [amount, accountId, version]); if (result.rowCount === 0) { throw new ConflictError('Stale version'); } }
4 Naturally Idempotent Operations

Design operations that are inherently idempotent — setting absolute values rather than relative deltas.

// ❌ NOT idempotent — repeated calls keep adding await account.incrementBalance(100); // ✅ Idempotent — same result no matter how many times await account.setBalance(existingBalance + 100, { transactionId: 'txn_abc123' // dedup key }); // ✅ Idempotent — PUT replaces entire resource await fetch('/api/users/42', { method: 'PUT', body: { name: 'Alice', email: 'a@b.com' } });

Trade-offs & Failure Scenarios

Key decisions and what can go wrong

Short TTL (1h)
vs
Long TTL (48h) — More storage cost but handles slow retries from mobile clients with poor connectivity
Redis (fast, volatile)
vs
Database (durable, slower) — Redis is fast but keys can be lost on restart; DB is authoritative but adds latency
Client-generated keys
vs
Server-generated keys — Client keys enable retry, server keys ensure format but require an extra round trip
Return 409 on lock
vs
Wait and poll — 409 is simpler but pushes retry logic to client; waiting blocks server resources
Per-endpoint idempotency
vs
Global idempotency — Per-endpoint allows key reuse across endpoints; global is simpler but keys can't be shared

🔴 Redis Crashes Mid-Processing

The lock is lost. A retry may trigger duplicate processing. Mitigation: use DB unique constraint as the final safety net.

🟡 Lock Expires Before Completion

Long-running operations outlive the lock TTL. Another request acquires the lock. Mitigation: extend locks with a background heartbeat.

🔵 Clock Skew Between Nodes

TTL-based expiration may behave inconsistently across nodes with drifted clocks. Mitigation: use Redis PEXPIRE (server-side) not client-calculated times.

🟡 Partial Failure (Half-Completed)

Service crashes after charging payment but before storing the response. Retry sees no cached result and charges again. Mitigation: store PROCESSING state before calling downstream.

🔴 Hot Key (Thundering Herd)

Many retries hit the same idempotency key simultaneously. Redis serializes them via SETNX but the first request is still in-flight. Mitigation: return 409 with Retry-After.

🔵 Key Reuse After TTL Expiry

A very delayed retry arrives after the key expired from the store. It's processed as a new request. Mitigation: use DB unique constraints as a durable fallback.
