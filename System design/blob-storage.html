What is Blob Storage?

Binary Large Object (BLOB) storage is a flat-namespace object store designed for unstructured data of any size

📦 Core Concept

Unlike file systems (hierarchical) or databases (structured records), blob storage treats data as opaque objects identified by a key within a flat namespace (bucket/container).

  • Object = data + metadata + unique key
  • Bucket/Container = namespace that groups objects
  • No hierarchy — "/" in keys is a naming convention, not a directory
  • Objects are immutable — you replace, never partially update

🛠 Key Properties

  • Durability: 99.999999999% (11 nines) — data replicated across facilities
  • Scalability: Virtually unlimited — no provisioning needed
  • Availability: 99.9%–99.99% depending on tier
  • Eventual consistency: Reads after writes may be stale (though S3 is now strongly consistent)
  • HTTP API: REST-based access (PUT, GET, DELETE)
  • Pay-per-use: Storage GB + request count + egress bandwidth

📈 Why Not Just Use a File System?

Traditional file systems weren't designed for cloud-scale distributed storage:

  • File systems require mounting — blob storage is HTTP-native
  • File systems have fixed capacity — blob storage auto-scales
  • File systems have single-machine durability — blob storage replicates across AZs
  • File systems have path-length limits — blob keys can be up to 1024 bytes
  • Metadata is limited in FS — blob stores support rich custom metadata

Amazon S3 — Deep Dive

The pioneer and market leader in cloud blob storage, launched in 2006

◈ Key Concepts

  • Bucket — globally unique namespace
  • Object — file + metadata (up to 5TB)
  • Key — unique identifier within bucket
  • Region — geographic location
  • Versioning — keep all versions of objects
  • Lifecycle rules — auto-transition/delete

◈ Consistency Model

Since Dec 2020, S3 offers strong read-after-write consistency for all operations:

  • PUT new object → immediate GET returns it
  • Overwrite PUT → GET returns latest
  • DELETE → GET returns 404
  • LIST reflects all recent changes

No more eventual consistency workarounds!

◈ Access Control

  • IAM Policies — user/role-based access
  • Bucket Policies — resource-based JSON
  • ACLs — legacy, per-object grants
  • Pre-signed URLs — temp access tokens
  • VPC Endpoints — private network access
  • Block Public Access — account-wide safety

◈ Performance

  • 3,500 PUT/s per prefix
  • 5,500 GET/s per prefix
  • Multipart upload for files > 100MB
  • Transfer Acceleration via CloudFront
  • Byte-range fetches for parallel reads
  • S3 Select — query in place (CSV/JSON/Parquet)

◈ Data Protection

  • Versioning — recover from accidental deletes
  • MFA Delete — require MFA to delete versions
  • Object Lock — WORM compliance
  • Replication — cross-region / same-region
  • Encryption — SSE-S3, SSE-KMS, SSE-C

◈ Pricing Model

  • Storage: $0.023/GB/month (Standard)
  • PUT/POST: $0.005 per 1,000 requests
  • GET: $0.0004 per 1,000 requests
  • Data out: $0.09/GB (first 10TB)
  • Data in: FREE
  • No minimum: pay only for what you use

Key Tradeoffs

Every blob storage decision involves fundamental engineering tradeoffs

⚖️ Cost vs. Access Speed

Cheapest (hours to retrieve) Most expensive (instant)

Lower storage cost always means higher retrieval cost or latency. Lifecycle policies help but require accurate access prediction.

🌐 Durability vs. Cost (Redundancy)

Single AZ (cheaper, less durable) Multi-region (expensive, most durable)

One Zone-IA is 20% cheaper but data is lost if an AZ is destroyed. Cross-region doubles cost but survives regional failures.

🔒 Consistency vs. Performance

Eventual (faster, stale reads possible) Strong (slower, always current)

S3's strong consistency came at engineering cost (they rewrote their metadata layer). Some systems still choose eventual consistency for write throughput.

💰 Vendor Lock-in vs. Features

Portable (fewer features) Feature-rich (more lock-in)

S3 has 20+ integrations (Lambda triggers, Athena, Macie, etc.) that tie you to AWS. S3-compatible alternatives let you migrate but sacrifice ecosystem depth.

📥 Object Size: Small vs. Large

Blob stores are optimized for large objects. Small objects (<1KB) incur disproportionate metadata overhead and per-request costs.

  • Small objects: High request cost, metadata overhead, poor throughput
  • Solution: Bundle small objects, use a database for tiny records
  • Large objects: Use multipart upload, byte-range fetches
  • Sweet spot: 1MB–5GB per object for optimal cost/performance

🚀 Latency: First Byte vs. Throughput

Blob storage is optimized for throughput, not latency. First-byte latency is typically 50-200ms.

  • Need low latency? Put a CDN in front, or use a cache (Redis/ElastiCache)
  • Need high throughput? Multipart + parallel connections, Transfer Acceleration
  • Need both? S3 Express One Zone (single-digit ms, 10x throughput, 10x cost)

  • Data sovereignty / on-prem requirement
  • Air-gapped environments (military, government)
  • You want to avoid cloud egress costs entirely
  • Kubernetes-native storage with S3 API
  • Hybrid cloud with S3-compatible tiering

  • Egress costs are your #1 concern
  • You serve data globally and need edge performance
  • You use Cloudflare Workers for compute
  • You want S3 compatibility without AWS lock-in
  • CDN + storage in one (no separate CDN needed)

Choose Backblaze B2 when...

  • Budget is the #1 priority
  • Backup/archival is the primary use case
  • You pair with Cloudflare CDN (free egress between them)
  • Simple workloads that don't need advanced features

How Blob Storage Works Internally

The engineering principles that enable 11 nines of durability

💾 Erasure Coding

Instead of storing 3 full copies (3x overhead), erasure coding splits data into k data chunks + m parity chunks. Any k of k+m chunks can reconstruct the original.

// Example: Reed-Solomon (10,4) — 10 data + 4 parity Original file: 10 MB Split into: 10 × 1MB data chunks Generate: 4 × 1MB parity chunks Total stored: 14 MB (1.4x overhead vs 3x for replication) // Can lose ANY 4 of 14 chunks and still recover // S3 uses a variant of this for cold storage classes

🛠 Consistent Hashing

Maps object keys to storage nodes in a way that minimizes data movement when nodes are added/removed.

// Hash ring with virtual nodes hash("object-key") → position on ring → node Node A: [0°, 90°) ← owns 25% of keyspace Node B: [90°, 180°) Node C: [180°, 270°) Node D: [270°, 360°) // Adding Node E: only ~20% of data moves // vs. naive hash: ~80% would move

📈 Metadata Layer

The metadata layer maps keys to physical locations. This is the hardest scaling challenge — S3 stores trillions of objects.

// Metadata per object (simplified) { key: "photos/sunset.jpg", version_id: "v3", size: 3145728, chunks: [ {node: "az1-r3-n7", offset: 0x4F200}, {node: "az2-r1-n2", offset: 0x8A100}, {node: "az3-r5-n4", offset: 0x1C800} ], checksum: "sha256:ab4f...", storage_class: "STANDARD" } // Stored in a distributed DB (like DynamoDB internally)

🔧 Multipart Upload

Large objects are split into parts, uploaded in parallel, then assembled server-side. Enables resumable uploads and parallel throughput.

// Multipart upload flow 1. CreateMultipartUpload → uploadId 2. UploadPart(uploadId, partNum=1, data) → ETag1 UploadPart(uploadId, partNum=2, data) → ETag2 ... (parallel, up to 10,000 parts) 3. CompleteMultipartUpload(uploadId, parts[]) // Part sizes: 5MB min, 5GB max // Max object: 5TB (10,000 × 5GB) // Failed part? Just re-upload that part
