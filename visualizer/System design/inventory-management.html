Comparisons with Alternatives

Different approaches to inventory tracking and why we chose event-sourced, write-ahead stock management.

Approach Key Idea Pros Cons Best For
Event-Sourced Ledger Chosen Every stock change is an immutable event; current count derived from event stream Full audit trail, temporal queries, easy debugging, natural fit for CQRS Higher storage, complex read-side projections, eventual consistency on reads Large-scale e-commerce with strict auditing needs
Simple Counter (UPDATE stock SET qty = qty - 1) Direct mutable counter in a relational table; every sale decrements in-place Dead simple, strong consistency with row locks, minimal storage No history, lost updates under contention, hard to debug discrepancies Small shops, <100 orders/min
Reservation / Soft-Lock Reserve stock at cart-add; commit on checkout; release on timeout Prevents oversell without payment, great UX for flash sales Complexity of TTLs, phantom stock when users abandon carts Ticket sales, limited-edition drops
Distributed Counter (Redis DECR) In-memory atomic counter per SKU; async sync back to DB Extremely fast writes, handles spikes well Data loss risk on crash, eventual consistency with persistent store High-QPS flash sales, used as front-line with DB backup

When to Pick Each

  • Event-Sourced Ledger when you need an audit trail, multi-warehouse, or regulatory compliance
  • Simple Counter when speed-to-market matters and scale is small
  • Reservation Model when overselling is catastrophic (concerts, drops)
  • Distributed Counter as a front-line defense during traffic spikes, backed by a durable store

Real-World Examples

  • Amazon — event-sourced, multi-warehouse with regional stock pools
  • Shopify — hybrid counter + event log per location
  • Ticketmaster — reservation model with hard TTLs per seat
  • Alibaba (Double 11) — Redis DECR front-line, MySQL back-end

Use Cases & Common Pitfalls

Where inventory systems shine — and where engineers typically make mistakes.

Primary Use Cases

🛒

E-Commerce Marketplace

Multi-seller platform tracking millions of SKUs across warehouses. Expect 10K-100K orders/min during peaks. Needs real-time stock visibility and oversell prevention.

🎫

Ticket / Event Booking

Fixed-supply inventory (seats, rooms, slots). Zero tolerance for overselling. Reservation-with-TTL pattern dominates. Typically 1K-50K concurrent users at on-sale.

🏭

Omnichannel Retail

Unified view of stock across physical stores, warehouses, and online channels. Ship-from-store, BOPIS (buy online pick up in store). Reconciliation is the hard problem.

📦

Warehouse Management (WMS)

Bin-level tracking, pick/pack/ship workflows. Integrates barcode/RFID scanning. Needs location-aware stock and cycle count reconciliation.

🍮

Grocery / Perishable Goods

Stock with expiry dates, lot tracking, FIFO enforcement. Must handle shrinkage, spoilage, and partial fulfillment. Freshness is a dimension of availability.

⛔

Anti-Use-Case: Digital Goods

Unlimited-supply digital products (downloads, subscriptions) don't need inventory tracking. Use entitlement/license management instead of stock counts.

Scaling Strategies

10x Growth

Horizontal Scaling
  • Shard inventory DB by SKU hash
  • Add Redis read replicas for stock queries
  • Scale Inventory Service stateless pods behind LB
  • Partition event stream by warehouse ID

100x Growth

Architecture Evolution
  • Regional stock pools with geo-aware routing
  • CQRS: separate write store (event log) and read store (materialized views)
  • Pre-computed stock snapshots at edge (CDN-cached quantities with short TTL)
  • Tiered consistency: eventual for browse, strong for checkout

Trade-off Analysis

Failure Scenarios

⚠ Inventory DB Down

Redis cache serves stale stock counts (read-only mode). Writes queue in Kafka. On recovery, replay events to reconcile. Risk: overselling during outage if cache shows positive stock that's actually sold out.

⚠ Redis Cache Crash

Fall back to direct DB reads. Latency spikes from p2ms to p50ms. Activate circuit breaker to shed non-critical stock checks (e.g., PLP counts). Critical path (checkout) always reads from DB if cache misses.

⚠ Event Bus (Kafka) Down

Inventory updates can't propagate to read models. Write to local WAL and retry. Stock counts on read side become stale. Alerting triggers, and manual reconciliation batch runs on recovery.

⚠ Network Partition (Multi-Region)

Each region operates on its local stock pool. Cross-region transfers freeze. Risk of same item sold from two regions. On heal: conflict resolution via last-write-wins or manual review for oversold items.
