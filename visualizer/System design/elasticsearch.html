Elasticsearch

A distributed, RESTful search and analytics engine built on Apache Lucene. Designed for horizontal scalability, near real-time search, and multi-tenancy.

Component Breakdown

Key components and their roles in the Elasticsearch ecosystem

Coordinating Node

The gateway for all client requests. Parses queries, identifies target shards via routing, scatters requests to data nodes, gathers partial results, and performs final reduction (sorting, aggregation merge).

Stateless CPU-bound

Master Node

Manages cluster metadata: index settings, mappings, shard allocation table, node membership. Elected via Raft-like consensus. Should be dedicated (3+ nodes) and never hold data in production.

Cluster State Lightweight

Data Node (Hot/Warm/Cold)

Stores shard data on local disk, executes search and indexing operations. Hot tier uses SSDs for recent writes; warm tier for read-heavy older data; cold/frozen for archives with searchable snapshots.

I/O Heavy Memory Critical

Ingest Node

Runs ingest pipelines — ordered sequences of processors (grok parsing, date extraction, GeoIP lookup, script transforms) — on documents before they reach the indexing stage.

Pre-processing Extensible

Shard (Primary + Replica)

Each index is divided into primary shards (default 1). Each primary has configurable replicas (default 1). Primary handles writes; replicas serve reads and provide failover. Rebalanced on node join/leave.

Lucene Instance Replicable

Lucene Engine

Each shard wraps a Lucene index: immutable segments containing inverted index (term→doc mapping), BKD trees (numerics/geo), doc values (columnar), stored fields. Segments merge in background for efficiency.

Inverted Index Segment Merge

Translog

Write-ahead log ensuring durability between Lucene commits. Every index/delete/update is appended to the translog. On crash recovery, uncommitted operations are replayed from the translog.

Durability WAL

Cluster State

Single source of truth for the cluster: index metadata, shard routing table, node membership, templates, pipelines, and ILM policies. Published by the master node and synced to all nodes.

Centralized Replicated

When to Pick Each

Choose Elasticsearch when...

You need full-text search AND analytics on the same data. Complex queries with fuzzy matching, geo-spatial, nested objects. Observability/logging at scale. Rich ecosystem matters (Kibana, Beats, ML).

Choose ClickHouse when...

Your workload is purely analytical — GROUP BY, time-series rollups, funnel analysis. You don't need full-text search. You want SQL and petabyte-scale columnar performance at lower cost.

Choose Meilisearch/Typesense when...

You need instant, typo-tolerant search for a product catalog or documentation site. Dataset fits in RAM on one machine. Developer experience and simplicity outweigh enterprise features.

Choose OpenSearch when...

You're on AWS and want managed service without Elastic licensing concerns. Need ES-compatible APIs but prefer Apache 2.0 license. Running in regulated environments requiring open-source guarantees.

Use Cases & Common Pitfalls

Primary Use Cases

Centralize logs from thousands of services. Full-text search across billions of log lines with sub-second response. Kibana dashboards for real-time monitoring.

~100K-1M events/sec

Product / E-Commerce Search

Faceted search with filters (price, category, brand), fuzzy matching for typos, boosting by relevance and popularity, autocomplete suggestions.

~1K-50K QPS

Power search bars for SaaS apps, documentation sites, knowledge bases. Highlight matching terms, filter by metadata, rank by freshness.

~100-10K QPS

Correlate security events across firewalls, endpoints, and cloud. Detect anomalies with ML. Alert on threat patterns. Elastic Security / SIEM solution.

~50K-500K events/sec

Distributed tracing, metrics, and logs unified in one platform. Correlate traces with logs. Service maps. Elastic APM agents instrument code automatically.

Traces + Metrics + Logs

Geo-Spatial Search

Find locations within bounding boxes, radius queries, geo-polygon filters. Power "near me" features, delivery zone matching, and mapping applications.

Geo queries

Anti-Use-Cases

Primary Database (OLTP)

No ACID transactions, no joins, eventual consistency. Don't use ES as your source of truth for transactional data. Use a proper RDBMS and sync to ES.

Frequent Updates to Same Docs

ES does delete+reindex on every update (immutable segments). Write-heavy update patterns cause massive I/O. Use a database with in-place updates instead.

Exact BI / Aggregation (Large Scale)

Aggregations are approximate at scale (HyperLogLog for cardinality). For exact counts on petabytes or complex joins, use a columnar DB like ClickHouse or BigQuery.

Simple Key-Value Lookups

If you only need get-by-ID without search, Redis or DynamoDB is faster and cheaper. ES overhead (inverted index, segments) adds no value here.

Scaling Strategies

Horizontal Scaling (Add Nodes)

Add data nodes and ES automatically rebalances shards. No downtime. Works well until shard count gets too high (10K+ shards = master bottleneck). Use ILM to rollover indices and control shard growth.

PreferredAuto-rebalance

Data Tiering (Hot/Warm/Cold/Frozen)

ILM policies automatically move indices through tiers. Hot: fast SSDs for writes. Warm: read-only on cheaper storage. Cold: reduced replicas. Frozen: searchable snapshots from S3 (no local storage).

Cost OptimizeILM

Index Partitioning (Time-Based)

Use date-based indices (logs-2024.01.15) with rollover. Old indices shrink, force-merge to 1 segment, and move to warm. Enables efficient deletion (drop whole index vs. delete-by-query).

Time SeriesEfficient Deletes

Cross-Cluster Search (CCS)

Federate searches across multiple independent clusters. Each cluster is autonomous. Useful for geographic distribution, team isolation, or very large deployments exceeding single-cluster limits.

Multi-RegionFederation

Fundamental Trade-offs

Indexing Speed vs. Search Latency

Faster refresh_interval (default 1s) means more segments = more I/O during search. Increase to 30s-60s for write-heavy workloads. Disable replicas during bulk loads, re-enable after.

Relevance vs. Performance

Complex queries (multi-match with fuzziness, nested, function_score) are expensive. Simple queries on keyword fields are fast. Profile queries and consider pre-computing signals at index time.

Availability vs. Consistency

ES favors availability (AP in CAP). During network partitions, reads may return stale data. write_consistency and wait_for_active_shards give tunable durability at the cost of availability.

Storage Cost vs. Query Speed

Frozen tier (searchable snapshots) cuts storage cost 90%+ but first queries are slow (fetch from S3). Best for data you rarely access but must keep searchable for compliance.

Failure Scenarios

Data Node Failure

Replica shards on surviving nodes promote to primary. Cluster goes YELLOW until new replicas are allocated. If all copies of a shard are lost, that shard's data is gone. Configure allocation awareness for rack/zone distribution.

Master Node Failure

Remaining masters elect a new master (requires quorum: N/2+1). During election (~seconds), no cluster state changes (no new index creation, no shard movement). Reads and writes to existing shards continue unaffected.

Split Brain (Prevented)

ES 7+ uses a voting configuration that prevents split brain by design. Before 7.x, misconfigured discovery.zen.minimum_master_nodes caused dual masters and data corruption.

Disk Full / Circuit Breaker

At 85% disk, new shards won't allocate. At 90%, shards relocate away. At 95%, indices go read-only. Circuit breakers protect against OOM by rejecting requests exceeding heap thresholds.
