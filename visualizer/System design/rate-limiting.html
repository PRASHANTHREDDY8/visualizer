Rate Limiting Algorithms

Four fundamental algorithms power rate limiting. Each has different trade-offs in accuracy, memory usage, and burst handling. Click an algorithm to see it in action.

🎂

Token Bucket

Tokens added at fixed rate. Each request consumes a token. Allows bursts up to bucket capacity.

Burst Friendly Low Memory Most Popular
📋

Sliding Window Log

Tracks exact timestamp of each request. Counts requests in a rolling time window.

Most Accurate High Memory Expensive
📅

Fixed Window Counter

Divides time into fixed windows. Counts requests per window. Simple but has boundary spike issue.

Simple Low Memory Boundary Issue
💧

Leaky Bucket

Requests enter a FIFO queue processed at fixed rate. Smooths out bursts into steady flow.

Smooth Output No Burst Queue-based

📦 Components

Component Breakdown

Key components of a production rate limiting system and the technology choices behind them.

■ Rate Limiter Middleware

Intercepts every request and enforces rate limit rules before it reaches business logic.

TechnologyCustom middleware in API Gateway (Kong, Envoy, or app-level)
Key DecisionToken Bucket for APIs (allows burst), Leaky Bucket for webhooks (smooth rate)
ScalingStateless — all state in Redis. Horizontally scales with gateway replicas.

■ Redis Counter Store

Stores per-key counters, token counts, and sliding window timestamps with sub-ms latency.

TechnologyRedis 7+ with Lua scripts for atomic check-and-increment
Key DecisionLua scripts ensure atomicity — MULTI/EXEC has race conditions under load
ScalingRedis Cluster with hash-slot sharding by user/key ID. Replicas for read-heavy patterns.

■ Rule Configuration

Defines rate limit rules per tier, endpoint, and user. Hot-reloadable without deploys.

TechnologyConfig stored in DB, cached in Redis with pub/sub invalidation
Key DecisionHierarchical rules: global → tier → user override. Most specific wins.
ScalingConfig rarely changes — aggressive caching. Pub/sub for instant propagation.

■ Response Headers & Feedback

Communicates rate limit state to clients via standard HTTP headers for adaptive behavior.

HeadersX-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, Retry-After
Key DecisionUse IETF draft standard headers. Include Retry-After on 429 responses.
Client SDKsSDKs should implement exponential backoff with jitter using Retry-After.

🚀 Scaling Strategies

  • Redis Cluster — shard by user/key hash. Each shard handles ~50K ops/sec.
  • Local cache + sync — cache counters locally, sync to Redis periodically. Trades accuracy for speed.
  • Multi-region — each region has its own Redis. Global limits use eventual consistency or a coordination service.
  • Tiered approach — rough IP-based limits at edge, precise per-user limits at gateway.
  • Graceful degradation — if Redis is down, fail open (allow) or fail closed (deny) based on risk tolerance.

⚠️ Failure Scenarios

  • Redis down — fail open with local in-memory approximation. Log for alerting.
  • Clock skew — use Redis server time (TIME command), not local clocks, for window calculations.
  • Race conditions — Lua scripts in Redis ensure atomic read-check-update. Avoid MULTI/EXEC.
  • Hot keys — celebrity/viral user. Pre-shard their key or use local rate limiting.
  • Config push failure — stale rules. Use TTL-based fallback to last-known-good config.

Key Trade-offs

Accuracy vs. Performance

Sliding window log is exact but O(n) memory per user. Token bucket is O(1) and fast but allows bursts. Choose based on your precision requirements.

Centralized vs. Distributed

Centralized (single Redis) is simple and accurate. Distributed (per-node) is faster but allows temporary over-limit. Most systems use centralized for critical APIs.

Fail Open vs. Fail Closed

If the rate limiter is down — allow all requests (fail open, risk overload) or deny all (fail closed, risk availability). Most choose fail open with monitoring.

User Experience vs. Protection

Aggressive limits protect infrastructure but frustrate users. Use tiered limits, burst allowances, and clear 429 responses with Retry-After to balance both.
