Content Delivery Network

A globally distributed network of edge servers that cache and serve content close to users, reducing latency from hundreds of milliseconds to single digits.

Architecture Diagram

Component Breakdown

☍
Edge PoP (Point of Presence)
A physical datacenter location with CDN servers. Contains cache storage (RAM + SSD), reverse proxies, and TLS termination. Positioned near population centers to minimize round-trip time.
Nginx / Varnish ~5ms latency 300+ global
📦
Edge Cache
Two-tier caching: hot objects in RAM (L1), warm objects on NVMe SSD (L2). Uses LRU eviction with TTL-based expiry. Cache keys include URL, headers, query params, and cookies (configurable).
LRU + TTL TB-scale per PoP
🌍
DNS / Anycast Routing
Routes users to nearest PoP via GeoDNS (CNAME records) or BGP Anycast (same IP announced from multiple PoPs). Anycast gives automatic failover if a PoP goes down.
GeoDNS BGP Anycast Auto-failover
🛡
Origin Shield / Mid-Tier
A regional cache layer between edge and origin. Collapses multiple cache-miss requests from different PoPs into one origin fetch. Protects origin from thundering herd.
Request collapsing Regional (5-10)
🔄
Cache Invalidation
Purge stale content globally. Methods: instant purge by URL/tag, soft-purge (serve stale while revalidating), or TTL-based expiry. Propagation takes 1-5 seconds globally.
Purge API Surrogate keys Stale-while-revalidate
⚡
Edge Compute
Run custom logic at the edge (Cloudflare Workers, Lambda@Edge, Fastly Compute). Enables A/B testing, auth, redirects, header manipulation without hitting origin.
V8 Isolates <1ms cold start 150+ PoPs

Comparisons with Alternatives

ApproachHow it WorksProsConsBest For
Pull-based CDN
MOST COMMON		 Edge fetches from origin on first request, then caches. Subsequent requests served from cache. Simple setup, auto-populates cache, no push infrastructure needed First request is slow (cache miss), thundering herd on cold start Web apps, APIs, general content. (CloudFront, Cloudflare, Fastly)
Push-based CDN Origin proactively pushes content to all edge nodes before users request it. Zero cache misses for known content, predictable latency Requires origin to know what to push, storage cost at every PoP, complex sync Video streaming (Netflix Open Connect), large file distribution, game patches
Multi-CDN Use multiple CDN providers simultaneously; route based on performance or cost. No vendor lock-in, resilience if one CDN fails, optimize cost/performance per region Complex routing logic, cache fragmentation, higher operational cost Large enterprises, live streaming, global SaaS (Apple, Microsoft)
P2P CDN Users serve content to each other via WebRTC; CDN seeds initial copies. Scales with audience size, reduces bandwidth cost dramatically Inconsistent quality, privacy concerns, only works for popular content Live streaming spikes, large-scale video events (Peer5, Streamroot)

When to pick each

Pull CDN — Default choice. Works for 90% of use cases. Start here unless you have a specific reason not to.
Push CDN — When you know exactly what content will be requested and cache misses are unacceptable (video catalogs, firmware updates).
Multi-CDN — When availability > 99.99% is required, or you serve 100+ countries and no single provider covers all well.
P2P — Live events with predictable massive concurrent viewers (sports, concerts). Saves 60-80% bandwidth at peak.

Real-world examples

Netflix: Push-based (Open Connect appliances in ISP datacenters) + pull CDN (AWS CloudFront for API/images)

Cloudflare: Pure pull with Anycast — same IP everywhere, automatic geo-routing

Akamai: Pull CDN + Tiered Distribution (origin shield equivalent)

Apple: Multi-CDN strategy — uses Akamai, Fastly, Cloudflare depending on region and content type

Use Cases & Pitfalls

Primary Use Cases

🌐
Static Asset Delivery
Images, CSS, JS, fonts. Massive bandwidth savings. 95%+ cache hit ratio typical. Foundation of every modern website.
🎥
Video Streaming (VOD & Live)
HLS/DASH segments cached at edge. Adaptive bitrate. 4K video needs ~25 Mbps — CDN handles millions of concurrent streams.
🚀
API Acceleration
Cache GET responses with short TTLs (5-60s). Edge compute for auth/rate-limiting. TLS handshake savings alone cut 100ms.
🔒
DDoS Protection
Absorb volumetric attacks across globally distributed infrastructure. 100+ Tbps capacity. Origin IP hidden behind CDN.
🗺
Software Distribution
OS updates, game patches, app binaries. Terabytes pushed to millions of users simultaneously. Pre-positioned at edge.
📊
E-commerce / Retail
Product images, personalized content at edge, cart API caching. Every 100ms latency reduction = 1% revenue increase.

Anti-Use Cases

❌
Highly Personalized Content
If every response is unique per user (personalized feeds), CDN cache hit ratio approaches 0%. Use edge compute instead.
❌
Real-time WebSockets
Persistent bidirectional connections bypass CDN caching entirely. Use dedicated WebSocket infrastructure (Pusher, Ably).
❌
Intranet / Private Apps
If all users are in one office/VPN, a CDN adds unnecessary hops. Serve directly from regional infrastructure.
Not varying cache key on critical headers ▶

The mistake: Caching a response that varies by Accept-Encoding, Accept-Language, or auth state without including those in the cache key.

Why it happens: Default CDN configs cache by URL only. Works in dev where all requests are identical.

The consequence: Users get wrong content — gzipped served to clients that don't support it, English served to French users, admin content served to regular users.

The fix: Explicitly set Vary headers. Configure CDN cache key to include necessary headers. Test with different client configurations.

Cache stampede / thundering herd on TTL expiry ▶

The mistake: Setting the same TTL on popular content across all PoPs. When it expires, hundreds of PoPs simultaneously hit origin.

Why it happens: Uniform TTLs are simple. The problem only manifests at scale during traffic spikes.

The consequence: Origin gets overwhelmed. Latency spikes for all users. Potential cascade failure.

The fix: Use stale-while-revalidate to serve stale content while fetching fresh. Enable request coalescing / origin shield. Add jitter to TTLs.

Caching responses with Set-Cookie headers ▶

The mistake: Not stripping Set-Cookie from cacheable responses. CDN caches the response including cookies meant for one user.

Why it happens: Application sets cookies on all responses (analytics, sessions) without CDN awareness.

The consequence: Session hijacking — User A gets User B's session cookie from cache. Major security vulnerability.

The fix: Never cache responses with Set-Cookie. Strip cookies in CDN config for static assets. Separate cookie-setting endpoints from cacheable content.

Over-aggressive cache-busting destroying hit ratio ▶

The mistake: Adding timestamps or random query params to every asset URL, or setting TTL=0 / no-cache on everything "just to be safe."

Why it happens: Fear of serving stale content. Developer burned by caching bug once, now disables caching everywhere.

The consequence: CDN becomes an expensive proxy with 0% hit rate. Origin bears full load. Paying for CDN with no benefit.

The fix: Use content-hash-based filenames for assets (webpack does this). Set long TTLs (1 year) on hashed assets. Use short TTLs + stale-while-revalidate for HTML.

Not accounting for cache inconsistency across PoPs ▶

The mistake: Assuming all users see the same version immediately after deployment. Different PoPs have different cache states.

Why it happens: Works on single-server setups. CDN's distributed nature means eventual consistency.

The consequence: User in NYC sees new version, user in Tokyo sees old version. Broken if new HTML references new JS that old PoP hasn't cached yet.

The fix: Version all assets with content hashes. Deploy assets first, HTML second. Use instant purge + pre-warm for critical updates. Embrace immutable URLs.

Best Practices

Use immutable URLs with content-hash filenames
app.a1b2c3.js — set Cache-Control: max-age=31536000, immutable. New deploys generate new hashes. Zero purge needed for assets. 99%+ hit rate.
Implement stale-while-revalidate for HTML
Cache-Control: max-age=60, stale-while-revalidate=300 — Users always get fast responses (stale or fresh). Background revalidation keeps content fresh without latency cost.
Enable origin shield (mid-tier cache)
Collapses cache misses from 300 PoPs into 1 origin request. Reduces origin load by 90%+ during cold starts or purges. Essential for origin protection.
Monitor cache hit ratio as a top-level metric
Target: 95%+ for static, 80%+ for dynamic. If ratio drops, investigate: bad Vary headers, cookies leaking, query param pollution, or TTLs too short.
Use surrogate keys for targeted purging
Tag responses with surrogate keys (e.g., product-123, category-shoes). Purge by tag instead of URL patterns. Faster, more precise, fewer stale pages.
Compress at the edge, not just origin
Enable Brotli (20-30% smaller than gzip). CDN can compress on-the-fly per Accept-Encoding. Cache both compressed and uncompressed variants.
Implement proper cache hierarchy
Browser cache (seconds-minutes) → Edge PoP (minutes-hours) → Shield (hours-days) → Origin. Each tier reduces load on the next. Don't skip tiers.
Use edge compute for personalization
Instead of making content uncacheable, cache the template and personalize at edge. A/B tests, geo-targeting, and feature flags without origin round-trips.

Trade-offs Key Decisions

Freshness vs. Performance
Short TTLs = fresher content but more origin hits. Long TTLs = fewer origin hits but staler content. Use stale-while-revalidate to get both.
Cache Hit Ratio vs. Personalization
More cache key variants = more personalized but lower hit ratio. Solution: edge compute to personalize cached templates.
Consistency vs. Availability
Instant global purge is hard. Some PoPs will serve stale content for seconds after purge. Accept eventual consistency or use versioned URLs.
Cost vs. Coverage
More PoPs = lower latency everywhere but higher cost. Focus PoPs in regions where your users actually are. Don't pay for Africa PoPs with 0 traffic.

Estimation Back-of-Envelope

Scenario: 10M DAU, average page loads 30 assets (images/JS/CSS), each ~100KB

Daily bandwidth: 10M users x 30 assets x 100KB = 30 TB/day (without CDN cache)

With 95% hit ratio: Origin serves only 5% = 1.5 TB/day. CDN absorbs 28.5 TB.

Peak QPS: 10M DAU → ~115 req/s average → ~1,000 req/s peak (8-10x). CDN absorbs 950 req/s, origin sees 50.

Cost saving: CDN bandwidth ~$0.02-0.08/GB vs. origin compute + bandwidth for same traffic = typically 60-80% cost reduction.

Failures What Happens When...

Single PoP fails: Anycast reroutes to next-nearest PoP. Users see slightly higher latency (20-50ms more). Automatic, no intervention needed.

Origin goes down: CDN serves stale cached content (if stale-if-error configured). Uncacheable requests fail. Origin shield reduces blast radius.

DNS failure: Users can't resolve CDN domain at all. Complete outage. Mitigate with low DNS TTLs and multiple DNS providers.

Cache poisoning: Attacker caches malicious response at edge. Affects all users until TTL expires or purge. Validate origin responses, sign content.
