Comparisons with Alternatives

How Stripe's approach compares to other payment architectures.

Approach Key Idea Pros Cons Used By
Payment Intent + Two-PhaseSTRIPE Create intent → authorize → capture as separate steps with idempotency Supports SCA/3DS, flexible capture timing, built-in retry safety More API calls, higher integration complexity Stripe, Adyen
Direct Charge (Single API call) One call to charge the card immediately Simple integration, fewer round trips No SCA support, no auth-then-capture, hard to handle 3DS Legacy PayPal, Braintree (old API)
Hosted Payment Page Redirect user to processor's hosted page Minimal PCI scope, processor handles UI Less control over UX, redirect friction, limited customization PayPal Checkout, Mollie
Orchestration Layer (Multi-PSP) Route payments through multiple processors via abstraction layer Failover, optimized routing, rate shopping Massive complexity, reconciliation challenges, higher latency Large merchants (Uber, Airbnb)

When to pick each

Payment Intent (Stripe-style)

When you need SCA compliance, flexible capture timing, subscription billing, or marketplace payouts. Best for most modern applications.

Direct Charge

When operating in regions without SCA, processing simple one-time charges, or building an MVP with minimal payment complexity.

Hosted Page

When PCI compliance is a blocker, you have a small team without frontend resources, or you're in a heavily regulated market.

Multi-PSP Orchestration

When processing $100M+/year, operating in 10+ countries, or needing sub-1% downtime guarantees via failover.

Use Cases & Common Pitfalls

Where this architecture applies, and the mistakes engineers make building it.

Primary Use Cases

E-Commerce Platform

Online stores processing card payments with auth+capture for shipping delays. Supports multi-currency and marketplace splits.

1K–1M txn/day

SaaS Subscription Billing

Recurring charges with dunning, proration, usage metering. Payment intents handle card updates and retry logic.

10K–500K subscribers

Marketplace / Platform

Split payments between platform and sellers. Connected accounts, instant payouts, and 1099 reporting.

100K+ sellers

On-Demand / Gig Economy

Pre-auth at booking, capture at completion, tip adjustment. Handle disputes for service quality.

10K–1M txn/day

Anti-Use-Cases

Crypto / Blockchain Payments

Traditional card rails don't apply. Use purpose-built crypto payment infra (Coinbase Commerce, BitPay) instead.

High-Frequency Trading Settlements

Latency requirements (microseconds) are incompatible with card network round-trips. Use FIX protocol and direct bank settlement.

Peer-to-Peer Transfers (Social)

For Venmo-like transfers between individuals, use ACH/RTP rails directly rather than card-based payment intents.

Scaling & Trade-offs

Capacity planning, growth strategies, and failure modes.

Capacity Estimation (Stripe-scale)

  • ~500M+ API requests/day
  • ~thousands of payments/second at peak
  • ~$1T+ annual payment volume
  • P99 latency target: <300ms for payment creation
  • Storage: petabytes of transaction and audit logs

Horizontal Scaling Strategy

  • Stateless API servers behind global load balancers
  • Database sharding by merchant_id (even load distribution)
  • Event-driven async processing for non-critical paths
  • Read replicas for reporting and analytics queries
  • Edge caching for idempotency key lookups

Trade-offs

  • Consistency over availability for payment state (CP in CAP)
  • Latency vs. fraud: more checks = safer but slower
  • Flexibility vs. simplicity: PaymentIntent API is complex but powerful
  • Multi-region vs. data residency: EU data must stay in EU

Failure Scenarios

  • Card network timeout → retry with idempotency key
  • Database failure → queue payments, process when recovered
  • Webhook delivery fails → exponential backoff + manual retry UI
  • Fraud service down → fail-open with elevated monitoring
  • Region outage → DNS failover to secondary region
