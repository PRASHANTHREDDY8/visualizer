Component Breakdown

WebSocket Gateway

Purpose: Maintains millions of persistent connections with clients.

Tech: Erlang/Elixir (WhatsApp's actual choice) — lightweight processes handle 2M+ connections per server.

Scaling: Horizontal. Each server holds ~2M connections. Consistent hashing maps users to servers.

Chat Service

Purpose: Routes messages between sender and recipient(s), manages delivery receipts.

Tech: Erlang with custom XMPP-based protocol for low-overhead message framing.

Key Decision: Store-and-forward model — messages queued until recipient connects, then deleted from server.

Presence Service

Purpose: Real-time online/offline/typing status.

Tech: In-memory Redis with pub/sub for broadcasting status changes to contacts.

Trade-off: Eventually consistent — slight delay is acceptable for presence info.

Group Service

Purpose: Manages groups (up to 1024 members), handles fan-out of messages.

Tech: Dedicated service with group metadata in MySQL, fan-out via message queue.

Scaling: Fan-out-on-write for small groups, fan-out-on-read for broadcast lists.

Media Service

Purpose: Upload, transcode, thumbnail generation, and encrypted storage of media.

Tech: Media encrypted client-side with random AES key. Server stores ciphertext in S3, URL sent in message.

Scaling: CDN for downloads, separate upload endpoints to avoid blocking chat traffic.

Key Service (E2E Encryption)

Purpose: Manages Signal Protocol key exchange without accessing plaintext.

Tech: Stores public identity keys, signed pre-keys, and one-time pre-keys per device.

Key Decision: Server is untrusted — only facilitates key exchange, never holds private keys.

Message Store (Cassandra)

Purpose: Transient storage for undelivered messages.

Tech: Cassandra with partition key = recipient_user_id, clustering key = timestamp.

Key Decision: Messages deleted after delivery — server is a mailbox, not an archive.

Session Cache (Redis)

Purpose: Maps user IDs to their current WebSocket server for O(1) message routing.

Tech: Redis Cluster with replication. TTL-based expiry on disconnect.

Scaling: Partitioned across Redis nodes by user ID hash.

Comparisons with Alternatives

Approach Key Difference Pros Cons Used By
XMPP + Custom Protocol (WhatsApp) Lean binary protocol over persistent TCP/WebSocket Minimal bandwidth, 2M connections/server, proven at scale Custom protocol = harder to debug, Erlang expertise required WhatsApp
MQTT-based Pub/sub messaging protocol designed for IoT Lightweight, well-documented, QoS levels built-in Not optimized for chat UX (typing, read receipts), limited group support Facebook Messenger (originally)
HTTP Long Polling Client polls server repeatedly for new messages Simple to implement, works through all firewalls/proxies High latency, wastes bandwidth, poor battery life on mobile Early web chat apps
gRPC Streaming Bidirectional streams over HTTP/2 Strong typing (protobuf), multiplexing, excellent tooling Higher overhead than raw TCP, complex reconnection logic Discord, Slack (internal)

When to Pick Each

Choose XMPP/Custom when...

You need extreme efficiency at massive scale (billions of messages/day), can invest in custom infrastructure, and mobile battery life is critical.

Choose MQTT when...

Building IoT-adjacent messaging, need simple pub/sub with QoS guarantees, and the team is small.

Choose gRPC Streaming when...

Building a chat feature within a larger microservices ecosystem, need strong contracts, and the client base is primarily desktop/web.

Use Cases & Common Pitfalls

Primary Use Cases

Consumer Messaging App

1:1 and group chat with media sharing, read receipts, and real-time presence. Scale: 100M-2B users, 100B+ messages/day.

WhatsApp's core use case

Enterprise Team Chat

Internal communication with channels, threads, file sharing. Needs audit logging and compliance (message retention).

Slack / Teams pattern

Customer Support Chat

Real-time chat between customers and agents with routing, queue management, and bot integration.

Intercom / Zendesk

Gaming Chat

Low-latency messaging in game lobbies, voice channel signaling, ephemeral messages.

Discord pattern

Anti-Use-Cases

Broadcast-Only (1-to-millions)

If there's no reply path, use a push notification system or pub/sub (Kafka + SSE), not a full chat architecture.

Async Email-Like Messaging

If latency tolerance is hours (not seconds), a simpler queue + inbox model is far cheaper to operate.

Common Pitfalls

Caution
Not handling message ordering in distributed systems

The mistake: Assuming messages arrive in send order when routed through multiple servers.

Why it happens: Works in dev with one server; breaks under load with multiple chat servers and network jitter.

Consequence: Messages appear out of order — "Yes" arrives before "Want to grab lunch?"

Fix: Use Lamport timestamps or vector clocks. WhatsApp uses server-assigned monotonic IDs per conversation. Client reorders by this ID before displaying.

Treating group messages like N individual messages

The mistake: Sending a group message as N separate 1:1 messages from the sender to each member.

Why it happens: Simplest mental model — and works for small groups.

Consequence: A 1024-member group message creates 1024x write amplification. Sender uploads media 1024 times.

Fix: Fan-out-on-write at the server level. Store the message once, create delivery records per recipient. Media uploaded once, URL shared.

Ignoring the "thundering herd" on reconnection

The mistake: All clients reconnect simultaneously after a server restart or network blip.

Why it happens: Clients use fixed retry intervals (e.g., always retry after 1s).

Consequence: Server gets slammed with millions of simultaneous connection attempts, cascading failure.

Fix: Exponential backoff with jitter. Clients add random delay: base_delay * 2^attempt + random(0, base_delay).

Storing messages permanently on the server

The mistake: Keeping all messages forever server-side "for sync."

Why it happens: Enables easy multi-device sync and message history.

Consequence: Storage costs grow unbounded. Privacy/compliance risk. Becomes a high-value target for attacks.

Fix: WhatsApp model: delete from server after delivery. Client is source of truth. Multi-device sync uses encrypted backup + local transfer protocol.

Skipping end-to-end encryption for "MVP"

The mistake: Planning to "add E2E encryption later" after launch.

Why it happens: E2E encryption adds complexity (key management, multi-device, group key rotation).

Consequence: Retrofitting E2E encryption requires redesigning message format, key exchange, and group protocols. Often requires breaking changes.

Fix: Design for E2E from day one. Use Signal Protocol (open source, battle-tested). The server should never see plaintext — this constraint simplifies many other decisions.

Best Practices

Design for offline-first

Assume the user is offline. Queue messages locally, sync when connected. Use message IDs for deduplication on reconnect. This is the single most important UX decision for mobile messaging.

Use the Signal Protocol for E2E encryption

Don't invent your own crypto. Signal Protocol handles forward secrecy, future secrecy, and multi-device with a proven security model. Libraries exist for all platforms (libsignal).

Implement delivery receipts as first-class messages

Sent/delivered/read are separate ack messages flowing through the same pipeline. Don't bolt them on as a side channel — they need the same reliability guarantees as content messages.

Partition by recipient, not sender

All messages destined for a user land on the same partition/shard. This makes "fetch all unread messages for user X" a single-partition read — the most common query pattern.

Use heartbeats aggressively for mobile connections

Mobile connections drop silently (tunnel into subway, airplane mode). Server-side heartbeat timeout (30-60s) detects dead connections. Client uses adaptive heartbeat intervals to conserve battery.

Keep the server stateless for chat processing

Session state (which server holds the connection) lives in Redis, not in the chat server's memory. This lets you restart/scale chat servers without losing message routing capability.

Graceful degradation: shed presence before messages

Under load, stop broadcasting presence/typing indicators first (low-value, high-volume). Message delivery is sacred — never shed it. This buys significant headroom.

Key Trade-offs

Consistency vs. Availability

Choice: AP (Available + Partition-tolerant). A message may be delivered twice (at-least-once), but never lost. Client deduplicates by message ID. Presence is eventually consistent.

Server Storage vs. Client Storage

Choice: Client is source of truth. Server is transient mailbox — deletes after delivery. Reduces storage costs dramatically but complicates multi-device sync.

Privacy vs. Features

Choice: Privacy first. E2E encryption means server can't index messages, can't do server-side search, can't moderate content. Features like search must run client-side.

Erlang BEAM vs. Mainstream Tech

Choice: Erlang. 2M connections/server (vs ~100K in Java/Go). Hot code upgrades with zero downtime. Trade-off: smaller talent pool, steeper learning curve.

Failure Scenarios

Chat Server Crash

Clients on that server reconnect (with jitter) to another server via load balancer. Undelivered messages remain in queue. New server picks them up from Cassandra/queue. No message loss.

Redis Session Cache Failure

Can't route messages to correct server. Fallback: broadcast to all servers (expensive but correct). Or: client reconnects, re-registers session. Messages queued during outage.

Cassandra Node Down

Replication factor 3 — reads/writes continue at CL=QUORUM. If multiple nodes fail, switch to CL=ONE (risk stale reads) or queue writes. Zero data loss with RF=3.
