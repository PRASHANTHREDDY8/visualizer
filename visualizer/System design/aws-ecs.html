AWS Elastic Container Service (ECS)

Fully managed container orchestration — run Docker containers at scale without managing servers

Component Breakdown

ECS Cluster

Control Plane

Logical grouping of services and tasks. A cluster can mix Fargate and EC2 capacity providers.

Key decisions:
  • One cluster per environment (dev/staging/prod) is typical
  • Capacity provider strategy determines Fargate vs EC2 split
  • Container Insights enable detailed observability

Task Definition

Blueprint

Immutable JSON document specifying how containers run: image, CPU/mem, ports, volumes, env vars, IAM roles.

Key decisions:
  • Version with revisions (like Docker Compose)
  • Multi-container tasks for sidecars (envoy, log agent)
  • CPU/memory determines available Fargate sizes

ECS Service

Orchestrator

Ensures desired task count is always running. Handles deployments, load balancer integration, and auto-scaling.

Key decisions:
  • Deployment: rolling (default) or blue/green (CodeDeploy)
  • Min/max healthy percentages control rollout speed
  • Circuit breaker auto-rolls back failed deploys

Fargate

Compute

Serverless compute engine. No EC2 management. Each task gets isolated vCPU, memory, and network interface.

Sizing:
  • 0.25 to 16 vCPU, 0.5 to 120 GB memory
  • 20 GB ephemeral storage (expandable to 200 GB)
  • Fargate Spot: 70% discount, 2-min interruption notice

Application Load Balancer

Networking

Layer 7 load balancing with path/host-based routing. Registers ECS tasks as targets dynamically.

ECS integration:
  • Dynamic port mapping (multiple tasks per host)
  • Health checks deregister unhealthy tasks
  • Weighted target groups for blue/green deploys

ECR (Container Registry)

Storage

Private Docker registry. Image scanning, lifecycle policies, cross-region replication, immutable tags.

Best practices:
  • Enable scan-on-push for vulnerability detection
  • Lifecycle policies to prune old images (cost)
  • Use immutable tags for production images

When to pick each

Choose ECS Fargate when:
  • You want serverless containers without K8s complexity
  • Your team is primarily AWS-native
  • Workloads run 24/7 or need consistent compute
  • You need Docker flexibility without server management
Choose EKS when:
  • Multi-cloud or hybrid-cloud is a requirement
  • You need advanced scheduling, operators, service mesh
  • Team has Kubernetes expertise
  • You need Helm, ArgoCD, or other K8s ecosystem tools
Choose Lambda when:
  • Workloads are event-driven and short-lived (<15 min)
  • Traffic is spiky with periods of zero usage
  • You want true scale-to-zero pricing
  • Functions don't need persistent connections or state

App Runner: Startups and prototypes needing quick deployment

Use Cases & Common Pitfalls

Primary Use Cases

Microservices Platform

Run dozens of containerized services with independent scaling. Each service gets its own task definition, ALB target group, and scaling policy. Service discovery via Cloud Map.

10-1000+ services

Batch Processing

Run compute-intensive jobs (ML training, video encoding, ETL) as standalone tasks. Fargate Spot for cost savings. Tasks auto-terminate on completion.

Event-driven

Web Applications

Containerized web apps with auto-scaling behind ALB. Rolling deployments with zero downtime. Health checks ensure only healthy tasks receive traffic.

Always-on

CI/CD Workers

Ephemeral build agents that scale with pipeline load. Each build gets a fresh container. Fargate Spot for cost efficiency on interruptible builds.

Bursty

Anti-Use Cases

Sub-second event processing

Fargate cold start is 30-60s. For sub-second triggers, use Lambda or keep warm tasks. ECS is for persistent workloads, not event-driven functions.

GPU-heavy ML inference (Fargate)

Fargate doesn't support GPUs. Use EC2 launch type with GPU instances (p4d, g5) or SageMaker for ML inference workloads.

Multi-cloud portability required

ECS is AWS-only. If you must run on GCP/Azure, use Kubernetes (EKS/GKE/AKS) or a platform-agnostic orchestrator.

Common Pitfalls

▸ Over-sizing task CPU/memory

The mistake: Allocating 4 vCPU / 8 GB to a service that uses 0.5 vCPU / 1 GB.

Why it happens: Teams copy-paste production config or "just to be safe" without profiling actual usage.

Consequence: 4-8x overspend on Fargate (billed per vCPU-hour and GB-hour).

Fix: Enable Container Insights, monitor actual CPU/mem utilization for 1-2 weeks, then right-size. Use ECS Exec to profile in production.

▸ Not configuring health check grace period

The mistake: Leaving ALB health check grace period at 0 seconds for services with slow startup.

Why it happens: Default is 0; developers test with instant-start containers locally.

Consequence: Tasks get killed before they finish booting, causing infinite restart loops and deployment failures.

Fix: Set healthCheckGracePeriodSeconds to at least 2x your container's startup time. Monitor task start duration in CloudWatch.

▸ Using bridge networking instead of awsvpc

The mistake: Using bridge network mode (Docker default) instead of awsvpc (ECS default for Fargate).

Why it happens: Teams migrating from Docker Compose keep bridge mode.

Consequence: No per-task security groups, can't use Cloud Map service discovery, complex port mapping.

Fix: Use awsvpc mode. Each task gets its own ENI with its own security group. Fargate requires awsvpc.

▸ Hardcoding secrets in task definitions

The mistake: Putting DB passwords, API keys in plain-text environment variables in the task definition.

Why it happens: Quick to set up; env vars are easy.

Consequence: Secrets visible in AWS Console, CloudTrail, and anyone with DescribeTaskDefinition permission.

Fix: Use secrets field pointing to Secrets Manager or SSM Parameter Store. ECS injects at runtime; never stored in the task def.

▸ No deployment circuit breaker

The mistake: Deploying without a circuit breaker, so a bad image causes infinite failing task launches.

Why it happens: Circuit breaker is opt-in; default deployment just keeps trying.

Consequence: Failed tasks pile up, consuming capacity. CloudWatch alarms fire. Manual rollback required at 2 AM.

Fix: Enable deployment circuit breaker with rollback: deploymentCircuitBreaker: { enable: true, rollback: true }

▸ Ignoring task placement constraints (EC2)

The mistake: Running all tasks on a single AZ or instance, creating a SPOF.

Why it happens: Default placement spreads but doesn't enforce AZ balance.

Consequence: AZ failure takes down all instances of a service.

Fix: Use spread placement strategy across AZs: placementStrategy: [{ type: "spread", field: "attribute:ecs.availability-zone" }]

Best Practices

Design Phase

  • One service per task definition — avoid multi-service tasks (except sidecars)
  • Define CPU/memory based on profiling, not guessing — start small and scale up
  • Design for immutable infrastructure — no SSH into containers, no manual state
  • Plan your VPC subnets: public (ALB) and private (ECS tasks) with NAT for outbound

Implementation

  • Use multi-stage Docker builds — production images should be minimal (distroless/alpine)
  • Implement graceful shutdown (handle SIGTERM) — ALB deregistration takes up to 30s
  • Use Secrets Manager/SSM for all credentials — never hardcode in task definitions
  • Set stopTimeout to allow graceful shutdown (default 30s, max 120s)
  • Tag all resources (environment, team, cost-center) for cost allocation

Operational

  • Enable Container Insights for CPU/memory/network metrics per task
  • Set up deployment circuit breaker with automatic rollback
  • Use ECS Exec for debugging — replaces SSH into containers
  • Configure CloudWatch alarms on: task count, CPU > 80%, unhealthy targets, 5xx rate
  • Implement structured JSON logging with correlation IDs across services

Scaling

  • Use target tracking scaling (CPU at 60-70%) as baseline, step scaling for spikes
  • Set appropriate cooldown periods — too short causes flapping, too long causes latency spikes
  • Mix Fargate and Fargate Spot via capacity provider strategy (e.g., 70/30 split)
  • For EC2 launch type: use managed scaling with capacity providers to auto-scale ASG
  • Pre-warm for known traffic patterns using scheduled scaling (e.g., morning spike)

Trade-off Analysis

Fargate vs EC2 Launch Type

FargateNo servers, pay per use, less control
EC2GPU support, custom AMI, cheaper at scale
VerdictStart Fargate; move to EC2 if you need GPUs or cost savings at >100 tasks

Rolling vs Blue/Green Deployment

RollingGradual, no extra cost, slower rollback
Blue/GreenInstant rollback, 2x capacity during deploy
VerdictRolling for most services; Blue/Green for critical APIs

Single-AZ vs Multi-AZ

Single-AZLower latency between services, lower cost
Multi-AZHA, survives AZ failures
VerdictAlways Multi-AZ for production. Period.

Failure Scenarios

  • Task crash: Service scheduler restarts immediately
  • AZ failure: Tasks relaunch in other AZs (if multi-AZ)
  • Bad deploy: Circuit breaker rolls back in ~5 min
  • ECR outage: Running tasks unaffected; new launches fail
