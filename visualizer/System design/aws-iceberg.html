🧊Apache Iceberg on AWS

Open table format for huge analytic datasets — bringing data warehouse reliability to data lake flexibility on S3

What is Apache Iceberg?

A table format specification that sits between your compute engines and raw data files on object storage

The Core Idea Iceberg is NOT a storage engine or a query engine. It is a table format — a specification for how to organize data files and metadata on S3 so that multiple engines (Spark, Trino, Athena, Flink) can reliably read and write the same tables with ACID guarantees.
📋

Table Format, Not Storage

Iceberg defines how to track which data files belong to a table, their statistics, and their schema — all stored as metadata files alongside your data on S3.

🔒

ACID Transactions

Every write is atomic. Readers always see a consistent snapshot. No dirty reads, no partial writes. Achieved via optimistic concurrency on metadata pointers.

⏳

Time Travel

Every commit creates a new snapshot. You can query your table as of any prior snapshot — audit, debug, or rollback with a simple timestamp or snapshot ID.

🔄

Schema Evolution

Add, drop, rename, or reorder columns without rewriting data. Iceberg tracks schema by column IDs, not positions — so old files still work with new schemas.

🔍

Hidden Partitioning

Partition transforms (year, month, day, hour, bucket, truncate) are defined in metadata. Users query with normal predicates — Iceberg handles partition pruning automatically.

⚡

Partition Evolution

Change your partitioning strategy without rewriting historical data. New data uses the new scheme; old data retains its original layout. Both coexist seamlessly.

The catalog is the entry point.

It stores a pointer to the current metadata file for each table:

db.orders → s3://bucket/metadata/v3.metadata.json

On AWS, the catalog is typically:
• AWS Glue Data Catalog (managed, serverless)
• Nessie (git-like branching)
• Hive Metastore (legacy)

This single pointer is what enables atomic commits — updating it atomically switches the entire table to a new version.

Why Iceberg over plain S3? Plain S3 + Parquet gives you cheap storage and columnar efficiency, but you lose: consistency guarantees (a reader may see partial writes), efficient updates (must rewrite whole files), time travel (no history), and smart planning (must list all files). Iceberg adds a thin metadata layer that solves all of these while keeping data on the same S3 — you only pay for extra metadata files (typically <1% of total storage).

Choose Iceberg when...

You need multi-engine access (Athena + Spark + Flink all on same tables), you expect schema/partition changes, or you want true openness with no vendor lock-in. Best for analytics-heavy workloads with periodic batch updates.

Choose Delta Lake when...

You're all-in on Databricks/Spark ecosystem. Delta has tighter Spark integration, better auto-optimization (OPTIMIZE, Z-ORDER as SQL commands), and good streaming with Structured Streaming.

Choose Hudi when...

Your primary workload is streaming ingestion with frequent upserts (CDC from databases). Hudi's Merge-on-Read is optimized for high-frequency writes with reasonable read performance.

Query Execution Flow

Step-by-step: what happens when you query an Iceberg table on AWS

Step 0 / 7
1

Query Submitted Athena / Spark

User runs: SELECT * FROM orders WHERE order_date = '2024-01-15' AND status = 'shipped'

2

Catalog Lookup AWS Glue

Engine asks catalog: "Where is the current metadata for db.orders?" → Gets S3 path to latest metadata.json

3

Read Metadata JSON S3 GET

Read v42.metadata.json: current schema (15 columns), partition spec (day(order_date)), current snapshot ID, and pointer to manifest list.

4

Manifest List Pruning Manifest List

Read manifest list. Each entry has partition range summaries. Prune: only manifests that could contain order_date = 2024-01-15 are kept. Skips 90% of manifests.

5

Manifest File Pruning Manifests

Read surviving manifests. Each entry has per-file column statistics (min/max for status). Prune files where max(status) < 'shipped' or min(status) > 'shipped'. Only 12 of 500 files survive.

6

Data File Reads Parquet on S3

Read only the 12 qualifying Parquet files. Column pruning: only read needed columns. Predicate pushdown into Parquet row groups for further filtering.

7

Results Returned Engine

Engine merges results, applies any pending delete files, and returns final result set. Total S3 reads: ~15 objects instead of thousands.

Key Insight: Three Levels of Pruning Iceberg's metadata tree enables progressive pruning — manifest list prunes by partition range, manifest files prune by column statistics, and Parquet format prunes by row group stats. This is why Iceberg queries can be 10-100x faster than scanning all files in a Hive-style partition.

Pitfalls & Common Mistakes

Things that will bite you in production if you're not careful

⚠️ Small File Problem

Streaming ingestion (Flink/Spark Streaming) creates many small files per commit — often 1-10MB each. Iceberg metadata handles this fine, but read performance degrades massively with thousands of tiny files (each S3 GET has latency overhead).

Fix: Run compaction regularly. Use rewrite_data_files action to merge small files into optimal 256MB-512MB files. On AWS, schedule a Glue job or EMR step for periodic compaction.

⚠️ Orphan Files Accumulating

Failed writes, expired snapshots, and compaction leave behind unreferenced data files on S3. Over months, these "orphan files" can cost significant storage money without serving any purpose.

Fix: Run remove_orphan_files procedure periodically (weekly). Set older_than to a safe window (e.g., 3 days) to avoid removing files from in-progress operations.

⚠️ Snapshot Explosion

Every commit creates a snapshot. High-frequency streaming (every minute) = 1,440 snapshots/day. Metadata files grow, catalog operations slow down, and time-travel storage cost balloons.

Fix: Configure snapshot expiration: history.expire.max-snapshot-age-ms (e.g., 7 days). Run expire_snapshots regularly. For streaming, commit at longer intervals (5-10 min) if latency allows.

⚠️ Write Conflicts with Optimistic Concurrency

Iceberg uses optimistic concurrency — two writers both read the same metadata version, both try to commit. One succeeds, one gets a CommitFailedException and must retry. Under high concurrency, retries cascade.

Fix: Design write patterns to minimize conflicts — partition-level isolation (different writers write to different partitions), or use a single writer per table with a queue. Configure commit.retry.num-retries.

⚠️ Ignoring Metadata File Growth

Each metadata.json includes ALL historical snapshots and schema versions. Over time, this single JSON file grows to MBs, slowing every table operation because it's read on every query plan.

Fix: Set write.metadata.previous-versions-max to limit versions kept in metadata. Use metadata compression. Recent Iceberg versions support metadata log cleanup.

⚠️ Not Understanding Delete Files Performance

Merge-on-Read (MoR) creates delete files that must be applied at read time. If you accumulate many delete files without compacting, reads slow to a crawl as the engine must cross-reference every data file with potentially thousands of deletes.

Fix: Monitor delete file counts. Compact aggressively after bulk delete operations. Consider Copy-on-Write for read-heavy tables where write latency is acceptable.

⚠️ S3 Consistency Assumptions

While S3 now provides strong read-after-write consistency, Iceberg's commit protocol still needs atomic metadata pointer updates. If your catalog (Glue) has eventual consistency in rare cases, you might read stale metadata.

Fix: Use AWS Glue as catalog (strongest AWS integration). Ensure your Iceberg library version handles S3 consistency correctly. Avoid custom catalog implementations unless you understand the commit protocol deeply.

Best Practices

Production-grade Iceberg on AWS

✅ Right-size Your Data Files

Target 256MB–512MB per data file. Too small = excessive S3 GETs and metadata overhead. Too large = poor parallelism and wasted reads for selective queries.

-- Spark: set target file size SET spark.sql.iceberg.target-file-size-bytes = 536870912; -- 512MB -- Compaction to right-size existing files CALL catalog.system.rewrite_data_files( table => 'db.orders', options => map('target-file-size-bytes', '536870912') );

✅ Automate Table Maintenance

Schedule three maintenance operations: expire snapshots, remove orphan files, and compact data files. On AWS, use Glue jobs, Step Functions, or EMR scheduled steps.

-- Run these on a schedule (daily or more frequent for streaming tables) -- 1. Expire old snapshots (keep 7 days) CALL catalog.system.expire_snapshots('db.orders', TIMESTAMP '2024-01-08 00:00:00'); -- 2. Remove orphan files (older than 3 days) CALL catalog.system.remove_orphan_files( table => 'db.orders', older_than => TIMESTAMP '2024-01-12 00:00:00' ); -- 3. Compact small files CALL catalog.system.rewrite_data_files(table => 'db.orders');

✅ Use Hidden Partitioning Wisely

Let Iceberg handle partitioning transforms. Users write natural predicates (WHERE order_date = '2024-01-15') and Iceberg applies partition pruning automatically. Avoid over-partitioning (don't partition by high-cardinality columns).

-- Good: partition by day transform on timestamp CREATE TABLE orders ( order_id bigint, order_ts timestamp, customer_id bigint, amount decimal(10,2) ) USING iceberg PARTITIONED BY (day(order_ts), bucket(16, customer_id)); -- Bad: partitioning by customer_id directly (too many partitions) -- Bad: not partitioning at all (no pruning benefit)

✅ Sort Within Partitions for Better Pruning

Sort data within files by frequently-filtered columns. This tightens min/max column statistics in manifests, enabling more aggressive file pruning.

-- Sort by status so files have tight min/max ranges ALTER TABLE orders WRITE ORDERED BY status, amount; -- Or use Z-ordering for multi-column filter patterns CALL catalog.system.rewrite_data_files( table => 'db.orders', strategy => 'sort', sort_order => 'zorder(status, customer_id)' );

✅ Configure AWS Glue Catalog Properly

Use Glue as your Iceberg catalog for best AWS integration. Enable Lake Formation for fine-grained access. Set the catalog implementation in your Spark/Flink config.

-- Spark config for Glue Catalog spark.sql.catalog.glue_catalog = org.apache.iceberg.spark.SparkCatalog spark.sql.catalog.glue_catalog.warehouse = s3://my-bucket/warehouse spark.sql.catalog.glue_catalog.catalog-impl = org.apache.iceberg.aws.glue.GlueCatalog spark.sql.catalog.glue_catalog.io-impl = org.apache.iceberg.aws.s3.S3FileIO -- Enable S3 acceleration for better throughput spark.sql.catalog.glue_catalog.s3.acceleration.enabled = true

✅ Monitor Table Health Metrics

Track: number of data files, average file size, number of delete files, manifest count, snapshot count, and compaction lag. Alert if small files exceed thresholds.

-- Query table metadata for health check SELECT * FROM glue_catalog.db.orders.files; -- all data files SELECT * FROM glue_catalog.db.orders.manifests; -- manifest info SELECT * FROM glue_catalog.db.orders.snapshots; -- snapshot history SELECT * FROM glue_catalog.db.orders.history; -- table history -- Check for small file problem SELECT count(*) as file_count, avg(file_size_in_bytes)/1024/1024 as avg_mb FROM glue_catalog.db.orders.files;

✅ Use Copy-on-Write vs Merge-on-Read Deliberately

Copy-on-Write (CoW): rewrites affected files on update/delete. Slower writes, faster reads. Best for read-heavy tables with infrequent updates.
Merge-on-Read (MoR): writes delete files. Faster writes, slower reads (must merge at query time). Best for write-heavy tables or streaming.

-- Set write mode per table ALTER TABLE orders SET TBLPROPERTIES ( 'write.delete.mode' = 'merge-on-read', -- for DELETEs 'write.update.mode' = 'merge-on-read', -- for UPDATEs 'write.merge.mode' = 'merge-on-read' -- for MERGE INTO );
