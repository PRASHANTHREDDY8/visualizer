Core Microservices Patterns

The foundational patterns that solve recurring problems in distributed architectures.

⚡

API Gateway

Communication

Single entry point for all client requests. Routes to appropriate services, handles cross-cutting concerns like auth, rate limiting, and response aggregation.

Kong NGINX AWS API Gateway Spring Cloud Gateway
⛔

Circuit Breaker

Resilience

Prevents cascading failures by monitoring calls to external services. Opens the circuit after a failure threshold, returning fast failures instead of waiting for timeouts.

Resilience4j Hystrix Polly (.NET) Envoy
🔄

Saga Pattern

Data Consistency

Manages distributed transactions as a sequence of local transactions. Each step has a compensating action for rollback. Can be orchestrated (central coordinator) or choreographed (event-driven).

Orchestration Choreography Temporal Axon Framework
📜

Event Sourcing

Data Management

Stores state as a sequence of immutable events rather than current state. Enables full audit trails, temporal queries, and event replay for debugging or rebuilding projections.

EventStoreDB Kafka Axon DynamoDB Streams
↔

CQRS

Data Management

Command Query Responsibility Segregation — separate models for reads and writes. Write model optimized for consistency, read model optimized for queries. Often paired with Event Sourcing.

Write: PostgreSQL Read: Elasticsearch Projections Materialized Views
🔍

Service Discovery

Communication

Dynamic registration and lookup of service instances. Client-side or server-side discovery allows services to find each other without hard-coded addresses.

Consul Eureka K8s DNS etcd
📨

Event-Driven / Async Messaging

Communication

Services communicate through events published to a message broker. Decouples producers from consumers, enables eventual consistency, and absorbs traffic spikes.

Kafka RabbitMQ AWS SNS/SQS NATS
🗄

Database per Service

Data Management

Each service owns its data store exclusively. Ensures loose coupling — services can choose the best storage technology (polyglot persistence) and evolve schemas independently.

PostgreSQL MongoDB DynamoDB Redis
🛡

Sidecar / Service Mesh

Infrastructure

Deploys a proxy alongside each service to handle cross-cutting concerns: mTLS, retries, circuit breaking, load balancing, and distributed tracing without modifying application code.

Istio Linkerd Envoy Consul Connect
🌳

Strangler Fig

Migration

Incrementally migrate from a monolith by routing specific requests to new microservices while the rest still hit the monolith. Over time, the monolith shrinks and is eventually decommissioned.

Proxy Routing Feature Flags Canary Releases
🚢

Bulkhead

Resilience

Isolates components so that a failure in one doesn't cascade. Uses separate thread pools, connection pools, or resource limits per dependency — like watertight compartments in a ship.

Thread Pool Isolation Semaphore Isolation K8s Resource Limits
⚙

Externalized Configuration

Infrastructure

Store configuration outside the service (environment variables, config server, key-value store). Enables changing behavior without redeployment and managing environment-specific settings.

Spring Cloud Config Consul KV AWS Parameter Store Vault
📊

Observability (3 Pillars)

Infrastructure

Distributed tracing, structured logging, and metrics collection. Correlates requests across services with trace IDs, enabling debugging of latency issues and understanding system behavior.

Jaeger / Zipkin Prometheus Grafana OpenTelemetry
📱

Backends for Frontends (BFF)

Communication

A dedicated backend per frontend type (web, mobile, IoT). Each BFF aggregates and transforms data specifically for its client's needs, avoiding a one-size-fits-all API.

GraphQL BFF REST BFF gRPC Internal

Use Cases

When microservices patterns shine — and when they don't.

E-Commerce Platform

Order, inventory, payment, shipping as separate services. Saga for checkout flow. Event-driven for notifications. Scale payment service independently during flash sales.

Streaming Platform

Content ingestion, recommendation engine, user profiles, billing as services. CQRS for read-heavy catalog queries. Circuit breaker for third-party CDN calls.

Banking / Fintech

Account service, transaction service, fraud detection, KYC. Event sourcing for immutable audit trail. Saga for fund transfers. Bulkhead to isolate critical payment paths.

SaaS Multi-Tenant

Tenant isolation via service-per-tenant or shard-per-tenant. API Gateway handles tenant routing. Externalized config per tenant. BFF for web vs mobile dashboards.

DON'T: Simple CRUD App

A basic admin panel with 2 developers doesn't need microservices. The network overhead, deployment complexity, and operational cost far outweigh any benefit.

DON'T: Early-Stage Startup

When domain boundaries are unclear and requirements change weekly, microservices cement the wrong boundaries. Start with a modular monolith, extract services when pain is proven.

Common Pitfalls

Mistakes engineers commonly make when adopting microservices.

▶ Distributed Monolith — Services that must deploy together

The Mistake

Splitting into services that share databases, require synchronized deployments, or have tightly coupled APIs. You get the complexity of distributed systems with none of the benefits.

Why It Happens

Teams split by technical layers (API, business logic, data) instead of business domains. Or they share a single database "for convenience."

The Consequence

Changes to one service break others. Deployments require coordination across teams. You can't scale independently.

The Fix

Follow Domain-Driven Design (DDD) bounded contexts. Each service owns its data. Define clear contracts (API schemas). If two services always change together, merge them.

▶ No Circuit Breakers — Cascading failure across services

The Mistake

Service A calls Service B synchronously without timeout or fallback. When B is slow, A's thread pool fills up, then A becomes slow, and everything upstream cascades.

Why It Happens

In a monolith, calls are in-process and effectively instant. Developers carry that assumption into distributed calls.

The Consequence

One slow database query in a leaf service can take down the entire platform.

The Fix

Implement circuit breakers on all inter-service calls. Set aggressive timeouts. Use bulkheads to isolate thread pools. Have graceful degradation (return cached/default data when circuit opens).

▶ Shared Database — Coupling through the data layer

The Mistake

Multiple services read/write the same database tables directly. Schema changes become coordination nightmares.

Why It Happens

It's the quickest way to share data. Feels pragmatic in the short term.

The Consequence

Services can't evolve their schemas independently. Performance issues in one service's queries affect all others. No clear data ownership.

The Fix

Database per service. Synchronize data via events or API calls. Use the outbox pattern for reliable event publishing.

▶ Missing Observability — Can't debug distributed failures

The Mistake

Adopting microservices without investing in distributed tracing, centralized logging, and metrics. When something breaks, no one can trace the request across services.

Why It Happens

Observability tooling feels like overhead when starting out. Teams defer it as "nice to have."

The Consequence

Mean Time to Recovery (MTTR) skyrockets. Debugging requires correlating logs from 10+ services manually. Intermittent failures become unsolvable mysteries.

The Fix

Instrument from day one. Use OpenTelemetry for vendor-neutral traces. Propagate correlation/trace IDs in all requests. Set up dashboards for the golden signals (latency, traffic, errors, saturation).

▶ Too Many Services Too Early — Premature decomposition

The Mistake

Starting with 20+ microservices from day one before understanding domain boundaries.

Why It Happens

Excitement about microservices architecture. Desire to "do it right" from the start.

The Consequence

Wrong service boundaries that need expensive refactoring. Operational overhead that slows a small team to a crawl. Distributed debugging for simple features.

The Fix

Start with a well-structured monolith or 3-5 services along clear domain boundaries. Extract new services only when you have proven pain (scaling bottleneck, team contention, deployment frequency needs).

Best Practices

Proven guidelines for building robust microservices systems.

Design Phase

  • Use Domain-Driven Design (DDD) to identify bounded contexts — these become your service boundaries
  • Define service contracts (OpenAPI, Protobuf) before implementation — design by contract
  • Prefer asynchronous communication (events) over synchronous calls for decoupling
  • Design for failure: every inter-service call can fail, timeout, or return stale data
  • Each service should be independently deployable — if it can't be, it's not a separate service

Implementation

  • Implement the Outbox Pattern for reliable event publishing (avoids dual-write problem)
  • Use idempotency keys for all write operations to handle retries safely
  • Keep services stateless — store state in the database or external cache
  • Version your APIs from day one (URL versioning or header-based)
  • Implement health check endpoints (/health, /ready) for orchestrator integration
  • Use correlation IDs propagated through all service calls for end-to-end tracing

Operations

  • Containerize everything (Docker) and orchestrate with Kubernetes for consistent deployments
  • Implement CI/CD per service — independent pipelines, independent release cycles
  • Monitor the Four Golden Signals: latency, traffic, errors, saturation (per service)
  • Set up alerting on SLO violations, not just raw metrics
  • Use canary deployments or blue-green for zero-downtime releases
  • Run chaos engineering experiments (Chaos Monkey) to validate resilience patterns

Data Management

  • One database per service — never share a database between services
  • Accept eventual consistency as the default; use sagas for distributed transactions
  • Use event-driven data replication instead of shared databases for cross-service queries
  • Implement the CQRS pattern when read and write workloads have different scaling needs
  • Use change data capture (CDC) with Debezium for reliable database event streaming

Scaling & Trade-offs

How microservices patterns handle growth and the fundamental trade-offs.

📈 Capacity Estimation

100K DAU example:
Peak QPS: ~1,000/s (10x average)
Each service: 3 replicas minimum
Database: Read replicas + connection pooling
Message queue: 5,000 events/s throughput
Storage: grows linearly with event sourcing

🚀 10x Growth Strategy

Scale hot services independently (payment during sales). Add read replicas and caches. Partition event bus topics. Use auto-scaling rules per service based on CPU/queue-depth.

⚖ CAP Trade-offs

Consistency vs. Availability: Most microservices choose AP (available + partition-tolerant). Sagas provide eventual consistency. Only use strong consistency where business requires it (payments).

💥 Failure Scenarios

If the event bus dies: Services buffer locally (outbox), retry when bus recovers.
If a service dies: Circuit breaker opens, fallback to cached data.
If API Gateway dies: DNS failover to standby; all traffic halts briefly.

⏱ Latency vs. Throughput

Synchronous calls minimize latency but limit throughput. Async events maximize throughput but add latency. Use sync for user-facing reads, async for writes and processing.

🔧 Operational Cost

Each service adds: CI/CD pipeline, monitoring dashboard, on-call rotation, infrastructure cost. Only split when the benefit (autonomy, scaling, isolation) exceeds this cost.
