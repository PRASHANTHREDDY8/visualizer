Component Breakdown

⚙

Notification Service

Core orchestrator that receives notification requests, validates, enriches with templates, checks user preferences, assigns priority, and dispatches to the message broker.

Technology
Java / C#Spring Boot / .NETgRPC
Key Decisions
Stateless design for horizontal scaling. Idempotency keys prevent duplicate notifications. Async processing via message broker for resilience.
Scaling
Horizontal — add more instances behind load balancer. Stateless, so any instance can handle any request.
⚡

API Gateway

Entry point for all notification requests. Handles authentication, request validation, rate limiting, and routing.

Technology
Azure API ManagementKongNGINX
Key Decisions
Token-based auth (JWT) for service-to-service. API versioning via URL path. Request body size limits to prevent abuse.
Scaling
Horizontal with DNS-based load balancing. Can handle 100K+ RPS per instance with connection pooling.
🛑

Rate Limiter

Prevents notification spam and protects downstream services. Enforces per-user, per-channel, and per-service rate limits.

Technology
RedisToken BucketSliding Window
Key Decisions
Sliding window counters in Redis for accuracy. Different limits per channel (email: 10/hr, push: 50/hr, SMS: 5/hr). Burst allowance for critical notifications.
Scaling
Redis Cluster with hash-slot-based sharding. Sub-millisecond check latency.
📄

Template Engine

Renders personalized notification content from templates. Supports multiple formats (HTML email, plain text, push payload) with i18n.

Technology
Handlebars / Jinja2Template DBRedis Cache
Key Decisions
Templates stored in DB with version history. Hot-path templates cached in Redis. A/B testing support for content optimization.
Scaling
CPU-bound (rendering). Scale horizontally with template cache warming. Compiled templates for hot paths.
👤

User Preference Service

Manages user notification preferences: opted-in channels, quiet hours, frequency caps, and category subscriptions.

Technology
PostgreSQLRedis CacheREST API
Key Decisions
Read-heavy workload — aggressive caching with TTL. Preference changes trigger cache invalidation via pub/sub. GDPR-compliant opt-out tracking.
Scaling
Read replicas for queries. Cache hit rate > 95% reduces DB load dramatically.
✉

Message Broker (Kafka)

Decouples notification creation from delivery. Provides durability, ordering, and replay capabilities for all notification events.

Technology
Apache KafkaAzure Event HubsPartitioned Topics
Key Decisions
Separate topics per priority level (P0, P1, P2). Partition by user_id for ordering guarantees per user. 7-day retention for replay and debugging.
Scaling
Add partitions to increase throughput. Each partition can sustain ~10K msgs/sec. Consumer groups for parallel processing.
🚀

Channel Workers

Channel-specific delivery agents. Each worker type handles the protocol and provider integration for its channel (APNs, FCM, SMTP, Twilio, WebSocket).

Technology
APNs/FCM SDKSendGrid/SESTwilioWebSocket
Key Decisions
Provider abstraction layer enables swapping vendors without code changes. Circuit breaker pattern for provider outages. Exponential backoff with jitter for retries (max 3).
Scaling
Independent scaling per channel. Push workers need more instances during peak hours; email workers scale with batch size.
📊

Analytics & Tracking

Tracks delivery status (sent, delivered, opened, clicked, failed) across all channels. Powers dashboards and alerting.

Technology
ClickHouseKafka StreamsGrafana
Key Decisions
Append-only event log in ClickHouse for fast aggregations. Real-time delivery rate monitoring triggers alerts on anomalies.
Scaling
ClickHouse sharding for write throughput. Pre-aggregated materialized views for dashboard queries.

Use Cases & Common Pitfalls

Primary Use Cases

🔔

Transactional Alerts

Order confirmations, password resets, 2FA codes, payment receipts. Must be delivered immediately with near-100% reliability.

Scale: 10K-100K/min • Latency: <5s • Priority: P0
📱

Social / Activity Feeds

Likes, comments, follows, mentions. High volume, tolerates slight delay. Microsoft Teams uses this for @mentions and reactions.

Scale: 1M+/min • Latency: <30s • Priority: P1
📨

Marketing Campaigns

Promotional emails, product announcements, re-engagement pushes. Batch-processed, personalized, with A/B testing.

Scale: 10M+ batch • Latency: minutes-hours • Priority: P2
⚠

System Alerts & Monitoring

Infrastructure alerts, SLA breaches, security incidents. Must cut through noise — PagerDuty-style escalation chains.

Scale: 1K/min • Latency: <1s • Priority: P0
🎮

Gaming (Xbox Live)

Friend online, game invite, achievement unlocked, tournament starting. Real-time push across console, PC, and mobile.

Scale: 500K/min peak • Latency: <2s • Priority: P0-P1
📚

Scheduled Digests

Daily summary emails, weekly reports, activity digests. Aggregated from individual events, rendered as rich HTML.

Scale: 50M/day • Latency: scheduled • Priority: P2

Anti-Use-Cases

Don't use this for real-time chat. Chat requires persistent connections, message threading, read receipts, and typing indicators — a separate messaging system (like WhatsApp's architecture) is more appropriate. Notifications should inform users *about* chat messages, not *be* the chat system.
Don't use this for streaming data feeds. Financial tickers, IoT sensor streams, or live video events need dedicated streaming infrastructure (Kafka Streams, Flink) with different latency and throughput guarantees.
Don't use this for synchronous request-response workflows. If the caller needs to wait for the notification result before proceeding (e.g., inline OTP verification), use a synchronous API call instead of an async notification pipeline.

Design Pitfalls

⚠ Notification Storm (Thundering Herd) ▼
The MistakeSending millions of notifications simultaneously during a batch campaign without throttling.
Why It HappensTeams treat batch sends like single sends — just "loop and fire." No thought to downstream provider limits.
ConsequenceEmail providers block your domain (spam flag). Push providers rate-limit you. SMS costs spike. Users unsubscribe in droves.
The FixImplement send-rate governors. Batch campaigns should use a leaky bucket dispatcher that spreads sends over time. Monitor provider feedback loops.
⚠ No Deduplication Strategy ▼
The MistakeNot implementing idempotency keys or content-based dedup, causing users to receive the same notification 3-5 times during retries.
Why It HappensRetry logic is added for reliability, but without dedup, each retry creates a new notification.
ConsequenceUser trust erodes. "You sent me 4 password reset emails" — complaint tickets spike. Possible regulatory issues for SMS.
The FixRequire idempotency keys on all notification requests. Store them in Redis with a TTL matching your retry window. Reject duplicates at the API layer.
⚠ Ignoring User Preferences Until Too Late ▼
The MistakeChecking user preferences at the worker level (after queuing) instead of before queuing, wasting queue capacity on notifications the user opted out of.
Why It HappensPreference check seems like a "delivery concern" and gets pushed to the worker.
ConsequenceQueue bloat: 30-40% of queued messages get dropped at delivery. Wasted compute. Inaccurate delivery metrics.
The FixCheck preferences in the Notification Service before queuing. Only enqueue to channels the user has opted into. Cache preferences in Redis for fast lookups.
⚠ Single Priority Queue ▼
The MistakeUsing one queue for all priorities, causing 2FA codes to wait behind marketing emails during peak campaigns.
Why It Happens"Keep it simple" — one queue is easier to manage. Priority feels like premature optimization.
ConsequenceCritical notifications (security alerts, OTP codes) delayed by minutes during marketing blasts. User can't log in because 2FA is stuck behind 500K promo emails.
The FixSeparate Kafka topics or queue lanes per priority: P0 (critical), P1 (high), P2 (normal). P0 consumers have dedicated capacity that never competes with bulk sends.

Interview Pitfalls

💡 Jumping to microservices without justification ▼
The MistakeImmediately drawing 15 microservices without discussing trade-offs or whether a modular monolith could work.
The FixStart simple, then explain WHY you'd split: "The notification service and delivery workers have different scaling profiles — workers need 10x more instances during peaks — so separating them lets us scale independently."
💡 Forgetting to discuss failure handling ▼
The MistakeOnly describing the happy path. Not mentioning what happens when FCM is down, or when SMS delivery fails, or when Kafka loses a broker.
The FixProactively discuss: retry strategies, circuit breakers, DLQ for poison messages, fallback channels (if push fails, try email), and alerting on delivery failure rates.
💡 Not estimating capacity ▼
The MistakeSaying "we'll use Kafka" without estimating QPS, storage, or how many partitions/consumers you'd need.
The FixAlways do back-of-envelope math: "500M DAU × 10 notifications/day = 5B/day ≈ 58K/sec. Each message ~1KB, so ~58MB/sec throughput. With 3x replication, we need ~6 Kafka brokers."

Best Practices

🎯 Design Phase

  • Define notification categories upfront. Transactional (must-deliver), promotional (can-skip), system alerts (escalation-required). Each category has different SLAs and compliance requirements.
  • Design for multi-channel from day one. Even if you launch with just push + email, the abstraction layer for channels should exist. Adding SMS or webhook later should be a new worker, not a refactor.
  • Plan your priority levels early. At minimum: P0 (critical, immediate), P1 (important, near-real-time), P2 (informational, best-effort). Each gets its own queue lane with dedicated consumer capacity.
  • Calculate your dedup window. Use back-of-envelope: if retry window is 15 min and you retry 3x with exponential backoff, your dedup TTL needs to be at least 20 min. Factor in clock skew.

🛠 Implementation

  • Make consumers idempotent. Kafka guarantees at-least-once delivery. Every worker must handle re-delivery gracefully — use the notification ID as a dedup key in the delivery log.
  • Implement circuit breakers for external providers. When FCM returns 503s, stop hammering it. Open the circuit, route to fallback channel or buffer, and retry after cooldown.
  • Use structured logging with correlation IDs. Every notification gets a unique trace_id at creation. Log it at every step (validation → queue → worker → delivery). Essential for debugging "why didn't I get my notification?"
  • Batch provider API calls. FCM supports sending to 500 devices per request. SendGrid supports 1000 recipients per API call. Always batch — individual calls waste connection overhead and hit rate limits faster.
  • Handle device token rotation. Mobile push tokens expire and rotate. When APNs/FCM returns "invalid token," immediately update the device registry. Stale tokens waste capacity and skew delivery metrics.

🔧 Operations

  • Alert on delivery rate, not just send rate. Sending 100K/min means nothing if only 60K are delivered. Track delivery rate per channel. Alert when it drops below 95% for push or 98% for email.
  • Monitor queue depth per priority lane. P0 queue depth > 1000 for > 30s = critical alert. P2 queue depth can tolerate higher accumulation during peaks.
  • Implement graceful degradation. Under extreme load: shed P2 notifications first → batch P1 notifications → never shed P0. Document this shedding order for oncall.
  • Run chaos engineering. Regularly kill a push worker, simulate FCM outage, inject Kafka partition leader election. Verify that fallback and retry logic actually works.

📈 Scaling

  • Scale workers independently per channel. Push worker fleet might be 50 instances while email worker is 10. They have different throughput profiles and provider rate limits.
  • Use Kafka consumer groups wisely. One consumer group per worker type. Add consumers up to the number of partitions (beyond that, consumers sit idle). If you need more throughput, add partitions first.
  • Cache user preferences aggressively. Preference lookups happen on every notification. With 500M users and 58K notifications/sec, that's 58K preference lookups/sec. Redis cache with 5-min TTL, invalidate on preference change via pub/sub.
  • Shard notification log by user_id. The "notification history" table grows fastest. Shard by user_id hash. Archive notifications older than 90 days to cold storage (S3 + Athena for queries).

⚖ Trade-off Analysis

Latency vs ThroughputP0 optimizes for latency (<1s); P2 optimizes for throughput (batch).
Consistency vs AvailabilityFavor availability — a delayed notification is better than no notification.
Cost vs ReliabilityMulti-provider fallback (FCM → APNs → WebSocket) increases cost but ensures delivery.
Simplicity vs FlexibilityProvider abstraction adds complexity but enables vendor switching without downtime.

💥 Failure Scenarios

Push Provider Down (FCM outage)

Circuit breaker opens → notifications buffered in queue → fallback to in-app WebSocket for online users → retry FCM when circuit closes.

Kafka Broker Failure

Partition leadership rebalances to surviving brokers (automatic). Producers retry with backoff. ISR (in-sync replicas) ensure no data loss if replication factor ≥ 3.

Database Overload

Read replicas absorb query load. Write-behind pattern for notification log (batch writes every 100ms). If DB is fully down, workers continue delivering from queue — log writes are eventually consistent.
