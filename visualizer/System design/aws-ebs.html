Comparisons with Alternatives

Storage Type Key Difference Pros Cons Best For
EBS (Chosen) Network-attached block storage, persists independently Persistent, snapshots, encryption, flexible volume types AZ-scoped, network latency, cost per provisioned GB Boot volumes, databases, general workloads
Instance Store Physically attached NVMe on the host Highest IOPS (millions), zero network hops, included free Ephemeral — lost on stop/terminate, no snapshots Caches, temp buffers, scratch space
EFS Managed NFS, multi-AZ, elastic sizing Shared access, auto-scales, no pre-provisioning Higher latency (~ms), more expensive per GB, POSIX only Shared file systems, CMS, ML training data
FSx (Lustre/NetApp) High-performance parallel filesystem Massive throughput, S3 integration, sub-ms latency Complex, expensive, specialized use cases HPC, genomics, financial modeling

When to pick each

EBS when you need persistent block storage for a single instance (databases, boot volumes, apps that need data to survive reboots).
Instance Store when you need maximum local I/O performance and can tolerate data loss (caches, Kafka broker log dirs, Spark shuffle).
EFS when multiple instances need concurrent read/write access to the same files (shared config, web content, ML datasets).
FSx when you need HPC-grade parallel I/O with S3 data lake integration (scientific computing, video rendering).

Use Cases & Common Pitfalls

Primary Use Cases

🗃
Database Storage
MySQL, PostgreSQL, Oracle on EC2. Use io2 for mission-critical, gp3 for dev/test. Consistent low-latency I/O.
💻
Boot Volumes
OS root filesystem for every EC2 instance. gp3 is the default. Survives stop/start cycles.
📈
Data Warehousing
st1 volumes for sequential scan workloads — Hadoop HDFS, ClickHouse, log aggregation. Optimized for throughput.
📷
Backup & DR via Snapshots
Point-in-time snapshots stored in S3. Cross-region copy for disaster recovery. Incremental = fast & cheap.

Anti-Use Cases

❌
Shared Filesystem
EBS is single-attach (except io2 Multi-Attach). Use EFS or FSx for shared access across instances.
❌
Object Storage
Don't use EBS for storing millions of small objects, images, or static assets. Use S3 instead — infinitely scalable and cheaper.
❌
Cross-AZ Persistence
EBS is AZ-scoped. If you need multi-AZ data, use EFS, Aurora, or replicate via snapshots.
Under-provisioning IOPS for database workloads ▶

The mistake: Using gp3 defaults (3,000 IOPS) for a production database that needs 10K+ IOPS during peak.

Why it happens: gp3 is cheap and works in dev. Load testing doesn't replicate production patterns.

The consequence: I/O throttling causes latency spikes, query timeouts, and application errors under load.

The fix: Monitor VolumeQueueLength and VolumeReadOps/VolumeWriteOps. Right-size IOPS based on production metrics. Use io2 for latency-critical workloads.

Not enabling encryption on new volumes ▶

The mistake: Creating volumes without encryption, then needing to encrypt later (requires snapshot + copy + restore).

Why it happens: Encryption isn't the default, and there's no performance penalty, so people forget.

The consequence: Compliance failures, painful migration process, downtime to swap volumes.

The fix: Enable "EBS Encryption by Default" at the account level. Zero performance impact, protects data at rest and in transit.

Ignoring burst credit depletion on gp2 ▶

The mistake: Running I/O-heavy workloads on small gp2 volumes that depend on burst credits.

Why it happens: Small gp2 volumes burst to 3,000 IOPS but baseline is only 3 IOPS/GiB. A 100GB volume baselines at 300 IOPS.

The consequence: Once credits exhaust, performance drops to baseline. Application slows down unpredictably.

The fix: Migrate to gp3 (always 3,000 IOPS baseline) or size gp2 at 1,000+ GiB for sustained 3,000 IOPS.

Forgetting snapshots are incremental but billed on consumed storage ▶

The mistake: Taking frequent snapshots of large volumes thinking they're cheap because "incremental."

Why it happens: The first snapshot is a full copy. If data churns heavily, incrementals can still be large.

The consequence: Unexpectedly high S3 snapshot costs, especially for write-heavy databases.

The fix: Use Amazon Data Lifecycle Manager (DLM) to automate retention. Monitor snapshot size growth. For databases, prefer native backup tools + S3.

Not pre-warming volumes restored from snapshots ▶

The mistake: Restoring a snapshot and immediately running production traffic on it.

Why it happens: Restored volumes are lazily loaded from S3 — first access to each block has high latency.

The consequence: 5-50x higher latency on first reads until all blocks are fetched from S3.

The fix: Enable Fast Snapshot Restore (FSR) for critical volumes, or run dd / fio to read all blocks before serving traffic.

Best Practices

Enable encryption by default at the account level
No performance penalty. Protects data at rest (AES-256) and in transit between EC2 and EBS. Use AWS-managed or customer-managed KMS keys.
Use gp3 over gp2 for new workloads
gp3 is 20% cheaper per GB, gives 3,000 IOPS and 125 MB/s baseline without burst credit complexity. Provision additional IOPS/throughput independently of size.
Monitor CloudWatch EBS metrics continuously
Key metrics: VolumeQueueLength (>1 indicates saturation), VolumeReadOps/WriteOps, VolumeThroughput, BurstBalance (gp2). Set alarms before users notice.
Use DLM for automated snapshot lifecycle
Define backup schedules, retention policies, and cross-region copy rules. Avoids manual snapshot management and controls costs.
Right-size volumes using actual I/O patterns
Don't guess. Use CloudWatch metrics for 2+ weeks to understand peak IOPS and throughput. EBS Elastic Volumes lets you resize/re-type without downtime.
Use io2 with Multi-Attach for shared-storage clustering
Supports up to 16 Nitro instances. Requires cluster-aware filesystem (GFS2, OCFS2). For active-passive HA database patterns.
Enable Fast Snapshot Restore for production DR
Eliminates lazy-loading latency on restored volumes. Costs per AZ per snapshot but essential for low-RTO recovery.

Trade-offs Key Decisions

Cost vs. Performance
gp3 ($0.08/GB) is 20% cheaper than gp2 ($0.10/GB). io2 ($0.125/GB + $0.065/IOPS) is for when you need guaranteed sub-ms latency.
IOPS vs. Throughput
Small random I/O (OLTP) needs IOPS. Sequential large I/O (analytics) needs throughput. Pick volume type accordingly.
Durability vs. Cost
gp3/gp2: 99.8-99.9% durability. io2: 99.999%. If a single volume failure is catastrophic, pay for io2.
Simplicity vs. Performance
RAID 0 stripes across volumes for more IOPS/throughput, but adds complexity. Consider if io2 Block Express can handle the load in one volume.

Failures What Happens When...

Volume impairment: AWS automatically replaces the underlying hardware. Brief I/O pause (seconds). Data preserved due to replication.

AZ failure: All EBS volumes in that AZ become unavailable. Snapshots in S3 are unaffected — restore to a different AZ.

EC2 instance failure: EBS volume persists. Re-attach to a new instance in the same AZ. Root volumes with "Delete on Termination" are the exception.

Network partition: I/O operations queue and timeout. Application sees I/O errors. EBS retries internally but extended partitions cause volume impairment detection.
