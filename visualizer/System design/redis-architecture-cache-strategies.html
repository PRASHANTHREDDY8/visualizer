Component Breakdown

Deep dive into each component's role, technology choices, and scaling characteristics.

M
Redis Master
Handles all write operations. Single-threaded event loop processes commands sequentially ensuring atomicity. Uses hash slots (0-16383) for data partitioning in cluster mode.
Writes Only Single-threaded 100K+ ops/sec
R
Redis Replica
Asynchronous replication from master. Serves read traffic to scale read throughput horizontally. Automatically promoted to master during failover via Sentinel or cluster protocol.
Read-only Async Replication Auto-promote
S
Redis Sentinel
Distributed monitoring system. Detects master failure via quorum (min 3 sentinels). Performs automatic failover, notifies clients of topology changes, and acts as configuration provider.
HA Monitor Quorum-based Auto-failover
P
RDB Persistence
Point-in-time snapshots via fork() + copy-on-write. Compact binary format ideal for backups and disaster recovery. Configurable save intervals (e.g., save 60 10000).
Compact Periodic Fast Restart
A
AOF Persistence
Append-only log of every write command. Three fsync policies: always (safest), everysec (balanced), no (OS decides). AOF rewrite compacts the log in background.
Durable Every Write Rewritable

Binary gossip protocol on port+10000. Nodes exchange heartbeats, share slot mappings, detect failures, and propagate configuration changes. Handles slot migration during resharding.
Gossip Heartbeat Failure Detection

Smart clients (redis-py, ioredis, Jedis) maintain slot-to-node mapping. Handle MOVED/ASK redirections, connection pooling, pipelining, and cluster-aware routing.

Cache Strategy Comparisons

Side-by-side analysis of caching strategies and when to choose each one.

Strategy How it Works Pros Cons Best For
Cache-Aside Most Common App checks cache first. On miss, reads from DB, then writes to cache. Simple, app controls caching logic, resilient to cache failure Cache misses are expensive (extra round-trip), potential stale data General-purpose, read-heavy workloads
Read-Through Cache sits between app and DB. Cache auto-loads from DB on miss. App code is simpler, consistent caching logic Cache library must support DB loading, cold-start latency When you want transparent caching
Write-Through App writes to cache, cache synchronously writes to DB. Cache always consistent with DB, no stale reads Write latency increases (2 writes per operation), write amplification Strong consistency requirements, read-after-write
Write-Behind App writes to cache, cache asynchronously flushes to DB in batches. Lowest write latency, batching reduces DB load Data loss risk if cache fails before flush, complexity High write throughput, acceptable data loss window

Use Cases

Where Redis excels and where it doesn't belong.

Primary Use Cases

Session Store

Store user sessions with TTL. Sub-ms reads. Horizontal scaling via cluster. 100K-1M concurrent sessions.

API Response Cache

Cache expensive DB queries or third-party API responses. Typically 10-60s TTL. Reduces DB load by 80-95%.

Rate Limiting

Sliding window or token bucket using INCR + EXPIRE. Atomic operations guarantee correctness under concurrency.

Leaderboard / Ranking

Sorted Sets with O(log N) insert/update. ZRANGEBYSCORE for range queries. Real-time leaderboards for millions of users.

Message Queue / Stream

Redis Streams for persistent message queues. Consumer groups, acknowledgments, and message replay. Lightweight alternative to Kafka.

Distributed Lock

SET NX EX pattern or Redlock algorithm for distributed mutual exclusion. Critical for preventing double-processing.

Anti-Use Cases

Primary Database

Redis is not a replacement for PostgreSQL/MySQL. Limited querying, no ACID transactions across keys, memory-bound cost makes it prohibitive for large datasets.

Large Object Storage

Storing objects > 1MB is inefficient. Network bandwidth and memory fragmentation become bottlenecks. Use S3/blob storage instead.

Complex Queries

No JOINs, no ad-hoc queries, limited secondary indexing. If you need flexible querying, use a relational DB or Elasticsearch.

Common Pitfalls

Mistakes engineers frequently make with Redis. Click to expand.

Cache Stampede (Thundering Herd)
The mistake: Many keys expire at the same time, causing all requests to hit the database simultaneously.

Why it happens: Setting the same TTL for all cached items during bulk loading or cache warming.

The consequence: Database gets overwhelmed by sudden spike. Can cascade into full outage.

The fix: Add jitter to TTLs (TTL + random(0, TTL*0.1)). Use lock-based recomputation (only one request refills cache). Implement stale-while-revalidate pattern.
Hot Key Problem
The mistake: A single key receives disproportionate traffic (e.g., viral content, celebrity profile).

Why it happens: Natural traffic patterns — some data is accessed orders of magnitude more than others.

The consequence: Single Redis node becomes bottleneck. CPU saturation, increased latency for all keys on that shard.

The fix: Read replicas for hot keys. Local in-memory cache (L1) in front of Redis. Key splitting (append random suffix, merge reads). Redis 7.0+ client-side caching.
Big Key Anti-Pattern
The mistake: Storing very large values (>10KB) or collections with millions of elements in a single key.

Why it happens: Convenient to store entire objects; grows over time without monitoring.

The consequence: Blocks the event loop during serialization. DEL of a big key causes latency spikes. Uneven memory distribution across cluster.

The fix: Monitor with MEMORY USAGE. Split large collections into smaller chunks. Use UNLINK (async delete) instead of DEL. Set key-size alerts.
No Eviction Policy Set
The mistake: Running Redis with default noeviction policy and no maxmemory limit.

Why it happens: Works fine in development. Production traffic fills memory over time.

The consequence: Redis returns OOM errors. Writes fail. If swap is enabled, massive performance degradation as Redis pages to disk.

The fix: Always set maxmemory (typically 75% of available RAM). Choose appropriate eviction policy: allkeys-lru for cache, volatile-lru if mixing cache and persistent data.
KEYS Command in Production
The mistake: Using KEYS * or KEYS pattern in production to find keys.

Why it happens: Works in development with few keys. Seems like a natural API.

The consequence: Blocks the single-threaded event loop for the ENTIRE scan duration. With millions of keys, this means seconds of downtime.

The fix: Use SCAN with cursor-based iteration (non-blocking). Monitor with redis-cli --bigkeys. Disable dangerous commands via rename-command in redis.conf.
Ignoring Replication Lag
The mistake: Reading from replicas immediately after writing to master and expecting consistency.

Why it happens: Replication is async by default. Under normal load lag is sub-millisecond, masking the issue.

The consequence: Stale reads after writes. Users see old data. Critical for flows like "write then redirect and read."

The fix: Read-your-writes from master. Use WAIT command for synchronous replication when needed. Monitor replication offset lag.

Best Practices

Proven patterns for production Redis deployments.

Design & Implementation

Set TTL on Every Cache Key
Never cache without expiration. Use TTL appropriate to data freshness needs (seconds for real-time, minutes for semi-static, hours for rarely-changing). Add 5-10% jitter to prevent stampedes.
Use Pipelining for Bulk Operations
Pipeline reduces round trips. Instead of 100 sequential GET commands (100 round trips), pipeline them into 1 network call. 5-10x throughput improvement typical.
Namespace Your Keys
Use prefixes like "user:123:session" or "cache:api:products". Enables easy bulk invalidation with SCAN, clear ownership, and prevents collisions between services.
Prefer Hash for Object Storage
Store objects as Redis Hashes instead of serialized JSON strings. Hashes allow partial reads/updates (HGET/HSET), use less memory for small objects (ziplist encoding), and avoid full deserialization.

Operations & Scaling

Monitor Memory and Eviction Rate
Alert on: used_memory > 80% maxmemory, evicted_keys > 0 (unexpected eviction), connected_clients approaching limit. Use INFO MEMORY and INFO STATS regularly.
Use Cluster Mode for Horizontal Scaling
Start with Sentinel for HA. Move to Cluster when single-node memory or throughput is insufficient. Plan for 3+ masters minimum. Avoid cross-slot operations (MGET across shards).
Implement Circuit Breaker
Cache failures should not cascade to application failure. Implement fallback: if Redis is down, go directly to DB (with rate limiting). Never let cache be a hard dependency for reads.
Use Lua Scripts for Atomic Operations
Multi-step operations that must be atomic (check-and-set, rate limiting) should use Lua scripts executed via EVAL. Runs on server-side, no race conditions, single network call.

Scaling Strategies

Vertical (Scale Up)
Increase RAM and CPU. Works up to ~25GB per node. Beyond that, fork() for RDB/AOF becomes expensive (copy-on-write memory spike). Best for simplicity-first.
Horizontal (Cluster)
Add more shards. Linear throughput scaling. Key distribution via CRC16(key) mod 16384. Requires hash tags {prefix} for multi-key operations on same slot.
Read Replicas
Scale read throughput independently. Each replica serves reads at full throughput. Trade-off: eventual consistency (replication lag typically <1ms but unbounded under load).

Key Trade-offs

Consistency vs. Availability
Redis chooses availability (AP in CAP). Async replication means writes can be lost on failover. WAIT command trades latency for consistency. No true strong consistency in cluster mode.
Memory vs. Durability
RDB: lower memory overhead, periodic data loss risk. AOF everysec: max 1 second loss, more I/O. AOF always: no data loss but 10x slower writes. Most choose AOF everysec + RDB.
Throughput vs. Latency
Pipelining maximizes throughput but increases per-request latency. Background operations (RDB save, AOF rewrite) can cause latency spikes. Monitor with LATENCY HISTORY.
