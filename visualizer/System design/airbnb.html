Use Cases & Common Pitfalls

Primary Use Cases

🏠 Short-term Vacation Rentals

The core use case. 150M+ users searching/booking 7M+ listings across 220+ countries. Requires real-time availability, trust systems, and multi-currency payments.

💼 Long-term Stays (28+ days)

Monthly discounts, different cancellation policies, lease-like agreements. Requires different pricing models and host-guest communication patterns.

🌅 Experiences & Activities

Booking local activities hosted by locals. Different inventory model (time-slots with capacity), group bookings, weather-dependent cancellation.

🚚 Luxury / Airbnb Luxe

High-value bookings with concierge services. Requires manual verification, trip planning integration, higher trust bar.

Anti-Use Cases DON'T USE

Real-time Bidding / Auction

Airbnb uses fixed pricing (with smart suggestions). An auction model would require different consistency guarantees, real-time bidding infrastructure, and different UX patterns.

Instant Delivery / On-demand

Unlike Uber, Airbnb bookings aren't time-critical (usually days/weeks in advance). The architecture doesn't need sub-second matching or real-time driver tracking.

Common Pitfalls

⚠ Double-booking due to race conditions ▼

The mistake: Using simple database checks (SELECT then INSERT) without proper locking for calendar availability.

Why it happens: Works fine in testing with low concurrency but fails under real traffic with popular listings.

The consequence: Two guests book the same dates. One must be cancelled — terrible UX, potential revenue loss, and trust damage.

Fix: Use distributed locks (Redis SETNX) on the listing+date combo before availability check. Implement optimistic locking with version numbers as fallback. Use database-level constraints (UNIQUE on listing_id + date range using exclusion constraints in PostgreSQL).
⚠ Search index out of sync with booking state ▼

The mistake: Elasticsearch shows listings as available when they're already booked, because the index update is delayed.

Why it happens: CDC pipelines have inherent latency (seconds to minutes). Under high load, lag increases.

The consequence: Users see "available" listings, click through, and get an error. High bounce rate and frustration.

Fix: Dual-check: search for candidates in ES, then verify real-time availability against Redis/DB before showing results. Monitor CDC lag with alerts at >5s. Use short TTL cache for availability with cache-aside pattern.
⚠ Payment split failures leaving inconsistent state ▼

The mistake: Charging the guest and paying the host as a single atomic operation. If payout fails, the system is in a bad state.

Why it happens: Treating distributed payment as a local transaction. Different payment providers, different failure modes.

The consequence: Guest charged but host never paid. Or refund issued but host already paid out. Reconciliation nightmares.

Fix: Separate charge and payout into independent steps with a ledger in between. Guest charge goes to escrow. Host payout triggered only after check-in confirmation (or after a delay). Implement idempotent retry with exponential backoff for failed payouts.
⚠ N+1 queries in listing detail pages ▼

The mistake: Fetching listing details, then separately fetching host info, reviews, availability, pricing, similar listings — each as a separate API call.

Why it happens: Microservice boundaries create natural N+1 patterns when composing a page from multiple services.

The consequence: Page load > 3 seconds. Mobile users on slow connections abandon. SEO ranking drops.

Fix: GraphQL or BFF (Backend-for-Frontend) layer that batches and parallelizes service calls. Pre-compose listing detail into a denormalized cache (invalidated on changes). Use data loader pattern for batch resolution.
⚠ Not handling calendar timezone complexity ▼

The mistake: Storing and comparing dates in UTC without considering the listing's local timezone for check-in/check-out times.

Why it happens: "Just use UTC everywhere" is standard advice, but accommodation bookings are inherently local-time concepts.

The consequence: Off-by-one-day errors near midnight UTC. A booking for "March 5" might block "March 4" or "March 6" depending on timezone offsets. Guest arrives a day early/late.

Fix: Store availability as local dates (not timestamps) tied to the listing's timezone. All date comparisons happen in the listing's timezone. Display dates in the guest's timezone for UX but convert to listing timezone for availability checks.

Best Practices

Proven patterns for building a marketplace like Airbnb.

Design Phase

  • Define the trust model first — two-sided marketplaces live or die by trust between strangers
  • Separate read path (search, browse) from write path (booking, payment) — they scale differently
  • Design for eventual consistency in search but strong consistency in bookings
  • Plan multi-currency and multi-timezone from day one — retrofitting is extremely painful
  • Model the booking lifecycle as a state machine with clear transitions and rollback paths

Implementation

  • Use idempotency keys on all payment and booking mutations to handle retries safely
  • Implement circuit breakers between services — a payment provider outage shouldn't break search
  • Calendar availability: use date-range exclusion constraints in PostgreSQL (EXCLUDE USING gist)
  • Image pipeline: generate all size variants asynchronously, serve via CDN with content-negotiation (WebP/AVIF)
  • Search ranking: A/B test everything. Small ranking changes can shift millions in GMV

Operations

  • Monitor booking conversion funnel end-to-end: search → listing view → booking attempt → confirmation
  • Alert on search-to-book latency p99 — if booking takes >3s after payment, users abandon
  • Graceful degradation: disable personalized recommendations before disabling search; disable smart pricing before disabling bookings
  • Blue-green deployments for payment service — never take risks with money-handling code
  • Run chaos engineering: what happens when Redis is down? When ES cluster loses a node?

Scaling

  • Shard PostgreSQL by region initially (US, EU, APAC) — most queries are geo-local
  • Cache search results aggressively (30s TTL) — listing availability changes slowly relative to search QPS
  • Use read replicas for all read-heavy services (listing detail, user profiles, reviews)
  • Async everything that isn't user-blocking: emails, analytics events, recommendation updates
  • Pre-compute popular search results during off-peak hours and warm the cache

Failure Scenarios

Elasticsearch cluster down

Search is degraded but bookings still work. Fallback: serve cached popular results, disable filtering. Recovery: replica promotion, reindex from PostgreSQL via CDC.

Payment provider outage

New bookings fail at payment step. Existing bookings unaffected. Mitigation: multi-provider fallback (Stripe → Adyen), queue bookings for retry, show "try again" UX.

Redis cache failure

Session loss (users re-auth), search latency spikes (cache miss → DB), booking locks unavailable. Mitigation: Redis Cluster with replication, fall back to DB-level locks.
