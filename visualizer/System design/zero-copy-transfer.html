Zero-Copy Transfer

Eliminate redundant CPU-mediated data copies between kernel and user space to achieve maximum I/O throughput. The technique behind Kafka, Nginx, and modern network stacks.

Kernel Optimization sendfile() / splice() DMA Transfer Linux / Windows / BSD

Component Breakdown

The key hardware and software components that enable zero-copy data transfer.

DMA Engine (Direct Memory Access)

Purpose: Transfer data between device and memory without CPU involvement.

Key detail: Modern NICs with scatter/gather DMA can assemble packets from non-contiguous memory regions, eliminating the need for a single contiguous socket buffer.

Hardware

Page Cache (Kernel Buffer)

Purpose: Cache disk data in memory. In zero-copy, data stays here — never copied to user space.

Key detail: sendfile() tells the kernel to stream directly from page cache to the socket. The page cache becomes the single source of truth for the transfer.

Kernel Space

sendfile() System Call

Purpose: Transfer data between file descriptors entirely within kernel space.

Signature: sendfile(out_fd, in_fd, offset, count). Available on Linux 2.2+. On Linux 2.6.33+ with scatter-gather NIC, achieves true zero CPU-copy.

System Call

splice() / tee() System Calls

Purpose: Move data between two file descriptors where one is a pipe, without user-space transit.

Key detail: More flexible than sendfile() — works with pipes, sockets, and arbitrary FDs. Used by Nginx for proxied responses.

System Call

Memory-Mapped I/O (mmap)

Purpose: Map file contents directly into process address space, sharing pages with kernel cache.

Key detail: Eliminates one copy (kernel→user) but still requires CPU copy to socket buffer. Semi-zero-copy — good when you need to inspect/transform data.

Hybrid

NIC with Scatter-Gather

Purpose: Assemble outgoing packets from multiple non-contiguous memory buffers in a single DMA operation.

Key detail: Required for true zero-copy sendfile(). Without SG support, the kernel still copies to a contiguous socket buffer before DMA.

When to pick sendfile()

You're serving static content (files, logs, pre-computed data) over a network socket and don't need to inspect or modify the data in user space. The canonical use case.

When to pick splice()

You're proxying data between two sockets (reverse proxy) or piping between arbitrary FDs. More flexible than sendfile but requires a pipe as intermediary.

When to pick io_uring

You need async I/O with minimal syscall overhead at scale — database engines, high-QPS web servers. Worth the complexity only above ~100k ops/sec.

When to stick with read()/write()

You need to transform, compress, encrypt, or inspect data before sending. Zero-copy is impossible when the CPU must touch every byte. Use pipelining instead.

Real-World Examples

Apache Kafka

Uses sendfile() to transfer log segments directly from disk to consumer sockets. Key reason Kafka achieves GB/s throughput per broker.

Nginx

Uses sendfile for static files, splice() for proxied responses. Configurable via sendfile on; directive.

PostgreSQL (WAL shipping)

Streams WAL segments to replicas using zero-copy when available. Reduces replication lag under heavy write load.

Netty / Java NIO

FileChannel.transferTo() maps to sendfile() on Linux. Used by Cassandra, Elasticsearch, and Spark shuffle.

Use Cases & Common Pitfalls

Where zero-copy shines, where it doesn't, and mistakes to avoid.

Primary Use Cases

Static File Serving

Web servers delivering images, JS bundles, CSS, videos. Files don't change between disk and wire — perfect for sendfile().

~10-50% throughput improvement

Message Broker / Log Streaming

Kafka, Pulsar, and log shippers transfer immutable log segments. Data is appended once, read many times — zero-copy reads are a massive multiplier.

GB/s per broker

Database Replication

Shipping WAL/binlog segments from primary to replicas. The data must arrive bit-for-bit identical — no transformation needed.

Lower replication lag

CDN Edge Delivery

Edge nodes serve cached content to thousands of concurrent clients. Zero-copy + epoll = massive fan-out without CPU saturation.

High concurrency

Anti-Use-Cases

TLS/SSL Encrypted Transfer

Encryption requires reading and transforming every byte. Can't skip user-space. Use kTLS (kernel TLS) for partial zero-copy with encryption.

Compression On-The-Fly

gzip/brotli compression must process the data. Pre-compress files and then use sendfile() on the compressed version instead.

Small Payloads (< 16KB)

For tiny transfers, the syscall overhead of sendfile() vs read()+write() is negligible. The extra complexity isn't justified.

Common Pitfalls

Assuming sendfile() always means zero CPU copies ▼

The mistake: Using sendfile() and assuming you get zero-copy benefits regardless of hardware.

Why it happens: The man page says "zero-copy" but doesn't emphasize the NIC scatter-gather requirement.

The consequence: Without SG DMA, the kernel still copies from page cache to a contiguous socket buffer — you get 1 CPU copy instead of 0.

The fix: Check NIC capabilities with ethtool -k eth0 | grep scatter-gather. Most modern NICs (10GbE+) support it.

Using sendfile() when the file is being modified concurrently ▼

The mistake: Calling sendfile() on a file that another process is actively writing to.

Why it happens: Developers assume the kernel snapshots the file or provides isolation.

The consequence: Torn reads — the client receives a mix of old and new data. No atomicity guarantees.

The fix: Use immutable files (append-only logs with segment rotation like Kafka), or copy-on-write semantics, or take a read lock.

Forgetting that sendfile() doesn't work with all FD types ▼

The mistake: Trying to use sendfile() between two sockets or from a pipe.

Why it happens: The name "sendfile" implies any FD, but the input must be a file (or something with mmap support).

The consequence: EINVAL error at runtime, fallback to slow path.

The fix: Use splice() for socket→socket or pipe scenarios. On Linux, splice() is the generalized zero-copy primitive.

Not handling partial sendfile() returns ▼

The mistake: Assuming sendfile() transfers the entire requested count in one call.

Why it happens: With blocking sockets and small files, it usually does complete in one call.

The consequence: Under load or with non-blocking sockets, short writes cause data truncation.

The fix: Always loop on sendfile(), tracking the offset. Same pattern as write() — check return value, advance offset, retry.

Using mmap for sequential streaming (thinking it's zero-copy) ▼

The mistake: Using mmap + write() for streaming because "mmap avoids copies."

Why it happens: mmap does eliminate the read() copy, but people forget write() still copies to the socket buffer.

The consequence: Worse than sendfile() due to TLB shootdowns, page fault overhead, and the remaining CPU copy. Plus double the memory pressure.

The fix: For sequential streaming, always prefer sendfile(). Reserve mmap for random-access patterns where you read scattered portions of a large file.

Best Practices

Proven guidelines for implementing zero-copy transfer correctly and efficiently.

Design Phase

  • Separate data paths that need transformation from those that don't — only the untouched paths benefit from zero-copy
  • Design immutable data segments (like Kafka log segments) so sendfile() can operate without coordination
  • Verify NIC scatter-gather support in your target deployment environment before committing to the approach
  • Consider kTLS if you need both zero-copy and encryption — available on Linux 4.13+ with supported ciphers

Implementation

  • Always loop on sendfile()/splice() — handle short writes the same way you handle write()
  • Set TCP_CORK or TCP_NOPUSH before sendfile() to coalesce headers + file data into full-sized TCP segments
  • Use sendfile with offset tracking for resume/range-request support in HTTP servers
  • Benchmark against read()+write() baseline — zero-copy wins diminish below ~64KB transfers
  • For Java: use FileChannel.transferTo(), for Go: use io.Copy with *net.TCPConn (triggers splice), for Rust: use std::io::copy with appropriate types

Operations

  • Monitor /proc/vmstat for pgpgin/pgpgout — high values with low CPU indicate zero-copy is working
  • Watch for page cache pressure: cat /proc/meminfo | grep -i cache — sendfile() relies on warm page cache
  • Use perf stat to confirm CPU cycles aren't spent in copy_to_user/copy_from_user
  • Set appropriate readahead with blockdev --setra for sequential sendfile() workloads

Scaling

  • Combine with epoll/io_uring for high-concurrency: zero-copy handles throughput, async I/O handles connection count
  • Page cache size is your effective "zero-copy budget" — files that fit in cache benefit most
  • For files larger than RAM: use fadvise(SEQUENTIAL) + sendfile() in chunks to manage page cache pollution
  • On NUMA systems: pin threads to the NUMA node closest to the NIC for best DMA performance

Fundamental Trade-offs

Throughput vs. Flexibility

Zero-copy gives maximum throughput but you can't inspect, transform, or encrypt data in transit. If you need any processing, you lose zero-copy benefits.

Simplicity vs. Performance

read()+write() is trivial to implement and debug. sendfile() adds edge cases (partial writes, offset management, FD type restrictions). splice() adds pipe management.

Page Cache Dependency

Zero-copy relies on page cache. If your working set exceeds RAM, you get page faults that negate the benefit. Traditional buffered I/O gives more predictable performance for cold data.

Portability vs. Optimization

sendfile() semantics differ across Linux/BSD/macOS/Windows. splice() is Linux-only. io_uring is very new. Abstractions (like Java NIO) help but can't expose all features.

Failure Scenarios

Page cache eviction under memory pressure

If the system runs low on memory, page cache entries get evicted. Next sendfile() triggers disk I/O (page fault), dramatically increasing latency. Mitigation: monitor cache hit ratios, reserve memory for page cache.

NIC hardware failure / fallback to software path

If the NIC's SG engine fails or firmware bugs trigger a fallback, the kernel silently reverts to CPU copying. Performance drops without errors. Mitigation: monitor NIC stats, set performance alerts.

File truncation during sendfile()

If another process truncates the file mid-transfer, sendfile() may return short or signal an error depending on timing. Mitigation: use immutable segments or flock().
