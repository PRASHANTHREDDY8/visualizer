HTTP Methods — The Verbs of REST

GET Read

Retrieve a resource or collection. Must be safe and idempotent.

✓ Safe   ✓ Idempotent   ✓ Cacheable
@app.get("/api/v1/users/{user_id}") async def get_user(user_id: int): return await User.get(user_id)

POST Create

Create a new resource. Not idempotent — each call may create a new resource.

× Safe   × Idempotent   × Cacheable
@app.post("/api/v1/users", status_code=201) async def create_user(body: UserCreate): return await User.create(**body.dict())

PUT Replace

Full replacement of a resource. Client must send the complete representation.

× Safe   ✓ Idempotent   × Cacheable
@app.put("/api/v1/users/{user_id}") async def replace_user(user_id: int, body: UserUpdate): return await User.replace(user_id, body)

PATCH Partial Update

Partial modification. Only send changed fields. Use JSON Merge Patch or JSON Patch.

× Safe   × Idempotent*   × Cacheable
@app.patch("/api/v1/users/{user_id}") async def update_user(user_id: int, body: UserPatch): return await User.update(user_id, **body.dict(exclude_unset=True))

DELETE Remove

Remove a resource. Should be idempotent — deleting twice returns 204 or 404.

× Safe   ✓ Idempotent   × Cacheable
@app.delete("/api/v1/users/{user_id}", status_code=204) async def delete_user(user_id: int): await User.delete(user_id)

HEAD / OPTIONS

HEAD: Same as GET but no body — for checking existence or headers. OPTIONS: CORS preflight, discovering allowed methods.

✓ Safe   ✓ Idempotent

URL Design — Resource Naming

https:// api.example.com /v1 /users /42 /orders ?status=active&sort=-created_at&page=2&per_page=25
✓ Do This
GET /api/v1/users # collection GET /api/v1/users/42 # single resource GET /api/v1/users/42/orders # sub-resource POST /api/v1/users/42/orders # create under parent GET /api/v1/users?role=admin # filter with query params GET /api/v1/users?sort=-created_at # sort descending
× Don't Do This
GET /api/v1/getUsers # verb in URL GET /api/v1/user/42 # singular noun POST /api/v1/create-user # action in URL GET /api/v1/users/delete/42 # verb as path segment GET /api/v1/Users # uppercase GET /api/v1/user_orders # underscores instead of nesting

Standard Error Response (RFC 7807)

Consistent Error Envelope

{ "type": "https://api.example.com/errors/validation", "title": "Validation Error", "status": 422, "detail": "2 fields failed validation", "instance": "/api/v1/users", "errors": [ {"field": "email", "message": "Invalid format"}, {"field": "age", "message": "Must be >= 18"} ], "request_id": "req_a1b2c3d4" }

Python Implementation

from fastapi import HTTPException from fastapi.responses import JSONResponse @app.exception_handler(HTTPException) async def http_exc_handler(request, exc): return JSONResponse( status_code=exc.status_code, content={ "type": f"https://api.example.com/errors/{exc.status_code}", "title": exc.detail, "status": exc.status_code, "request_id": request.state.request_id, }, )

Pagination, Filtering & Versioning

Cursor vs Offset Pagination

# Offset (simple, suffers on large sets) GET /users?page=3&per_page=25 # Cursor (preferred for feeds/infinite scroll) GET /users?cursor=eyJpZCI6NDJ9&limit=25
Response envelope:
{ "data": [...], "meta": { "total": 1284, "next_cursor": "eyJpZCI6Njd9", "has_more": true } }

Filtering & Sorting

# Filter GET /users?status=active&role=admin # Date range GET /orders?created_after=2024-01-01 &created_before=2024-12-31 # Sort (- prefix for descending) GET /users?sort=-created_at,name # Field selection (sparse fields) GET /users?fields=id,name,email

API Versioning Strategies

# 1. URL path (most common, recommended) GET /api/v1/users GET /api/v2/users # 2. Header-based Accept: application/vnd.api.v2+json # 3. Query parameter GET /api/users?version=2
URL path versioning is the most explicit and cache-friendly approach. Use it unless you have a strong reason not to.

Comparisons with Alternatives

REST isn't the only game in town. Know when to use what.

Aspect REST FOCUS GraphQL gRPC WebSocket
Protocol HTTP/1.1 or HTTP/2 HTTP (single endpoint) HTTP/2 (binary) WS (persistent)
Data Format JSON (usually) JSON Protobuf (binary) Any (JSON, binary)
Typing OpenAPI/JSON Schema Built-in schema Proto definitions None built-in
Caching HTTP caching (ETags, CDN) Complex (requires custom) No HTTP caching Not applicable
Over/Under-fetching Possible (use sparse fields) Solved by design Solved by protobuf N/A
Real-time Polling / SSE Subscriptions Bidirectional streaming Native
Python Tooling FastAPI, Flask, DRF Strawberry, Ariadne grpcio, betterproto websockets, Socket.IO
Best For CRUD APIs, public APIs, microservices Complex UIs, mobile apps, BFF Internal services, high throughput Chat, live feeds, gaming

When to Pick Each

Choose REST when...

  • Building a public-facing API
  • Resources map to CRUD operations
  • HTTP caching is important
  • Team is diverse (REST is universal)
  • You need broad ecosystem support
Examples: GitHub, Stripe, Twilio

Choose GraphQL when...

  • Frontend needs flexible queries
  • Multiple clients with different data needs
  • Deep, nested relationships
  • Rapid frontend iteration
Examples: GitHub (v4), Shopify, Yelp

Choose gRPC when...

  • Internal service-to-service calls
  • High throughput, low latency needed
  • Strict contracts are essential
  • Streaming data (bidirectional)
Examples: Google Cloud, Netflix internal

Choose WebSocket when...

  • Real-time bidirectional communication
  • Live dashboards, collaborative editing
  • Push notifications (server-initiated)
  • Gaming, chat applications
Examples: Slack, Discord, Figma
Section 5

Use Cases & Common Pitfalls

Primary Use Cases for REST APIs

🌐 Public / Partner APIs

Stripe, Twilio, GitHub. REST is the lingua franca of web APIs. Easy to document with OpenAPI, easy to consume from any language.

Scale: 10K–1M+ requests/min

⚙ CRUD Microservices

User service, product catalog, order management. Resources map naturally to database entities. FastAPI + SQLAlchemy is the dominant Python stack.

Scale: 1K–100K requests/min per service

📱 Mobile Backends

REST + JSON is universally supported by iOS/Android HTTP clients. Use sparse fields and pagination for bandwidth efficiency on mobile.

Optimize: field selection, compression, caching headers

Anti-Use-Cases

REST is the wrong choice when…

Real-time bidirectional data

Chat apps, multiplayer games, live cursors. Use WebSockets or gRPC streaming instead. REST polling creates unnecessary load and latency.

Internal high-throughput RPC

Service-to-service at 100K+ TPS? gRPC with protobuf is 5–10x more efficient due to binary serialization and HTTP/2 multiplexing.

Common Pitfalls

Design Pitfalls

!
Using verbs in URLs instead of HTTP methods ▾
The mistake
POST /api/createUser or GET /api/deleteUser/42
Why it happens
RPC thinking carried from SOAP/XML-RPC. Feels natural for developers coming from function-call paradigms.
The consequence
Breaks REST semantics. Caches can't work properly. Clients can't predict behavior from conventions. You lose idempotency guarantees.
The fix
Use nouns for resources and HTTP methods for actions: POST /api/v1/users to create, DELETE /api/v1/users/42 to delete.
!
Returning 200 for everything with error in body ▾
The mistake
HTTP 200 {"success": false, "error": "User not found"}
Why it happens
Simpler error handling in naive implementations. Some teams fear that 4xx/5xx codes "break" clients.
The consequence
Monitoring tools can't detect failures. HTTP caches may cache errors. Clients need custom error-checking logic instead of using standard HTTP status code handling.
The fix
Use proper status codes: 404 for not found, 422 for validation errors, 500 for server errors. Every HTTP library has built-in status code handling.
!
Not implementing pagination from day one ▾
The mistake
GET /users returns all 500,000 users in one response.
Why it happens
"We only have 100 users right now, we'll add pagination later." But clients build against the unpaginated response.
The consequence
OOM errors, timeouts, and a breaking change when you finally add pagination. Clients built for the flat list break.
The fix
Always return paginated responses from the start: {"data": [...], "meta": {"total": 100, "page": 1, "per_page": 25}}
!
Exposing database schema directly as API schema ▾
The mistake
API response mirrors your SQLAlchemy model exactly, including password_hash, internal IDs, or join table columns.
Why it happens
Quick to implement — just serialize the ORM model. DRF's ModelSerializer makes this trivially easy.
The consequence
Leaks internal implementation details. Schema changes break the API. Security risk of exposing sensitive fields.
The fix
Use dedicated response schemas (Pydantic models in FastAPI, serializers in DRF). Treat the API contract as independent from the DB schema.

Implementation Pitfalls (Python-Specific)

!
N+1 queries in list endpoints ▾
The mistake
Fetching related objects inside a loop: for user in users: user.orders fires a query per user.
Why it happens
ORM lazy loading hides the actual SQL. Looks clean in Python but generates 1 + N queries.
The consequence
A list of 100 users fires 101 queries. Response time degrades linearly with collection size.
The fix
SQLAlchemy: selectinload(User.orders) or joinedload(). Django: select_related() / prefetch_related(). Always check queries in development with SQL logging.
!
Blocking I/O in async endpoints ▾
The mistake
Using requests.get() or synchronous DB calls inside an async def FastAPI endpoint.
Why it happens
Mixing sync and async code is easy when migrating from Flask to FastAPI. The code "works" but blocks the event loop.
The consequence
One slow I/O call blocks ALL concurrent requests on that event loop thread. Throughput drops to nearly synchronous levels.
The fix
Use httpx.AsyncClient instead of requests. Use async DB drivers (asyncpg, databases). Or use run_in_executor() for unavoidable sync code.
!
Not validating request bodies ▾
The mistake
Passing request.json directly to ORM without validation: User(**request.json)
Why it happens
Skipping validation to "move fast." Trusting that the client sends well-formed data.
The consequence
SQL injection, mass assignment vulnerabilities, type errors, data corruption. A client can set is_admin: true.
The fix
Always validate with Pydantic models (FastAPI) or serializers (DRF). Whitelist fields explicitly. Never trust client input.

Interview Pitfalls

?
Not distinguishing authentication vs authorization ▾
The mistake
Using "auth" to mean both, confusing 401 and 403, or not explaining the difference when asked about API security.
Why it happens
They're closely related and often conflated in casual discussion.
The consequence
Signals lack of security understanding. Leads to incorrect status code usage (401 for permission denied instead of 403).
The fix
Authentication = who are you? (401 if fails). Authorization = are you allowed? (403 if fails). JWT contains identity (authn); middleware checks permissions (authz).
?
Confusing PUT and PATCH ▾
The mistake
Using PUT for partial updates or PATCH for full replacement. Or only implementing one and calling it the other.
Why it happens
Many tutorials use them interchangeably. Django REST Framework uses the same serializer for both by default.
The consequence
PUT should be idempotent and replace the entire resource. Using it for partial updates breaks idempotency guarantees.
The fix
PUT: send the complete resource, server replaces it entirely. PATCH: send only changed fields using exclude_unset=True in Pydantic.
Section 6

Best Practices

Proven patterns for building production-grade REST APIs in Python.

Design Phase

API-First Design

  • Write OpenAPI spec before code — tools like openapi-generator generate client SDKs
  • Define resource models, endpoints, and error codes upfront
  • Get consumer feedback on the contract before building
  • Use Pydantic models as your single source of truth (FastAPI generates OpenAPI from them)

Consistent Response Envelopes

  • Wrap all responses: {"data": ..., "meta": ...}
  • Use RFC 7807 Problem Details for all errors
  • Always include request_id for debugging
  • Return created_at and updated_at in ISO 8601 with timezone

Implementation Phase (Python)

Security Essentials

  • Use HTTPS everywhere — no exceptions
  • JWT for stateless auth; rotate signing keys periodically
  • Rate limit by API key and IP: slowapi for FastAPI, flask-limiter for Flask
  • CORS: whitelist specific origins, never use * in production
  • Input validation on every endpoint (Pydantic, Marshmallow, or DRF serializers)
  • Never return stack traces in production error responses

Python-Specific Patterns

  • Use async def endpoints with asyncpg + httpx for I/O-bound workloads
  • Dependency injection for DB sessions, auth, and config (FastAPI's Depends())
  • Type hints everywhere — Pydantic validates at runtime
  • Middleware for cross-cutting concerns: logging, request ID, timing
  • Use structlog for JSON structured logging
  • Run with Uvicorn + Gunicorn in production: gunicorn -w 4 -k uvicorn.workers.UvicornWorker

Testing REST APIs

  • Use httpx.AsyncClient or TestClient for integration tests
  • Test every status code path: 200, 201, 400, 401, 403, 404, 422, 500
  • Test pagination boundaries and edge cases
  • Contract testing with schemathesis (auto-generates tests from OpenAPI)
  • Use factory_boy for test data, not fixtures
  • Always test with a real database (testcontainers-python)

Operational Best Practices

  • Health check endpoint: GET /health checks DB, cache, and dependencies
  • Structured JSON logs with request_id, latency, status_code, user_id
  • Metrics: p50/p95/p99 latency, error rate, request rate per endpoint
  • Graceful shutdown: handle SIGTERM, finish in-flight requests
  • Blue-green or canary deployments for zero-downtime
  • Database migrations with Alembic — always backward-compatible

Scaling & Trade-offs

How your REST API handles 10x, 100x, and 1000x growth.

Back-of-Envelope Estimation

# Assume: 10M DAU, 80/20 read-write ratio # Average user makes 20 API calls/day Total daily requests = 10M × 20 = 200M requests/day Avg QPS = 200M / 86400 ≈ 2,300 QPS Peak QPS (3x avg) = ~7,000 QPS # Read vs Write Read QPS = 7,000 × 0.8 = 5,600 QPS Write QPS = 7,000 × 0.2 = 1,400 QPS # Per server (FastAPI + Uvicorn, 4 workers, I/O bound) Capacity per server ≈ 500–2,000 QPS (depends on query complexity) Servers needed = 7,000 / 1,000 ≈ 7–14 servers (with headroom) # Bandwidth (avg response 2 KB) Bandwidth = 7,000 × 2 KB = 14 MB/s ≈ 112 Mbps

Scaling Strategies

▲ Horizontal Scaling

Add more API servers behind a load balancer. Stateless design (JWT, no server-side sessions) is key. This is the primary scaling lever for REST APIs.

◉ Caching Layers

CDN for static assets and cacheable GETs. Redis for frequently-read data. HTTP caching with ETags and Cache-Control headers. Can reduce DB load by 70–90%.

■ Read Replicas

Route GET requests to PostgreSQL read replicas. Write to primary. Use SQLAlchemy's bind_key or routing middleware for read/write splitting.

♦ Async Processing

Offload heavy operations (email, reports, image processing) to Celery workers via RabbitMQ/Redis. Return 202 Accepted with a status polling URL.

▶ Database Sharding

Shard by tenant_id or user_id for multi-tenant APIs. Use consistent hashing for even distribution. Consider at 100M+ rows.

▼ Rate Limiting & Backpressure

Token bucket per API key with Redis. Return 429 Too Many Requests with Retry-After header. Protect against abuse and cascading failures.

Key Trade-offs

Consistency vs Availability

Strong consistency (read-after-write) requires all reads go to primary DB. Eventually consistent reads from replicas give higher availability and lower latency. Choose per endpoint: user profile updates need consistency; analytics dashboards tolerate staleness.

Latency vs Throughput

Batching improves throughput but increases latency. Bulk endpoints (POST /users/batch) process many items but respond slower. Individual endpoints are faster per-request but less efficient for batch operations.

Simplicity vs Flexibility

Simple, opinionated APIs (fixed response format) are easier to cache and document. Flexible APIs (sparse fields, includes, filters) reduce round-trips but add complexity. Start simple, add flexibility when clients need it.

Security vs Developer Experience

Strict auth, rate limiting, and input validation add friction. But skipping them leads to breaches. Invest in great SDKs and documentation to make the secure path the easy path.

Failure Scenarios

Database goes down

Cached reads still work. Writes fail with 503. Connection pooling with pool_pre_ping=True detects and recovers. Auto-failover to standby with PgBouncer.

Traffic spike (10x normal)

Rate limiter protects backend. Auto-scaling adds API servers. CDN absorbs cacheable requests. Circuit breaker prevents cascade to downstream services.

Upstream service timeout

Set explicit timeouts on httpx calls (5s default). Use circuit breaker pattern (pybreaker). Return cached/default data with degraded flag. Never let one slow service block all requests.

Cache stampede

Popular cache key expires, 10,000 requests hit DB simultaneously. Fix: use probabilistic early expiration, lock-based cache refresh, or stagger TTLs. Redis SET NX for distributed locking.
