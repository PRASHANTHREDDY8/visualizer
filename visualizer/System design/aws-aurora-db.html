A cloud-native relational database that decouples compute from storage, delivering MySQL/PostgreSQL compatibility with up to 5x throughput improvement and automatic scaling.

1 Architecture Diagram

Aurora's key innovation: decoupling compute (SQL processing) from storage (data persistence), connected by a purpose-built distributed storage layer across 3 Availability Zones.

2 Component Breakdown

Aurora re-architects the database engine to push durability and replication into a purpose-built storage service, dramatically simplifying the compute layer.

Primary (Writer) Instance

Handles all DDL and DML write operations. Only one writer exists per cluster (except Multi-Master mode).

MySQL 8.0 / PG 16 InnoDB-based Crash Recovery <30s

The writer only sends redo log records (not data pages) to storage. This reduces network I/O by ~7x compared to traditional MySQL replication.

Vertical scaling: up to db.r6g.16xlarge (512GB RAM, 64 vCPU). Failover promotes replica in ~30s.

Read Replicas (up to 15)

Serve read queries from the shared storage volume. Zero-cost replication — no data transfer between writer and replicas.

Sub-10ms Lag Shared Storage Auto-failover Target

Replicas observe redo log updates from the storage layer. Buffer cache invalidation is near-instant because logs are applied at the storage layer, not replicated at the engine level.

Horizontal read scaling. Aurora Auto Scaling adds/removes replicas based on CPU or connection metrics.

Distributed Storage Volume

A shared, fault-tolerant, self-healing storage system spanning 3 AZs with 6-way replication.

6-copy Replication 10GB Segments Auto-grows to 128TB

Data is divided into 10GB "protection groups". Writes require 4/6 quorum, reads 3/6. Self-heals by detecting and repairing corrupt segments using peer copies. Log-structured — no checkpoint I/O storms.

Storage auto-scales in 10GB increments. You only pay for what you use. No pre-provisioning needed.

Cluster Endpoints

DNS-based endpoints that abstract instance topology. Writer endpoint, reader endpoint, and custom endpoints.

Auto-failover DNS TTL 5s Custom Endpoints

Cluster endpoint always resolves to the current writer. Reader endpoint round-robins across replicas. Custom endpoints let you route specific workloads to specific instance sizes.

RDS Proxy adds connection pooling, multiplexing, and graceful failover handling for serverless workloads.

Continuous Backup to S3

Redo log records are continuously streamed to S3, enabling point-in-time recovery (PITR) to any second.

PITR to 1-second 35-day Retention Zero-impact

Unlike traditional RDS which takes periodic EBS snapshots, Aurora's backup is truly continuous. Restoring creates a new cluster and replays logs to the target timestamp.

Backups have zero performance impact on the database. Cross-region backup replication available.

Aurora Serverless v2

Scales compute capacity in fine-grained (0.5 ACU) increments based on workload demand, in milliseconds.

0.5-256 ACU Millisecond Scaling Pay-per-use

Unlike Serverless v1 (which paused/resumed), v2 never goes to zero — it scales smoothly within a range you define. Ideal for variable workloads that can't tolerate cold starts.

Mix provisioned and serverless instances in the same cluster for cost optimization.

Choose Aurora when...

You need high OLTP throughput with MySQL/PG compatibility, want automatic storage scaling without managing shards, and your workload is single-region or single-writer with many readers.

Choose RDS when...

Your workload is <10K TPS, budget is constrained, you need 100% engine compatibility (e.g., specific MySQL plugins), or your read replica lag tolerance is generous (seconds).

Choose CockroachDB/Spanner when...

You need multi-region active-active writes with strong consistency, global user base requiring low-latency local writes, or you're building financial/regulatory systems.

Choose PlanetScale/Vitess when...

You've outgrown single-node MySQL and need horizontal write scaling with sharding, want non-blocking schema changes, or have a multi-tenant SaaS architecture.

5 Use Cases & Common Pitfalls

Where Aurora excels, where it doesn't, and mistakes to avoid.

Primary Use Cases

High-Throughput OLTP

E-commerce orders, banking transactions, gaming leaderboards. 100K+ TPS with predictable latency. Aurora's log-structured storage eliminates checkpoint I/O storms.

Read-Heavy Applications

Content platforms, social feeds, reporting dashboards. 15 read replicas with sub-10ms lag. Reader endpoint auto-distributes connections.

Variable / Bursty Workloads

SaaS platforms with unpredictable traffic, seasonal spikes. Serverless v2 scales 0.5-256 ACU in milliseconds without connection drops.

Dev/Test Environments (Cloning)

Instant production clones using copy-on-write. A 1TB database clones in seconds for pennies. Teams get isolated full-fidelity environments.

Anti-Use-Cases

Multi-Region Active Writes

Aurora is single-writer (except Global Database for DR). If you need active-active multi-region writes, use CockroachDB or DynamoDB Global Tables instead.

Analytics / OLAP Workloads

Column-oriented queries on TBs of data don't benefit from Aurora's row-store. Use Redshift, Athena, or ClickHouse for analytics. Aurora is OLTP-optimized.

Cost-Sensitive Low-Traffic Apps

A blog doing 10 QPS doesn't need Aurora's architecture. The minimum cost (~$60/mo for smallest instance + storage) is overkill. Use RDS or even SQLite.

Common Pitfalls

Not configuring reader endpoint correctly ▼
The Mistake
Sending all traffic (including reads) to the cluster/writer endpoint, leaving read replicas idle.
Why It Happens
Default connection strings in ORMs point to the writer endpoint. Devs don't realize there's a separate reader endpoint.
The Consequence
Writer instance gets overloaded with reads, replicas are wasted money, and you lose Aurora's biggest scaling advantage.
The Fix
Configure your app with two connection pools: writer endpoint for mutations, reader endpoint for queries. Use RDS Proxy for seamless read/write splitting.
Assuming zero replica lag means strong consistency ▼
The Mistake
Reading from a replica immediately after a write and expecting to see the new data, treating sub-10ms lag as zero lag.
Why It Happens
Marketing says "sub-10ms lag" so devs assume reads-after-writes are safe on replicas.
The Consequence
Stale reads in critical flows — e.g., user updates profile, refreshes page (hits replica), sees old data.
The Fix
For read-after-write consistency, either read from the writer endpoint for those specific queries, or use Aurora's "reader endpoint affinity" with session-level consistency (PostgreSQL only via aurora_replica_read_consistency).
Over-provisioning instance size instead of adding replicas ▼
The Mistake
Scaling up to a massive instance (db.r6g.16xlarge) when the workload is read-heavy, instead of distributing reads across replicas.
Why It Happens
Vertical scaling is simpler operationally — just change instance class. Adding replicas requires connection pool changes.
The Consequence
10x higher cost for marginal gains. A single r6g.16xl costs ~$7K/mo vs. multiple r6g.large at ~$150/mo each.
The Fix
Profile your workload. If >60% reads, add replicas behind the reader endpoint. Only scale vertically for write-bound workloads that can't be sharded.
Not setting up Aurora Global Database for disaster recovery ▼
The Mistake
Relying solely on single-region 3-AZ replication for critical production databases.
Why It Happens
"3 AZs is good enough" — teams underestimate the probability of a full region outage.
The Consequence
During a region failure, RTO is hours (restore from S3 cross-region) instead of minutes.
The Fix
For critical workloads, configure Aurora Global Database. Storage-level replication to a secondary region with <1 second lag and ~1 minute failover time.
Ignoring connection management in serverless/Lambda architectures ▼
The Mistake
Each Lambda invocation opens a new DB connection without pooling, exhausting Aurora's max_connections limit.
Why It Happens
Lambda's stateless model doesn't naturally lend itself to persistent connections.
The Consequence
"Too many connections" errors at scale. Aurora's connection limit depends on instance memory — a db.r6g.large supports ~1,000 connections.
The Fix
Use RDS Proxy. It multiplexes thousands of Lambda connections into a small pool of actual DB connections, handles credentials rotation, and enables graceful failover.

6 Best Practices

Proven practices for designing, implementing, and operating Aurora clusters in production.

Design Phase

  • Define read/write ratio upfront — this determines replica count and instance sizing strategy
  • Plan endpoint strategy: cluster (writes), reader (reads), custom (analytics/reporting on larger instances)
  • Choose between provisioned, Serverless v2, or mixed mode based on workload predictability
  • Set failover priority tiers: ensure at least one replica in a different AZ matches the writer's instance class
  • Design for Aurora's 64TB (MySQL) / 128TB (PostgreSQL) storage limit per cluster — plan sharding strategy if you'll exceed this

Implementation

  • Use separate connection pools for writer and reader endpoints in application code — never route reads to the writer by default
  • Enable Aurora Parallel Query for mixed OLTP/analytical queries — offloads scanning to the storage layer
  • Use aurora_replica_read_consistency = 'session' (PG) when you need read-your-writes consistency from replicas
  • Implement exponential backoff with jitter for connection retries during failover (DNS propagation takes up to 5s)
  • Use Aurora cloning for staging environments — instant, cost-effective, full-fidelity copies
  • Enable Performance Insights and Enhanced Monitoring from day one — they're essential for diagnosing lock contention and I/O patterns

Operations

  • Monitor: AuroraReplicaLag, DatabaseConnections, BufferCacheHitRatio, DMLLatency, StorageNetworkThroughput
  • Alert on replica lag >100ms — it indicates storage pressure or long-running transactions blocking garbage collection
  • Schedule maintenance windows during low-traffic periods — Aurora applies patches one replica at a time with automatic failover
  • Test failover quarterly: aws rds failover-db-cluster — verify your app handles the 5-second DNS TTL and reconnects cleanly
  • Enable deletion protection on production clusters — prevents accidental DELETE via console/API
  • Configure backup retention to maximum (35 days) for production — the cost is minimal and PITR saves you during incidents

Scaling

  • Use Aurora Auto Scaling with CPU or connection count targets to dynamically add/remove read replicas
  • For write scaling beyond a single instance: consider Aurora Multi-Master (limited use cases) or application-level sharding with multiple Aurora clusters
  • Deploy Aurora Global Database for cross-region scaling: storage-level replication with <1s lag to up to 5 secondary regions
  • Use Serverless v2 for unpredictable burst capacity instead of over-provisioning — set min ACU to handle baseline, max for peaks
  • Move reporting/analytics queries to a dedicated custom endpoint pointing to larger replica instances — isolate OLTP from analytics load

Key Trade-offs

Consistency vs. Read Throughput

Reading from writer gives strong consistency but limits throughput. Replicas give massive scale but eventual consistency (sub-10ms lag).

Strong Consistency Max Throughput

Aurora leans right — optimized for read scale with "good enough" consistency for most use cases.

Cost vs. Availability

Single instance is cheapest. Multi-AZ replicas add cost but enable 99.99% SLA. Global Database adds cross-region DR but doubles storage cost.

Low Cost High Availability

Multi-AZ replicas are the sweet spot for most production workloads (99.99% SLA).

Vendor Lock-in vs. Managed Simplicity

Aurora's proprietary storage layer is what makes it fast but it's AWS-only. Standard MySQL/PG lets you migrate freely but you lose Aurora's advantages.

Portability Performance

Aurora heavily favors performance. Mitigate lock-in by using standard SQL and avoiding Aurora-specific features where possible.

Write Scale vs. Architecture Simplicity

Single-writer is simple and consistent. Multi-writer or sharding across clusters adds write scale but introduces conflict resolution and routing complexity.

Simplicity Write Scale

Aurora chooses simplicity — single writer with fast failover. Application sharding is the escape hatch for extreme write workloads.

Failure Scenarios

Writer Instance Crash

Aurora promotes a replica within ~30 seconds. No data loss — all committed writes are durable in the storage layer. DNS endpoint updates with 5s TTL.

Single AZ Failure

Storage quorum (4/6) is maintained with 2 AZs. Reads continue (3/6 quorum). Writer fails over if in the affected AZ. Self-healing re-replicates lost copies.

Two AZ Failure

Read quorum (3/6) may be lost. Writes fail (need 4/6). Aurora pauses until AZs recover. Global Database enables cross-region failover for this scenario.

Storage Segment Corruption

Detected via checksums on every read. Corrupt segment is reconstructed from peer copies automatically. No application impact — transparent self-healing.
