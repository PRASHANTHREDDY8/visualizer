A real-time, multi-layered system that evaluates transactions in milliseconds using rule engines, ML models, and behavioral analytics — balancing security with customer experience.

Component Breakdown

API Gateway Entry Point

Single entry point that authenticates all transaction requests, applies rate limiting, and routes to the event stream.

  • Tech: Kong / AWS API Gateway with custom auth plugin
  • Latency budget: <5ms overhead
  • Scales: Horizontally via DNS round-robin + auto-scaling group

Event Stream Backbone

Kafka cluster handling 100K+ transactions/sec with per-customer ordering guarantees and 7-day retention.

  • Tech: Apache Kafka with 64 partitions, key=customer_id
  • Guarantees: At-least-once delivery, exactly-once with idempotent consumers
  • Scales: Add partitions + brokers; consumer groups for parallel processing

Rule Engine Real-time

Deterministic, low-latency rules catching known fraud patterns: velocity checks, blacklisted merchants, geo-fencing.

  • Tech: Drools / custom DSL with hot-reload (no redeploy for rule updates)
  • Latency: <2ms per transaction
  • Decision: Hard block (immediate decline) or soft flag (pass to ML)

ML Scoring Engine Core

Ensemble of XGBoost (tabular features) + Neural Network (sequence patterns) producing a 0–1 fraud probability.

  • Tech: TensorFlow Serving + XGBoost on GPU-backed instances
  • Latency: p99 <15ms for ensemble inference
  • Scales: Horizontal pod autoscaling; A/B test shadow models

Behavioral Analytics Profile

Builds per-customer spending profiles and detects deviations in amount, timing, location, and merchant category.

  • Tech: Flink streaming jobs computing rolling statistics
  • Features: Avg spend, time-of-day histogram, geo-radius, merchant clusters
  • Window: 1hr, 24hr, 7-day, 30-day rolling windows

Graph Analysis Network

Detects fraud rings by traversing entity relationships — shared devices, phone numbers, addresses between accounts.

  • Tech: Neo4j with real-time edge updates from event stream
  • Queries: 2-hop neighborhood, community detection, shortest path to known fraud
  • Latency: p99 <50ms for 2-hop traversal

Decision Orchestrator Critical

Aggregates all signals (rule score, ML score, behavioral anomaly, graph risk) and applies configurable policy thresholds.

  • Logic: Weighted combination with override rules for VIP/high-value
  • Outcomes: APPROVE (score<0.3), REVIEW (0.3–0.7), DECLINE (score>0.7)
  • SLA: End-to-end decision in <100ms

Feature Store Speed

Redis cluster providing sub-millisecond access to pre-computed features: velocity counts, device fingerprints, merchant risk scores.

  • Tech: Redis Cluster with read replicas, TTL-based expiry
  • Features: 200+ features computed from streaming + batch pipelines
  • Refresh: Real-time for velocity; hourly batch for aggregates

Comparisons with Alternatives

Approach Key Idea Pros Cons Best For
Hybrid (Rules + ML + Graph) ✓ Multi-layered: deterministic rules for known patterns, ML for novel fraud, graph for ring detection Highest accuracy; catches known + unknown fraud; explainable rules satisfy regulators Complex to build/maintain; higher infrastructure cost; requires ML + domain expertise Large banks with diverse transaction types and regulatory requirements
Rules-Only Expert-authored rules: velocity checks, blacklists, geo-fencing, amount thresholds Simple to understand and audit; deterministic; instant deployment of new rules Can't catch novel fraud; high false positive rate; rule sprawl becomes unmaintainable Small banks, early-stage systems, or as a first layer before adding ML
ML-Only (Supervised) Single ML model (gradient boosting or deep learning) trained on labeled fraud data Adapts to new patterns automatically; lower false positives than rules alone Black-box decisions hard to explain; needs large labeled dataset; cold start problem Fintech with strong data science team and sufficient labeled historical data
Unsupervised Anomaly Detect outliers without labels using Isolation Forest, Autoencoders, or clustering No labeled data needed; catches zero-day fraud; complementary to supervised models High false positive rate; hard to tune thresholds; less precise than supervised New markets with no fraud history, or as supplementary layer for novel attack detection

When to Pick Each

Choose Hybrid when…

You process >10K TPS, face regulatory scrutiny (need explainability), and have both known fraud patterns and novel attack vectors.

Examples: JPMorgan, HSBC, Stripe

Choose Rules-Only when…

You're a small bank with <1K TPS, limited data science resources, and need to ship fraud prevention in weeks not months.

Examples: Community banks, early-stage neobanks

Choose ML-Only when…

You have rich labeled data (>100K labeled fraud cases), a mature data platform, and customers tolerant of occasional false positives.

Examples: PayPal, Square (early days)

Choose Unsupervised when…

Entering a new market with no historical fraud labels, or detecting insider threats where labeled data doesn't exist.

Examples: Crypto exchanges, emerging market banks

Use Cases & Common Pitfalls

Primary Use Cases

Card-Not-Present (CNP) Fraud

Online purchases with stolen card numbers. Highest fraud rate channel (~65% of card fraud).

High Volume

Account Takeover (ATO)

Unauthorized access via credential stuffing or SIM swap. Behavioral biometrics critical.

Growing Threat

Wire Transfer Fraud

Business email compromise or social engineering leading to large unauthorized transfers.

High Impact

Money Laundering

Layering transactions to obscure illicit fund origins. Graph analysis excels here.

Regulatory

Synthetic Identity Fraud

Manufactured identities combining real + fake data to open accounts and build credit.

Long-term

First-Party / Friendly Fraud

Legitimate cardholders disputing valid charges. Requires different signals than third-party fraud.

Complex

Common Pitfalls

Treating fraud detection as a batch process ▼
The Mistake
Running fraud models on nightly batches instead of real-time scoring.
Why It Happens
Batch ML pipelines are easier to build and require less infrastructure investment.
The Consequence
Fraud detected 12-24 hours after occurrence — funds already withdrawn, chargebacks filed.
The Fix
Stream processing (Kafka + Flink) with sub-100ms inference. Batch for retraining only.
Optimizing only for fraud catch rate, ignoring false positives ▼
The Mistake
Setting model thresholds to catch 99%+ of fraud without measuring impact on legitimate customers.
Why It Happens
Fraud losses are visible (chargebacks), but revenue lost from declined legitimate transactions is invisible.
The Consequence
10:1 false-positive ratio means 10 good customers blocked for every fraudster caught. Customer churn, brand damage.
The Fix
Track and optimize for precision-recall trade-off. Target <1% false positive rate. Use dollar-weighted metrics.
Not accounting for concept drift in ML models ▼
The Mistake
Training a model once and deploying it indefinitely without monitoring performance degradation.
Why It Happens
Model performs well at launch; degradation is gradual and not immediately obvious.
The Consequence
Fraud patterns evolve (adversarial adaptation), model accuracy drops 20-40% within 3-6 months.
The Fix
Weekly model retraining with fresh labels. Monitor precision/recall daily. Champion-challenger deployment.
Building a single monolithic fraud model ▼
The Mistake
One model for all transaction types (card, wire, ACH, P2P) and all fraud types.
Why It Happens
Simpler architecture, less operational overhead, single team can own it.
The Consequence
Model underperforms on each channel because feature distributions differ massively. Wire fraud and CNP fraud share almost no features.
The Fix
Specialized models per channel/fraud type with a shared feature platform. Ensemble at the orchestration layer.
Ignoring feedback loop bias (label delay problem) ▼
The Mistake
Only labeling declined transactions as fraud, never seeing fraud in approved transactions.
Why It Happens
You only discover fraud in approved transactions when customers report it — sometimes weeks later.
The Consequence
Model becomes overconfident about approved transactions. Selection bias leads to progressively worse recall.
The Fix
Random approval sampling (let a small % of flagged transactions through), use chargeback data, and employ semi-supervised labeling.
No model explainability for regulatory compliance ▼
The Mistake
Using deep learning models without explainability layers, then failing regulatory audits.
Why It Happens
Deep learning models often outperform interpretable models in accuracy metrics.
The Consequence
Regulators require explanation for adverse actions (declining transactions). Unexplainable decisions violate fair lending laws.
The Fix
SHAP values for feature importance, rules layer for hard compliance checks, model cards documenting bias testing.

Best Practices

Design Phase

  • Define latency SLA upfront (<100ms end-to-end for real-time scoring)
  • Separate synchronous (real-time decision) from async (investigation, reporting) paths
  • Design for explainability from day 1 — regulators will ask "why was this declined?"
  • Plan for adversarial adaptation — fraudsters evolve faster than quarterly model releases
  • Build channel-specific models, not one-size-fits-all

Implementation

  • Feature store with dual-write: real-time (Redis) + batch (data lake) for consistency
  • Idempotent scoring — same transaction, same features = same score (deterministic)
  • Shadow scoring: run new models in parallel without affecting production decisions
  • Circuit breakers on ML service — fall back to rules if model latency exceeds SLA
  • Immutable audit log of every decision with full feature vector for replay

Operations

  • Alert on precision/recall drift, not just model accuracy (class imbalance makes accuracy misleading)
  • Monitor false positive rate by customer segment — avoid disproportionate impact on demographics
  • Canary deploys for model updates: 1% → 5% → 25% → 100% traffic rollout
  • Weekly model retraining with 30-day rolling labeled data
  • Runbooks for model degradation: auto-fallback to previous champion model

Scaling

  • Partition Kafka by customer_id for ordering guarantees without global coordination
  • Shard feature store by customer segment; hot customers (VIP) on dedicated Redis nodes
  • Pre-compute expensive graph queries; cache community membership scores with 5-min TTL
  • Horizontally scale ML inference with GPU-backed pods; batch requests for throughput
  • Cold-tier historical data to S3/Iceberg; keep only 90 days hot for real-time features

Scaling & Trade-offs

📊 Capacity Estimation

MetricValue
Daily transactions~500M (large bank)
Peak TPS~15,000 (Black Friday)
Avg transaction size~2KB enriched event
Daily ingestion~1TB raw events
Feature store~50M customers × 200 features = 100GB
Model inference15K inferences/sec × 15ms = 225 GPU-seconds/sec

📈 Growth Strategy

  • 10x (5K→50K TPS): Add Kafka partitions, scale inference horizontally, shard feature store
  • 100x (50K→500K TPS): Multi-region deployment, tiered scoring (fast rules filter 80%, only 20% hit ML), batch ML for cold-path
  • 1000x: Edge scoring at POS terminals, federated models per region, approximate features

⚖️ Key Trade-offs

  • Latency vs Accuracy: More models = better accuracy but higher latency. Budget: rules (2ms) + ML (15ms) + graph (50ms) = 67ms. Dropping graph saves 50ms but misses fraud rings.
  • False Positives vs False Negatives: Tighter thresholds catch more fraud but block more legitimate customers. $1 fraud blocked costs ~$0.50 in customer friction.
  • Freshness vs Cost: Real-time features are expensive (Redis). Stale features (hourly batch) are cheap but miss velocity patterns.

💥 Failure Scenarios

  • ML service down: Circuit breaker activates → fall back to rule engine only. Accept higher false positive rate temporarily.
  • Feature store unavailable: Use default/zero features → model outputs high uncertainty → route to manual review queue.
  • Kafka lag spike: Transactions queue up → prioritize high-value transactions for real-time scoring, batch the rest.
  • Graph DB timeout: Skip graph analysis, score without network signals. Alert ops team for investigation.
