Section 04

Comparisons with Alternatives

How AWS Glue compares to other data integration solutions

Approach Key Idea Pros Cons Best For
AWS GlueChosen Serverless, managed Spark ETL with auto-schema discovery No infra management, pay-per-use, integrated Data Catalog, auto-scaling Cold start latency, limited language support (Python/Scala), vendor lock-in AWS-native workloads, schema evolution, catalog-driven pipelines
Apache Airflow (MWAA) DAG-based orchestration with pluggable operators Flexible orchestration, rich ecosystem, open-source Orchestrator not processor, requires separate compute, operational overhead Complex multi-step pipelines, hybrid/multi-cloud
AWS EMR Managed Hadoop/Spark clusters with full control Full Spark control, persistent clusters, broad ecosystem (Hive, Presto, Flink) Cluster management, cost when idle, longer setup Large-scale processing, custom Spark tuning, long-running workloads
Databricks Unified analytics with optimized Spark and Delta Lake Superior performance (Photon), collaborative notebooks, Delta Lake built-in Higher cost, separate billing, not natively AWS-integrated Data science + engineering unified, lakehouse architecture

When to Pick Each

  • AWS Glue when you need serverless ETL tightly integrated with S3, Redshift, and the AWS ecosystem
  • Airflow when you need complex workflow orchestration across heterogeneous systems
  • EMR when you need full cluster control, custom libraries, or persistent Spark sessions
  • Databricks when you need unified data engineering + science with Delta Lake

Real-World Examples

  • Netflix uses Spark on EMR for large-scale content analytics
  • Lyft uses Airflow + custom operators for ride data pipelines
  • Shell uses Databricks for IoT sensor data processing
  • Capital One uses AWS Glue for regulatory data transformations
Section 05

Use Cases & Common Pitfalls

Where AWS Glue shines and where teams commonly stumble

Use Cases
Common Pitfalls

Primary Use Cases

📊 Data Lake ETL

Extract from RDS/DynamoDB, transform with Spark, load into S3-based data lake in Parquet/ORC format. Scale: 100GB-10TB daily.

🔍 Schema Discovery & Cataloging

Crawlers auto-detect schema across S3, JDBC sources, and streaming. Maintains a centralized Hive-compatible metastore.

🚀 Data Warehouse Loading

Transform and load data into Redshift, cleaning and deduplicating along the way. CDC support via bookmarks.

⚡ Real-time Streaming ETL

Process Kinesis/Kafka streams with micro-batch windows. Useful for near-real-time analytics and enrichment.

Anti-Use-Cases

❌ Sub-second Latency

Glue jobs have cold start of 30-90s. Use Lambda, Kinesis Analytics, or Flink for real-time (<1s) processing.

❌ Small File Processing

Spark overhead makes Glue inefficient for many tiny files. Use Lambda or Step Functions for file-at-a-time processing.

Section 07

Scaling & Trade-offs

Capacity planning and architectural trade-offs for AWS Glue pipelines

Capacity Estimation

DPU (Data Processing Unit): 4 vCPUs + 16GB RAM

Throughput: ~50-100 GB/hour per 10 DPUs (varies by transform complexity)

Cost: $0.44/DPU-hour (standard), $0.29/DPU-hour (flex)

Min billing: 1 minute (Glue 2.0+), 10 minutes (Glue 0.9/1.0)

Scaling Strategies

10x data growth:
Increase max DPUs, enable auto-scaling, optimize partitioning
100x data growth:
Split into multi-stage workflows, consider EMR for largest jobs, add Glue Flex for non-urgent loads
1000x data growth:
Hybrid: Glue for orchestration + catalog, EMR/Databricks for heavy compute, Redshift for serving

Trade-off Analysis

Cost vs. Latency: Flex execution is 34% cheaper but can be delayed up to 20 minutes during peak demand

Simplicity vs. Control: Glue abstracts Spark but limits tuning options vs. self-managed EMR

Freshness vs. Cost: Streaming Glue provides seconds of latency but costs more than hourly batch jobs

Vendor Lock-in vs. Productivity: Deep AWS integration accelerates development but makes multi-cloud harder

Failure Scenarios

DPU capacity exhausted: Jobs queue until DPUs free up. Mitigation: use Flex for non-critical jobs, request limit increases.

S3 throttling (503s): Too many requests to same prefix. Mitigation: randomize prefixes, use S3 request metrics.

OOM on driver: Too much data collected to driver. Mitigation: avoid collect(), increase driver memory class.

Schema drift breaks jobs: Source adds/removes columns. Mitigation: DynamicFrames + schema evolution in Catalog.
