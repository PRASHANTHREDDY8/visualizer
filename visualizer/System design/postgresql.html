Component Breakdown

⚙

Postmaster

The main supervisor daemon. Listens on port 5432, authenticates connections, and forks a dedicated backend process per client. Manages shared memory initialization and signal handling.

Process-per-connection fork() pg_hba.conf auth
▶

Backend Process

One per connection. Runs the full query lifecycle: parsing SQL into a parse tree, rewriting with rules, optimizing via the cost-based planner, and executing the chosen plan.

Parser (Bison/Flex) Planner/Optimizer Executor
▦

Shared Buffers

The primary data cache — stores 8KB pages read from disk. Uses a clock-sweep algorithm for eviction. Recommended: 25% of total RAM. All backends read/write through this layer.

8KB pages Clock-sweep Buffer pins
✎

WAL (Write-Ahead Log)

Guarantees durability and crash recovery. Every change is logged before being applied. WAL is also the foundation for streaming replication and point-in-time recovery (PITR).

16MB segments LSN tracking fsync
♻

Autovacuum

Reclaims storage from dead tuples left by MVCC. Also updates the `pg_statistic` catalog for the query planner. Critical for preventing table bloat and transaction ID wraparound.

Dead tuple cleanup ANALYZE XID wraparound prevention
⇄

Connection Pooler

PgBouncer or Pgpool-II sits between clients and PostgreSQL to multiplex connections. Essential for high-connection-count workloads since each PG backend uses ~5-10MB RSS.

Transaction pooling Session pooling Statement pooling

Use Cases & Common Pitfalls

Primary Use Cases

PRIMARY

Financial / Transactional Systems

ACID guarantees, serializable isolation, and row-level locking make PG ideal for banking, payment processing, and ledger systems where correctness is non-negotiable.

PRIMARY

SaaS Multi-Tenant Applications

Row-Level Security (RLS), schemas for tenant isolation, and connection pooling handle multi-tenancy elegantly. Used by Citus for distributed multi-tenant workloads.

PRIMARY

Geospatial / GIS Applications

PostGIS extension adds spatial indexing (R-tree via GiST), geometry types, and geospatial queries. The gold standard for location-based services and mapping.

PRIMARY

Analytics & Data Warehousing

Window functions, CTEs, materialized views, parallel query, and partitioning support hybrid OLTP+OLAP. Extensions like TimescaleDB add time-series capabilities.

Anti-Use-Cases

AVOID

Simple Key-Value Cache

If you only need fast K/V lookups with TTL, Redis or Memcached are 10-100x faster. PG's MVCC overhead is wasted on this pattern.

AVOID

High-Write Append-Only Logs

For pure event streams at millions of writes/sec, use Kafka or ClickHouse. PG's row storage and vacuum make this pattern expensive.

AVOID

Graph Traversals (deep joins)

While recursive CTEs work for small graphs, deep traversals (6+ hops) across billions of edges are better served by Neo4j or DGraph.

Best Practices

⚙ Configuration

  • Set shared_buffers to 25% of RAM (never more than 8GB on most systems)
  • Set effective_cache_size to 75% of RAM — guides planner cost estimates
  • Set work_mem conservatively (4-64MB) — it's per-sort/hash-operation, not per-query
  • Use random_page_cost = 1.1 on SSDs (default 4.0 assumes spinning disks)
  • Enable huge_pages = try on Linux for shared buffer efficiency

🔍 Indexing

  • Create indexes on columns used in WHERE, JOIN, and ORDER BY — but not on every column
  • Use partial indexes for filtered queries: CREATE INDEX ... WHERE status = 'active'
  • Use covering indexes (INCLUDE) to enable index-only scans
  • Monitor unused indexes with pg_stat_user_indexes — they slow writes for no benefit
  • Use CONCURRENTLY for creating indexes on production tables without locking

📈 Monitoring & Operations

  • Monitor pg_stat_activity for long-running queries and idle-in-transaction connections
  • Track bloat ratio via pgstattuple — investigate if dead tuple ratio exceeds 20%
  • Alert on replication lag (pg_stat_replication) — lag > 1 minute warrants investigation
  • Use pg_stat_statements to identify top queries by total time, calls, and rows
  • Set log_min_duration_statement = 1000 to log slow queries (>1s) automatically

🚀 Connection Management

  • Always use a connection pooler (PgBouncer) in production — each backend costs 5-10MB
  • Set max_connections based on actual needed backends, not client count
  • Use transaction-mode pooling for stateless web apps (most common pattern)
  • Set idle_in_transaction_session_timeout to kill abandoned transactions

Scaling & Trade-offs

📈 Capacity Estimation

A well-tuned single PostgreSQL instance (64 cores, 256GB RAM, NVMe SSD) can handle ~50K TPS for OLTP workloads and store multiple terabytes. Read replicas scale reads linearly.

~50K TPS on modern hardware

⇄ Read Scaling

Streaming replicas handle read traffic. Use hot_standby_feedback to prevent conflicts. PgPool or app-level routing directs reads to replicas, writes to primary.

Near-linear scaling with replica count

⚒ Write Scaling

Vertical scaling first (bigger instance). Then: table partitioning, Citus for distributed tables, or application-level sharding. PG doesn't natively shard writes.

Requires external tooling beyond single-node

💥 Failure Scenarios

Primary down: Promote standby (pg_ctl promote, ~seconds). Disk full: WAL archiving halts, transactions fail. Runaway query: OOM killer may hit backends. Use statement_timeout.

Failover in seconds with proper HA setup (Patroni)

⚖ Consistency vs Availability

PG defaults to strong consistency (synchronous commits). For HA, trade some durability: synchronous_commit = off risks losing the last few ms of transactions on crash.

🛠 Partitioning Strategy

Declarative partitioning (range, list, hash) since PG 10. Essential for tables > 100M rows. Enables partition pruning, faster vacuums, and easier archival of old data.
