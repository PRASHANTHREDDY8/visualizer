Component Breakdown

Deep dive into each service's responsibilities, technology choices, and scaling characteristics.

OT

Collaboration Service

The heart of the system. Receives client operations, transforms them against concurrent edits using Operational Transformation, maintains canonical document state, and broadcasts transformed ops to all connected clients.

Operational Transform WebSocket Go / Java
D

Document Service

Handles document lifecycle: creation, deletion, sharing, permissions (viewer/commenter/editor), and metadata. Serves as the source of truth for document ownership and access control lists.

gRPC Spanner ACL Engine
P

Presence Service

Manages ephemeral, real-time state: who's viewing a document, cursor positions, active selections, and typing indicators. Uses Redis pub/sub for low-latency fanout. State is never persisted to disk.

Redis Pub/Sub Ephemeral State ~50ms latency
H

History Service

Stores full revision history as an append-only operations log. Supports time-travel (view doc at any point), named versions, revision comparison (diffs), and undo across editing sessions.

Event Sourcing Snapshot + Replay Diff Engine
S

Document Store (Bigtable)

Stores the latest materialized document snapshot plus metadata. Optimized for fast reads of the current state. Periodically compacted from the ops log to avoid replaying entire history on load.

Bigtable / Spanner Row-level locking Geo-replicated
Q

Operations Log (Event Store)

Append-only log of every operation applied to every document. The authoritative history. Enables replay for conflict resolution, undo, and reconstructing any historical state. Partitioned by document ID.

Append-only Partitioned by doc_id Kafka / Spanner

Comparisons with Alternatives

How OT compares with other real-time collaboration strategies.

Approach Key Idea Pros Cons Used By
Operational Transform (OT)Chosen Transform concurrent ops against each other to maintain consistency Proven at scale, fine-grained character-level edits, low bandwidth Complex to implement correctly, server-dependent, hard to decentralize Google Docs, Microsoft Office Online
CRDT (Conflict-free Replicated Data Types) Data structures that automatically merge without conflicts No central server needed, works offline natively, mathematically proven convergence Higher memory overhead (tombstones), complex for rich text, eventual consistency semantics Figma, Apple Notes, Yjs-based apps
Last-Writer-Wins (LWW) Latest timestamp wins on conflict Dead simple to implement, works with any storage Loses edits silently, poor UX for simultaneous editing, needs synchronized clocks Dropbox (file-level), simple note apps
Locking / Turn-based Only one user can edit a section/document at a time No conflicts possible, simple mental model Blocks collaboration, poor UX, doesn't scale for real-time co-editing SharePoint (legacy), traditional wikis

When to pick each

Choose OT when...

You need proven, character-level real-time collaboration with a central authority. Best for text-heavy documents where latency must be minimal and you have server infrastructure.

Choose CRDT when...

Offline-first is critical, you want peer-to-peer sync, or decentralization matters. Better for structured data (trees, lists) and when you can tolerate higher memory usage.

Choose LWW when...

Collaboration is rare, data units are coarse-grained (whole files), or conflicts are acceptable losses. Simple to implement but poor for true collaborative editing.

Use Cases & Common Pitfalls

Primary Use Cases

Collaborative Document Editing

Multiple users editing the same document in real-time with character-level granularity — the canonical Google Docs experience.

1M+ concurrent docs

Collaborative Spreadsheets

Cell-level concurrent editing with formula dependency tracking and real-time recalculation across users.

10K cells/sheet active

Collaborative Presentations

Slide-level editing with object manipulation (shapes, text boxes) and presenter mode with live audience view.

100 concurrent editors

Code Editors (Pair Programming)

Real-time code collaboration with syntax-aware operations, shared terminals, and cursor following.

2-10 concurrent users

Anti-Use-Cases

High-frequency numerical data

Stock tickers, IoT sensors, game state — update rates too high for OT. Use state-sync or CRDT counters instead.

Binary file editing

Images, videos, CAD files — OT works on structured text, not arbitrary binary. Use file-locking or specialized merge tools.

Append-only logs / chat

Messages are never concurrent on the same content. Simple ordering (timestamp + tiebreaker) suffices without OT complexity.

Common Pitfalls

Not handling the "transform puzzle" — OT composition correctness +

The mistake: Implementing OT with only pairwise transform without handling the diamond property (TP2) or composition of operations.

Why it happens: Basic insert/delete transforms seem straightforward for 2 users, but break with 3+ concurrent editors or batched ops.

Consequence: Documents diverge silently — User A sees different content than User B. Corruption accumulates over time.

Fix: Use a proven OT library (ShareJS, ot.js) or adopt a CRDT. If building custom OT, implement rigorous property testing with randomized concurrent operation sequences.

Treating presence state as durable data +

The mistake: Storing cursor positions and online status in a persistent database instead of ephemeral in-memory storage.

Why it happens: Developers apply the same persistence pattern to all state. Presence feels like "data" that should survive restarts.

Consequence: Ghost cursors (stale presence from disconnected users), high write amplification to DB, increased latency on presence updates.

Fix: Use Redis with TTL keys and pub/sub. Presence is inherently ephemeral — if a user disconnects, their state should vanish within seconds via TTL expiry.

Unbounded operation history without snapshotting +

The mistake: Storing every operation ever applied to a document without periodic snapshot compaction.

Why it happens: Event sourcing purists want to keep the complete history for replay. Works fine in testing but breaks at scale.

Consequence: Opening a heavily-edited document requires replaying thousands of ops. Load time degrades linearly with edit count. Storage costs explode.

Fix: Periodically create document snapshots (e.g., every 100 ops or every hour). On load, start from nearest snapshot and replay only recent ops. Archive old ops to cold storage.

Single-server collaboration without horizontal scaling +

The mistake: Routing all editors of a document to a single server instance without a plan for hot documents.

Why it happens: OT requires sequential ordering, so it seems natural to pin a document to one server. Works until a viral document gets 10K simultaneous editors.

Consequence: Hot documents overwhelm a single node. Memory exhaustion, increased latency, and if that node fails, all editors disconnect.

Fix: Partition by document but support read replicas for presence fan-out. For extremely hot docs, split into sections with independent OT channels. Use a sequencer service (Paxos/Raft) rather than a single server.

Not implementing exponential backoff for reconnection +

The mistake: Clients immediately retry WebSocket connections on disconnect without backoff or jitter.

Why it happens: Developers want instant reconnection for good UX. Seems fine in local testing with 1-2 clients.

Consequence: Thundering herd — if a server restarts, thousands of clients reconnect simultaneously, overwhelming the new server and potentially cascading the failure.

Fix: Exponential backoff with jitter (base * 2^attempt + random). Cap at 30s. Show a "reconnecting..." UI so users know the system is recovering.

Best Practices

Proven patterns for building reliable collaborative editing systems.

Design Phase

  • Define max concurrent editors per doc (informs OT server sizing)
  • Choose OT vs CRDT based on your network model early
  • Design the operation schema before the UI (insert, delete, format, etc.)
  • Plan for offline: buffer ops locally, replay on reconnect
  • Set latency SLA: p99 < 200ms for op propagation

Implementation

  • Use operation-based (not state-based) sync for bandwidth efficiency
  • Assign monotonic revision numbers to every operation
  • Implement client-side prediction: apply ops locally, confirm from server
  • Batch rapid keystrokes into single ops (debounce 50-100ms)
  • Use protocol buffers for wire format (50-70% smaller than JSON)

Operational

  • Monitor: ops/sec per document, transform queue depth, WebSocket count
  • Alert on divergence: periodically checksum client vs. server state
  • Graceful degradation: fall back to polling if WebSocket fails
  • Blue-green deploy: drain WebSocket connections gracefully on deploys
  • Load test with realistic editing patterns, not just random ops

Scaling

  • Shard by document ID — one doc's state lives on one node
  • Use consistent hashing for doc→server mapping with virtual nodes
  • Cache hot documents in memory, lazy-load cold ones from storage
  • Snapshot every N ops to bound replay time on doc open
  • Separate presence fan-out from OT processing (different scaling axes)

Back-of-envelope estimates and how the system handles growth.

Scaling Strategy

10x growth: Add more collaboration server nodes. Consistent hashing redistributes docs. Cache layer absorbs read spikes.

100x growth: Geo-replicate collaboration clusters per region. Split hot documents into section-level OT channels. Move to CRDT for cross-region sync to avoid single-master bottleneck.

Key Trade-offs

Consistency vs. Latency: OT guarantees eventual consistency with low-latency local prediction. Users see their own edits instantly (optimistic UI).

Memory vs. Load Time: Keeping docs in server memory = fast ops but limits docs/server. Evict cold docs with LRU, reload from snapshot on next access.

Failure Scenarios

Collab server crash: Clients reconnect to another node. Ops log ensures no data loss — new server replays from last snapshot.

Network partition: Clients buffer ops locally. On reconnect, server transforms buffered ops against any missed concurrent edits. Convergence guaranteed by OT properties.
